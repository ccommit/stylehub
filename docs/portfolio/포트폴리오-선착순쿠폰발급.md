# 선착순 쿠폰 발급 API 동시성 / 성능 개선

## 한 줄 요약

> 선착순 쿠폰 발급의 동시성 제어를 *비관적 락 → 분산 락 → Redis DECR + Lua atomic + 비동기 저장* 으로 진화시키며 **4 가지 메커니즘 정량 비교**. 다중 인스턴스 환경 (4 인스턴스 + nginx LB + Spring Session) 에서 *최종 RPS 640+, fails 0, 정합성 100%* 도달. 누적 ~80 만 reqs 측정에서 *음수 카운터 / 중복 발급 0 건* 검증.

## 프로젝트 개요

- **도메인**: 선착순 쿠폰 발급 API (`POST /api/v1/coupon-events/{id}/issue`)
- **시나리오**: 평상시 트래픽의 수십 배가 *순간 폭주* 하는 이벤트 오픈 시점
- **검증 목표**: 100 장 한도에 500 명이 동시 hit 시 *정확히 100 명만 발급* + *최대 RPS*
- **측정 도구**: Locust 2.43.4 + 자체 작성 시나리오 + nginx LB
- **환경**: 단일 머신 + Spring Boot 4 인스턴스 + MySQL + Redis (모두 동거)

## 발견한 문제

### 동시성 제어의 *영역별 적합성* — 통념과의 충돌

처음 락 후보 검토 시 가설: *"비관적 락 → 다중 인스턴스 가면 분산 락이 답"*. 분산 락 인프라 (`@DistributedLock` AOP, SpEL 동적 키, UUID 자기 락 해제) 까지 미리 만들어 두었음.

그러나 *실제로 측정해보지 않으면 진짜 답을 모름*. 동시성 영역의 핵심 질문:

1. *어떤 락 메커니즘이 어느 영역에 맞는가?*
2. *통념 (분산 락 = 효율적) 이 우리 환경에서도 옳은가?*
3. *대용량 트래픽 가정의 다중 인스턴스 환경에서 어떻게 달라지는가?*

→ **4 가지 메커니즘 정량 비교 + 단일/다중 인스턴스 환경 매트릭스** 측정 필요.

### 시나리오 문서 검증 케이스 (`성능테스트-시나리오.md` 시나리오 4)

1. 100 장 / 500 명 → 정확히 100 발급
2. 같은 user 중복 → 1 번만 성공 (409 ALREADY_ISSUED)
3. 만료/시작 전 쿠폰 → 전원 400
4. 1000 장 / 1000 명 → SOLD_OUT 없이 전원 성공
5. 부하 단계: 50 / 200 / 500 / 1000

## 진단 과정 — 가설과 검증의 반복

### v1 — DB 비관적 락 (시작점)

```java
@Transactional
public void issueCoupon(User user, Long couponEventId) {
    CouponEvent event = couponEventRepository.findByIdWithLock(couponEventId);  // SELECT FOR UPDATE
    couponValidator.validateIssuable(event);
    checkDuplicateIssue(user.getUserId(), couponEventId);
    event.increaseIssuedCount();
    userCouponRepository.save(UserCoupon.create(user, event));
}
```

**측정 결과** (단일 인스턴스, 500 user / 100 장):
- RPS 630, Avg 459 ms, fails 0, 정합성 100/100/100

**한계**: DB row lock 큐 — 500 user 가 *직렬화* 대기. 평균 *459 ms 락 대기*.

### v2 — Redis 분산 락 (`@DistributedLock` SETNX 폴링) — *예상 못 한 실패*

```java
@DistributedLock(key = "'coupon:' + #couponEventId", waitTime = 5000, leaseTime = 3000)
public void issueCoupon(...) { ... }
```

**측정 결과**:
- RPS **190** (1/3 로 떨어짐)
- Avg **2,084 ms** (4.5 × 느려짐)
- **5xx 24.7 %** (분산 락 timeout 폭증)

**원인 추적**:
- 50 ms 능동 폴링 — *fairness 없음*, CPU/네트워크 낭비
- waitTime 5 초 안에 락 받지 못한 user 가 `INTERNAL_SERVER_ERROR (500)` throw
- DB row lock (kernel-level FIFO) 보다 *구조적으로 거친 grain*

→ ***측정으로 통념 반박***. *"분산 락이 다음 단계"* 라는 가설을 *데이터로* 깨뜨림.

### v3 — Redis DECR + Lua atomic ⭐ (정점)

핵심 통찰: ***락 자체를 제거*** — Redis 단일 스레드 atomic 모델 활용.

```java
// Lua script — 카운터 차감 + 중복 검증을 *atomic 한 묶음* 으로
private static final RedisScript<Long> ISSUE_COUPON_SCRIPT = new DefaultRedisScript<>(
    "local counterKey = KEYS[1]\n" +
    "local issuedSetKey = KEYS[2]\n" +
    "local userId = ARGV[1]\n" +
    "local maxCount = tonumber(ARGV[2])\n" +
    "\n" +
    "if redis.call('SISMEMBER', issuedSetKey, userId) == 1 then return -2 end\n" +
    "if redis.call('EXISTS', counterKey) == 0 then\n" +
    "    redis.call('SET', counterKey, maxCount)\n" +
    "end\n" +
    "local remaining = redis.call('DECR', counterKey)\n" +
    "if remaining < 0 then\n" +
    "    redis.call('INCR', counterKey)\n" +
    "    return -1\n" +
    "end\n" +
    "redis.call('SADD', issuedSetKey, userId)\n" +
    "return remaining\n",
    Long.class
);

public void issueCoupon(User user, Long couponEventId) {
    CouponEvent event = couponEventRepository.findById(couponEventId);  // 락 X
    couponValidator.validateIssuable(event);

    Long result = stringRedisTemplate.execute(ISSUE_COUPON_SCRIPT, ...);
    if (result == -1L) throw SOLD_OUT;
    if (result == -2L) throw ALREADY_ISSUED;

    eventPublisher.publishEvent(new CouponIssuedEvent(...));  // 비동기 저장 (v4)
}
```

**측정 결과**:
- RPS **640+** (비관적 락 +22 %, 분산 락 +228 %)
- Avg 402 ms, **5xx 0** (락 timeout 자체 없음)
- 정합성 100/100/100

### v4 — 비동기 저장 (Spring Event + @Async) — *예상 미달 발견*

```java
// 응답 즉시 반환, DB INSERT 는 백그라운드
public void issueCoupon(...) {
    // ... Lua atomic 동일
    eventPublisher.publishEvent(new CouponIssuedEvent(user.getUserId(), couponEventId));
}

@Async("couponInsertExecutor")
@EventListener
public void handleCouponIssued(CouponIssuedEvent event) {
    userCouponRepository.save(UserCoupon.create(...));
}
```

**가설**: DB INSERT 가 천장 → RPS 1,500 ~ 3,000 가능성

**측정 결과**: RPS 632 (거의 동일)

**발견**: *DB INSERT 가 진짜 병목이 아니었음*. 다른 천장 (Locust wait_time / 단일 머신 CPU) 이 한계.

→ *측정으로 가설 부분 반박*. 다만 비동기의 *진짜 가치 (피크 흡수 / DB 자원 분리 / 장애 격리)* 는 *우리 단일 머신 측정 환경 너머*. 운영 이점은 명확하므로 코드 채택.

## 개선 과정 — 측정 사이클별 단계 적용 + 매번 Before/After 측정

### Step 1 — atomic UPDATE 시도 (시리즈 1, 재고 차감 영역)

선행 시리즈에서 *atomic UPDATE 가 락 점유 시간 0* 임을 입증 (RPS 8.8 ×). *재고 차감* 에는 atomic UPDATE 가 답이지만, *선착순 쿠폰* 처럼 *여러 단계 묶음 (검증 + 카운터 + INSERT)* 영역에는 적용 불가.

### Step 2 — DB 비관적 락 측정 (단일 인스턴스 베이스라인)

- 환경: 단일 인스턴스 / 500 user / 100 장
- 결과: RPS 630, Avg 459 ms, 정합성 100% ✅

### Step 3 — Redis 분산 락 (`@DistributedLock`) 적용 + 측정

- 가설: 분산 락이 더 나을 것
- 결과: RPS 190 / 24.7% 5xx (가설 *반박*)

### Step 4 — 다중 인스턴스 환경 구축

- 4 Spring Boot 인스턴스 (port 8080~8083) + nginx LB (port 8090)
- nginx `hash $cookie_JSESSIONID consistent` (sticky session)
- *발견*: Tomcat 메모리 세션이 다중 인스턴스에서 동작 안 함 (401 폭증)

### Step 5 — Spring Session + Redis 도입 (3 줄)

```gradle
implementation 'org.springframework.session:spring-session-data-redis'
```

```java
@EnableRedisHttpSession
@SpringBootApplication
public class StylehubApplication { ... }
```

→ 모든 인스턴스가 *공유 세션* 사용. 다중 인스턴스 환경 완성.

### Step 6 — 다중 인스턴스 환경에서 4 메커니즘 재측정

| 환경 | 비관적 락 | 분산 락 (SETNX) | Redis DECR (Lua) | + 비동기 |
|---|---|---|---|---|
| 단일 인스턴스 | RPS 630 | RPS 190 | — | — |
| 다중 인스턴스 | RPS 526 | RPS 195 | **RPS 640** ⭐ | RPS 632 |

→ *"다중 인스턴스 가면 분산 락이 빛날 것"* 가설 *완전 반박*. 분산 락은 인스턴스 수와 *무관 (Redis 가 천장)*. 비관적 락이 *어떤 환경에서도* 분산 락보다 우월. **Redis DECR + Lua atomic 이 모든 차원에서 정점**.

### Step 7 — 부하 단계별 곡선 (시나리오 문서 검증)

| Users | RPS | Median | Max | 정합성 |
|---|---|---|---|---|
| 50 | 88 | 7 ms | 374 | ✅ |
| 200 | 257 | 89 ms | 307 | ✅ 100/100 |
| 500 | 640 | 380 ms | 6,510 | ✅ 100/100 |
| **1000** | **402** | **700 ms** | **19,504** | **✅ 1000/1000** |

→ *시나리오 문서의 모든 검증 케이스 + 부하 4 단계 충족*.

### Step 8 — fast-fail 경로 정량 검증

| 케이스 | Median | 비교 |
|---|---|---|
| 정상 발급 (200 user) | **89 ms** | 기준 |
| 만료 fast-fail (CP004) | **6 ms** | **15 × 빠름** ⚡ |
| 시작 전 fast-fail (CP003) | **7 ms** | **13 × 빠름** ⚡ |

→ *시나리오 문서의 "fast-fail 응답이 정상 처리보다 빠르게" 가설 정량 입증*.

## 왜 그렇게 했는지 — 의사결정 근거

### 1. 왜 *비관적 락이 아닌 Redis DECR* 을 최종 채택했는가

측정 데이터로 *압도적 우월성* 입증:
- RPS: 비관적 락 +22 %, 분산 락 +228 %
- 5xx: **0** (락 timeout 자체 없음 — 락이 없으니까)
- 정합성: 둘 다 100 % (Lua atomic 이 보장)
- DB 부하: 락 자체 X → DB 자원 보호

→ *측정으로 입증된 더 나은 선택 *을 따르는 것이 측정 기반 의사결정.

### 2. 왜 *분산 락 (SETNX 폴링) 채택 안 했나*

측정 결과 *모든 환경에서 더 나쁨*:
- 단일/다중 인스턴스 모두 비관적 락보다 RPS 1/3
- 24~28 % 5xx 발생 (waitTime timeout)
- *50 ms 능동 폴링 의 본질적 한계*

→ *"분산 락 = 다중 인스턴스 표준"* 통념을 *데이터로 반박*. 다만 인프라 (`@DistributedLock` AOP) 는 *다른 도메인 (선착순 쿠폰 외) 또는 Redisson 으로 교체* 가능성을 위해 *보존*.

### 3. 왜 *낙관적 락 검토 안 했나*

낙관적 락은 *low contention 영역* (사용자 프로필 수정 등) 에 적합. 선착순 쿠폰의 *high contention* (500 user 가 동일 row 동시 hit) 에서는 *retry 폭주* 로 RPS 매우 낮음. *측정 안 해도 구조상 명백히 부적합*.

### 4. 왜 *비동기 저장 (Spring Event + @Async) 채택했나*

측정으로 RPS 향상 입증 *못 함* (DB INSERT 가 진짜 병목이 아니었음). 그러나:
- *정합성 패턴* 깔끔 (Redis source of truth)
- *운영 시 진짜 가치* 명확 (피크 흡수 / DB 자원 분리 / 장애 격리)
- 측정 환경 너머의 가치 — 운영 이점 인정

→ *측정으로 직접 입증 안 된 영역도, 설계 의도가 명확하면 채택*. 단, 면접에서 *"측정으로 입증?"* 질문에 *솔직히* 답할 수 있게 *측정 한계 명시*.

### 5. 왜 *다중 인스턴스 환경 구축 + Spring Session* 까지 갔는가

*"단일 인스턴스 측정만으로 *대용량 트래픽 서버* 결론 짓는 건 약함"* 자기 점검 후 진행. 결과: *분산 락 가설 반박, Redis DECR 정점 도달, Spring Session 도입* 등 *narrative 정점*. 사용자 (멘토) 피드백을 *측정 자체로* 답한 사례.

### 6. 왜 *측정의 한계를 정직히 명시했는가*

```
측정 환경의 한계:
- 단일 머신 (앱 + DB + Redis + Locust 동거)
- Redis 단일 노드 (Cluster 가 아님)
- SETNX 폴링 직접 구현 (Redisson 같은 성숙한 라이브러리 X)
- HikariCP pool 25 / 인스턴스 (작은 풀)
- 측정 시간 1~2 분 (장기 안정성 X)
```

→ *"비관적 락 우월" 같은 결론은 *우리 측정 환경에서 RPS 차원* 에서만 옳음*. *수평 확장성, 장애 내성, 요구사항 적합성* 은 *측정 못 한 영역*. **측정의 영역과 한계를 정확히 분리하는 것이 측정 기반 의사결정의 진정성**.

## 프로젝트를 통해 얻은 것

### 기술적 스킬

- **Redis Lua scripting** — atomic 한 멀티 명령 처리, lazy init, 음수 보정 패턴
- **Spring Session + Redis** — 다중 인스턴스 세션 외부화 (`@EnableRedisHttpSession`)
- **Spring Event + @Async** — 비동기 처리 + 도메인별 ThreadPoolTaskExecutor 격리
- **nginx LB + cookie hash** — sticky session 패턴 + ip_hash 함정 회피
- **Locust 자체 작성 시나리오** — pymysql 연동, 세션 풀 사전 구축, 의도된 실패 vs 진짜 에러 분리
- **JPA `@Lock(PESSIMISTIC_WRITE)`, `@DistributedLock` AOP, Redis SETNX, Redis DECR** — 4 가지 동시성 메커니즘 구현 + 비교

### 분석 / 의사결정 스킬

- **가설 → 측정 → 반박/검증 사이클** — 4 가지 메커니즘 모두 측정으로 검증
- **통념 반박** — *"분산 락이 다음 단계"* 가설을 *데이터로* 깨뜨림
- **측정 한계 인정** — *"내가 측정한 것 vs 측정 못한 것"* 분리 명시
- **다중 인스턴스 환경의 함정** — Tomcat 메모리 세션의 분산 한계 *발견 + 즉시 해결*
- **fast-fail 경로 정량 검증** — *15 × 빠름* 으로 시나리오 문서 가설 입증
- **혼합 환경 정합성 깨짐 사례** — *"한 인스턴스만 옛 코드"* 가 *전체 정합성* 깨뜨림 발견

### 운영 / 설계 스킬

- **헥사고날 Port + Application/Service 분리** — 도메인 서비스가 락 메커니즘 변경에 유연
- **eventual consistency 패턴** — Redis source of truth + DB 비동기 저장
- **AOP 인프라 보존 + 운영 코드 분리** — `@DistributedLock` 유지, 적용 영역만 신중히 결정
- **시나리오 문서 기반 측정** — 검증 케이스 4 가지 + 부하 4 단계 모두 충족

## 진짜 다음 단계 (열린 영역)

이번 시리즈의 *측정 한계 너머* — *별도 시리즈* 에서 다룰 영역:

1. **Redisson `RLock` (pub-sub) 비교 측정** — 단순 SETNX 폴링의 한계 극복
2. **Redis Cluster 환경** — 분산 락 throughput 천장 상승
3. **별도 머신 + 다중 인스턴스 (수십 대) + 클라우드** — *진짜 대용량* (5K+ RPS) 측정
4. **Kafka 비동기 파이프라인** — 비동기 저장의 진짜 가치 (피크 흡수) 측정
5. **Chaos test** — 장애 내성 정량 검증

→ *"단일 머신 11 번가급 검증 + 다음은 클라우드 + Cluster + Kafka 영역"* 으로 *진짜 진짜 대용량 트래픽 서버* 검증 가능.
