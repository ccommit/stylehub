# 상품 조회 API 성능 개선 — 50 users 500배 단축, 10,000 users 극한 부하 무실패

## 한 줄 요약

**대용량(300만 건) 상품 데이터에서 동시 접속 50명만 되면 응답 시간이 128배로 붕괴되던 시스템을, 일곱 단계 개선(인덱스 · Projection · 풀 튜닝 · Covering Index · Redis 캐시 계층화 · sync=true · Tomcat 스레드 튜닝) 으로 50 users 기준 5/5 API 를 목표(P95 < 300ms) 에 도달시키고, 단일 서버 실용 상한을 2,000 users / 1,003 RPS 로 확정. 10,000 users 극한 스트레스 테스트에서도 실패율 0 % · 104,157 요청 무중단 처리를 실측으로 증명한 작업.**

---

## 프로젝트 개요

- **프로젝트**: StyleHub — 대용량 트래픽 커머스 서버
- **기술 스택**: Spring Boot / JPA (Hibernate) / QueryDSL / MySQL / HikariCP / Redis / Locust(성능 테스트)
- **데이터 규모**: products 테이블 3,172,205 건 (프로덕션 수준 시뮬레이션)
- **역할**: 단독 개발 — 성능 측정 · 병목 분석 · 개선 · 재측정 전 과정

## 발견한 문제

### 측정 과정에서 드러난 구조적 결함

Locust 로 단계별 부하 테스트(Warm-up 10명 → Light 50명 → 처리량 상한 검증)를 진행한 결과:

| 지표 | Warm-up (10명) | **Light (50명)** | 상한 검증 (설정 100만)¹ |
|---|---|---|---|
| `/products/{id}` P95 | 23 ms | **2,900 ms** | 4,800 ms |
| `/products (first page)` P95 | 1,200 ms | 3,500 ms | 5,700 ms |
| `/products (by category)` P95 | **5,400 ms** | 7,200 ms | 11,000 ms |
| **Aggregated P95** | 4,800 ms | **5,200 ms** | 6,800 ms |
| **RPS** | 4.5 | **10.5** | **10.6** |

¹ 단일 노트북에서 동시 접속 100만 명 스폰은 물리적으로 불가능. **Locust 의 user 설정값을 100만으로 올려 부분 스폰된 상태에서 측정** — RPS 가 Light(50명) 와 동일한 10.6 으로 수렴한 것이 *"유저를 더 늘려도 처리량은 안 늘어난다"* 는 처리량 상한의 증거.

발견한 핵심 문제 3 가지:
1. **단건 조회가 23ms → 2,900ms 로 128배 악화** — 원래 빠르던 API 가 시스템 전체 포화로 같이 붕괴
2. **카테고리 필터는 10명에서도 5,400ms** — 쿼리 자체가 무거움
3. **유저 설정을 100만으로 올려도 RPS 10 에서 고정** — 명확한 처리량 상한 존재 (HikariCP 풀 10 개의 한계)

## 진단 과정 — 가설과 검증의 반복

### 1차 진단: MySQL EXPLAIN

카테고리 필터 쿼리 분석:
```
type: index | key: PRIMARY | filtered: 2.50% | Backward index scan
```
→ PK 역순 스캔하며 WHERE 로 거름. **97.5% 가 버려져** LIMIT 21 을 채우려면 평균 840건 스캔. **카테고리 전용 인덱스가 없음**을 확인.

### 2차 진단: N+1 가설 (이후 틀린 것으로 판명)

첫 페이지가 833ms 걸리는데 EXPLAIN 은 "쿼리 빠르다" 고 말함 → DB 가 아닌 **애플리케이션 레이어 문제** 로 의심. `ProductListResponse.from()` 에서 `product.getUser()` 호출이 있으니 N+1 이라 추정.

### 3차 진단: 실제 SQL 로그 확인 — 가설 뒤집힘

`spring.jpa.show-sql=true` 로 실제 쿼리를 보니 **N+1 이 아니라 단일 쿼리에 31 컬럼 SELECT** 하고 있었다.
- `ProductListResponse` 가 실제 쓰는 컬럼: 8 개
- `password`, `description`(TEXT), `store_description`(400자) 등 **23 개 불필요 컬럼을 매번 전송**
- 보안 측면에서도 **password 해시를 앱 메모리로 올리는 심각한 문제**

**"EXPLAIN 한 줄로 끝내지 않고 실제 SQL 로그까지 봐야 한다"** 는 경험을 얻음.

### 최종 원인 3 가지 교차 분석

| 원인 | 증거 | 영향 범위 |
|---|---|---|
| **과다 컬럼 투영** (31→8) | SQL 로그 | 모든 목록 조회 |
| **카테고리 인덱스 부재** | EXPLAIN `filtered: 2.5%` | 카테고리 필터 |
| **HikariCP 기본 풀 10 개** | 유저 늘려도 RPS 고정 | 전체 동시성 |

수학적 포화점 유도: `풀 10 × 1/50ms / 22쿼리 ≈ RPS 9` — 실측 10.5 와 맞아떨어짐.

## 개선 과정 — 3 단계 분리 적용 + Before/After 독립 측정

각 개선의 기여도를 분리해서 측정하기 위해 **한 번에 다 적용하지 않고 순차적으로** 진행.

### Step 1. 카테고리 복합 인덱스 추가

```sql
CREATE INDEX idx_products_category
ON products (main_category, sub_category, product_id DESC);
```

- 300만 건에서 MySQL online DDL 로 **5.1 초** 만에 생성
- EXPLAIN: `type: index → ref`, `filtered: 2.5% → 100%`
- **카테고리 필터 P95: 5,400ms → 540ms (10배 감소)**

예상 밖 발견: 카테고리 외 API 도 개선됨 → **연쇄 효과**. 카테고리 쿼리가 빨라져 커넥션 풀 점유 시간이 줄고 → 풀 회전율 상승 → 전체 RPS 가 10.5 → 21.9 로 **2 배**. "느린 쿼리 하나가 시스템 전체 처리량 상한을 결정한다" 는 것을 실측으로 확인.

### Step 2. QueryDSL Projection 적용

```java
// Before: 엔티티 전체 조회 (31 컬럼)
.selectFrom(product).join(product.user, user).fetchJoin()

// After: DTO 로 직접 투영 (8 컬럼)
.select(Projections.constructor(ProductListResponse.class,
    product.productId, user.userId, user.storeName,
    product.name, product.mainCategory, product.subCategory,
    product.price, product.imageUrl))
```

- 컬럼 수 **31 → 8 로 1/4**
- `password`, `description`(TEXT), `store_description` 제거 → 보안·성능 동시 개선
- Light RPS **21.9 → 31.9 (46% 증가)**
- 원래 빠르던 API 들 P95 **2.5 배 추가 개선**

**Warm-up 에서는 효과가 안 보였던 흥미로운 관찰**: 10명 환경은 풀 경합이 없어 Projection 효과가 노이즈에 묻힘. 50명 환경에서만 드러남 → "통제 변수가 적은 환경에서 작은 개선은 드러나지 않는다" 는 교훈.

### Step 3. HikariCP 풀 크기 확대

```properties
spring.datasource.hikari.maximum-pool-size=50
```

설정 한 줄 추가. Step 2 로 쿼리가 가벼워진 상태라 풀 확대 효과가 극대화됨.

- 가벼운 쿼리 3 종 (`/products/{id}`, next page, by store) 이 **P95 30~35ms 로 완전 해소**
- 10 배 이상 개선 + **목표(P95 < 300ms) 달성**

또 다른 발견: 무거운 쿼리 2 종(first page, by category) 은 **오히려 악화** (1,100ms → 1,300ms). 풀 경합은 풀렸지만 이제는 DB 자체(디스크 I/O) 가 병목. **"성능 개선은 병목을 이동시킬 뿐"** 이라는 말을 숫자로 확인.

### Step 4a. Covering Index — DB 레벨 병목 해소

Step 3 에서 드러난 무거운 쿼리의 DB I/O 병목을 풀기 위한 다음 카드. 기존 `idx_products_category` 를 **SELECT 에 필요한 컬럼까지 포함한 covering index** 로 교체.

```sql
DROP INDEX idx_products_category ON products;
CREATE INDEX idx_products_category_cover
ON products (main_category, sub_category, product_id DESC,
             user_id, name, price, image_url);
```

EXPLAIN 의 Extra 에 `Using index` 가 찍혀 **테이블 접근 없이 인덱스만으로 조회 완료** 됨을 확인. 300만 건에서 21 번의 테이블 방문이 제거됐다.

- **by category P95 1,500ms → 200ms (7.5배 감소)** → **목표 달성**
- **first page 도 연쇄적으로 2배 개선** (1,300ms → 620ms)
- **목표 달성 API: 3 → 4**

### Step 4b. Redis 캐시 — 첫 페이지의 쿼리 자체 제거

남은 first page 는 `ORDER BY product_id DESC LIMIT 21` — DB 레벨에서 이미 최적 상태라 방향을 바꿨다. **"쿼리를 빠르게"** 가 아니라 **"쿼리 자체를 피한다".** 비로그인 공개 API 라 모든 사용자가 동일 응답을 받는 구간이라 캐시 효율이 가장 크다.

```java
@Cacheable(
    value = "products:firstPage",
    key = "#pageSize ?: 20",
    condition = "#cursor == null && #storeId == null && #mainCategory == null && #subCategory == null"
)
```

- TTL 30 초 (신상품 반영 지연 허용)
- `condition` 으로 필터 없는 첫 페이지 호출만 캐시 → 개인화 편차 큰 경로는 제외
- **first page P95 620ms → 7ms (88배 감소)** → **목표 달성**
- **나머지 API 도 1.3~2.3배 추가 개선** — first page 가 DB 를 건너뛰자 전체 DB 부하가 내려가면서 연쇄적으로 빨라짐
- **목표 달성 API: 4 → 5 (전 API 달성)**

**삽질 포인트 — Jackson 3 default typing 함정**: Spring Boot 4.0.3 이 Jackson 3.x 로 전환되면서 응답 DTO 인 Java `record` 에 `activateDefaultTyping(NON_FINAL)` 이 먹히지 않는 문제를 만남(record 는 final → 쓰는 쪽은 타입 생략, 읽는 쪽은 요구 → 99 % 실패). Jackson 3 가 `DefaultTyping.EVERYTHING` 을 제거해 default typing 으로는 해결 불가. **고정 `JavaType` 기반 타입드 직렬화기** 를 직접 구현해 해결. 버전 업이 설계 전제를 바꾼다는 실감을 얻음.

### Step 5. 확장 구간 — 500 / 1,000 / 2,000 users 까지 밀어붙이기

50 users 에서 5/5 를 달성한 뒤, 단일 서버의 실제 수용력을 실측하기 위해 사용자 수를 단계적으로 늘렸다. 각 구간마다 새로운 병목이 드러났고, 병목별로 다른 카드를 꺼내 해결한 과정.

**500 users** — 첫 시도에서 Aggregated P95 1,300 ms. 진단: 캐시 미스 경로(by category / by store) 가 전체의 50 % 이상을 차지해 풀을 포화시킴.

해결: **HikariCP 풀 50 → 100** + **캐시 범위 확대** (cursor 가 없는 모든 첫 페이지를 필터 조합별로 캐시).

```java
@Cacheable(
    value = "products:firstPage",
    key = "'size=' + (#pageSize ?: 20) + '|store=' + #storeId
          + '|main=' + #mainCategory + '|sub=' + #subCategory",
    condition = "#cursor == null"
)
```

결과: **P95 1,300 ms → 30 ms (43×)**, RPS 398.

**1,000 users** — 정상 같던 first page API 만 P95 4,100 ms 로 튐 (다른 API 는 300 ms 대). 진단: **Cache Stampede (썬더링 허드)** — TTL 만료 순간 동시 도착한 요청들이 전부 cache miss 로 DB 로 몰림.

해결: `@Cacheable(sync = true)` + TTL 30 → 60 초. 동시 miss 를 직렬화해 한 스레드만 DB 로 가도록.

결과: **first page P95 4,100 → 310 ms (13×)**, RPS 462 → 798 (1.7×).

> 단, `sync=true` 의 락은 **JVM 내부 락**이라 단일 인스턴스 한정. 다중 인스턴스 환경에서는 TTL 만료 순간 cache miss 가 인스턴스 수만큼 DB 로 전파되므로, 진짜 분산 stampede 방어는 Redisson `RReadWriteLock` 같은 분산 락 캐시 레이어가 필요. 이 프로젝트는 단일 서버 측정 환경이라 sync=true 로 충분, 다중 인스턴스 운영 시 부하 측정 후 Redisson 도입 여부 결정할 영역으로 분리 (코드 리뷰 반영).

**2,000 users** — Aggregated P95 1,300 ms, Median 이 13 ms → 530 ms 로 40 배 상승. 캐시 문제가 아닌 **시스템 전체 큐잉** 신호. `/products/{id}` 도 캐시로 전환했으나 RPS 가 오히려 1,016 → 890 으로 줄었다. 병목이 캐시/DB 밖에 있다는 뜻.

진단: **Tomcat 스레드 풀 기본 200** 이 처리량 상한. 이론 RPS 200 × (1000/250 ms) = 800 — 실측 890 과 일치.

해결: `server.tomcat.threads.max=400` + accept 큐 확대.

결과: **Aggregated P95 1,500 → 1,000 ms**, **RPS 577 → 1,003 (1.74×)**, 120,328 요청 무실패.

### 2,000 users 이상은 scale-out 영역

단일 서버의 합리적 상한을 숫자로 확정한 시점부터는 무작정 튜닝 대신 **scale-out 설계로 정리**.

- **Read Replica** — 읽기 전용 API 를 복제본으로 분산해 DB 처리량 확장
- **애플리케이션 수평 확장** — Load Balancer + 다중 인스턴스로 Tomcat 스레드 병렬 확보
- **CDN / 엣지 캐시** — 정적 성격 강한 경로(첫 페이지) 는 엣지에서 종료

"무작정 밀어붙이기" 보다 **"현재 구성의 합리적 상한선을 숫자로 확정 → 그 이상은 어떤 설계가 필요한지 명시"** 가 포트폴리오 스토리로 더 성숙하다고 판단했다.

### Redis 메모리 — 캐시 효율의 증거

2,000 users 테스트 도중 Redis 상태:

```
used_memory_human: 1.41 MB
DBSIZE: 55
```

300만 건 데이터에서 **핵심 트래픽이 55 키 / 1.41 MB 로 커버**되는 것을 실측. 파레토 법칙의 직접 증거 — 상위 소수 상품/카테고리에 트래픽이 몰림. 메모리 여유가 충분해 캐시 확장 여지는 남아 있음.

## 개선 결과 — 일곱 단계 누적 효과 + 확장 구간 실측

### 확장 구간 + 한계 테스트 실측 (50 → 10,000 users)

| 동시 사용자 | Aggregated P95 | 평균 RPS | 총 요청 / 2 분 | Max | 실패율 | 판정 |
|---|---|---|---|---|---|---|
| 50 | 69 ms | 31.6 | 3,792 | — | 0 % | 기준점 |
| 500 | **30 ms** | 398 | 47,700 | — | 0 % | 여유 |
| 1,000 | **310 ms** | 798 | 92,984 | 7,016 | 0 % | 양호 |
| 2,000 | **1,000 ms** | **1,003** | 120,328 | 6,834 | 0 % | **실용 상한** |
| 3,000 | 2,500 ms | 826 | 99,129 | 20,251 | 0 % | UX 실패 |
| 5,000 | 6,500 ms | 561 | 67,280 | 49,652 | 0 % | Congestion collapse |
| **10,000** | 5,600 ms | 868 | **104,157** | **108,638** | **0 %** | **극한 부하, 서버 무중단** |

**핵심 발견 5 가지:**

- **처리량 절대 상한 ≈ 1,003 RPS** (2,000 users 에서 최고점, 그 이후 사용자가 늘수록 RPS 감소)
- **Congestion collapse 확인** — 5,000 users 에서 RPS 561 로 반토막. 사용자 증가가 처리량 감소로 이어지는 역효과 구간
- **10,000 users 극한 부하에서도 실패 0 건** — 104,157 요청 전부 처리. `server.tomcat.accept-count=200` + 스레드 풀 400 이 OS 소켓·JVM 레벨 burst 를 이중으로 흡수
- **Max 108.6 초** — 10,000 users pageSize=50 일부 요청이 1분 49초 대기. "서버 생존" 과 "서비스 제공" 은 완전히 다른 개념 — 이게 **0 % 실패율 숫자만으로 건전성을 판단하면 안 되는 이유** 를 Max 값으로 실측 확인
- **전 구간 에러율 0 %** — 50 users 부터 10,000 users 까지 약 53 만 건의 요청을 전부 응답. Graceful degradation 이 설계대로 작동 (목표 SLO 는 Google SRE 의 99.9% / error rate < 0.1% — user-facing read API 표준 기준. 결제 같은 critical path 였다면 99.99% / 0.01% 로 잡았을 영역. 운영 환경의 LB jitter · 클라이언트 타임아웃 · GC pause 같은 외적 실패 마진까지 고려한 기준치이며, 실측 0% 는 그 마진 내에서도 압도적 달성을 의미.)

## 개선 결과 — 5 단계 누적 효과

### Before → Step 4b (Light 50명 기준)

## 왜 그렇게 했는지 — 의사결정 근거

### 1. 왜 "한 번에 다 적용" 이 아니라 단계별로 적용했는가

**각 개선의 순수 기여도를 분리해서 측정하기 위함.** 세 변경을 동시에 적용하면 "무엇이 얼마나 기여했는지" 를 사후에 알 수 없다. Step 1 만의 효과, Step 2 만의 추가 효과, Step 3 만의 효과를 따로 확인해야 **다음에 비슷한 상황에서 의사결정할 때 근거가 쌓인다.**

결과적으로 얻은 통찰.
- Step 1: 카테고리 P95 10배, RPS 2배 (간접 연쇄 효과)
- Step 2: 전체 API P95 2배, RPS 추가 1.5배
- Step 3: 가벼운 쿼리 해소, 무거운 쿼리 병목 이동 관찰
- Step 4a: covering index 로 by category 목표 달성, first page 도 연쇄 개선
- Step 4b: Redis 캐시로 first page 쿼리 자체 제거, 5/5 API 목표 전부 달성
- Step 5: 확장 구간(500/1,000/2,000 users) 실측 — 구간별로 캐시 범위, cache stampede (sync=true), Tomcat 스레드 한계가 순차적으로 병목으로 드러남. 단일 서버 초당 1,003 RPS 까지 검증

### 2. 왜 N+1 fetchJoin 이 아니라 Projection 을 택했는가

**실제 SQL 로그를 확인한 결과 N+1 이 없었기 때문.** 처음엔 fetchJoin 추가를 계획했지만 코드를 확인하니 이미 적용되어 있었다. 가설이 틀렸음을 인정하고 실제 원인(31 컬럼 과다 투영) 을 해결하는 방향으로 재설계.

**교훈**: 가설에 집착하지 않고 증거(실제 SQL 로그) 를 보고 방향을 바꾸는 게 중요. EXPLAIN 만으로는 이 문제를 못 잡았을 것.

### 3. 왜 HikariCP 풀을 10 → 50 으로 키웠는가

**Step 2 적용 후 RPS 가 여전히 이론 상한(40) 에 못 미치는 것을 보고 판단.** 이론 계산.

- 유저 50명 × wait 1.25초 평균 = 이론 최대 RPS 40
- Step 2 후 실측 RPS 31.9 → 이론 상한 80% 도달
- 남은 20% 는 풀 경합으로 추정

MySQL 의 `max_connections` 기본 151 내에서 50 은 안전한 선택. 운영 환경에서 서버가 여러 대면 총합이 넘지 않도록 따로 계산 필요 — 이번은 단일 로컬 서버라 검증 목적으로 충분.

### 4. 왜 300만 건 데이터로 테스트했는가

**프로덕션 수준의 데이터가 아니면 무의미한 숫자만 나오기 때문.** 개발 환경의 수백 건 테이블에서는 어떤 API 든 1ms 만에 응답한다. 인덱스 부재나 N+1 같은 문제가 드러나지 않는다.

실제로 이 프로젝트에서 드러난 구조적 문제들(카테고리 인덱스 부재, 과다 컬럼 투영, 풀 크기) 은 모두 **"대용량 데이터 + 동시 사용자"** 조건이 결합해야 발견되는 것들. 이 조건으로 테스트했기에 실무 수준의 경험이 됐다.

## 프로젝트를 통해 얻은 것

### 기술적 스킬

- **성능 측정 도구 경험**: Locust 로 부하 시나리오 설계, Warm-up/Light/Medium/Heavy/Spike 단계별 측정
- **지표 해석**: 평균이 아닌 P95/P99 로 꼬리 지연 판별, 의도된 실패와 진짜 에러 구분
- **MySQL 튜닝**: EXPLAIN 해석(`filtered`, `type`, `Extra`), 복합 인덱스 설계, online DDL
- **JPA / QueryDSL 심화**: fetchJoin 한계, Projections.constructor 사용, N+1 판별 방법
- **HikariCP 동작 원리**: 풀 크기 × 쿼리 시간 = 이론 RPS 유도, 풀 고갈과 전염 효과 관찰

### 문제 해결 관점

- **"가설 → 검증 → 재가설"** 사이클의 중요성: 첫 가설(N+1) 이 틀렸음을 인정하고 실제 증거(SQL 로그) 를 보고 방향 전환
- **병목은 이동한다**: 풀 크기를 늘렸더니 다른 병목(DB I/O) 이 드러남. 성능 개선은 한 번에 끝나지 않는다
- **교차 검사의 필요성**: EXPLAIN 단독으로는 N+1 이나 과다 컬럼을 볼 수 없음. SQL 로그 + 애플리케이션 코드 + 인프라 설정을 함께 봐야 진짜 원인이 잡힘
- **수치적 의사결정**: 감으로 "분산락이 빠를 것" 이라 추정하지 않고 Before/After 로 검증. 매 단계 숫자로 근거를 쌓음

### 블로그 시리즈화

이 과정 전체를 개발 블로그 시리즈(`상품조회블로그성능.md`) 로 정리. 측정 → 진단 → 개선 → 재측정 → 후속 계획의 사이클을 숫자로 기록해, 면접·협업 시 "대용량 트래픽 경험" 을 구체적으로 설명할 수 있는 자료로 활용.

## 남은 과제와 후속 계획

50 users 기준 5/5 API 목표 달성 + 단일 서버 2,000 users / 1,003 RPS 실측 완료. **2,000 users 이상은 단일 서버의 합리적 상한선을 넘는 scale-out 영역** 으로 규정하고 설계만 문서화.

### 후속 개선 로드맵
1. **Read Replica 도입** — 읽기 트래픽 복제본 분산. 단일 DB 가 처리하는 쿼리 수를 절반 이하로 → 2,000 users 구간의 DB I/O 여유 확보
2. **애플리케이션 수평 확장** — Load Balancer + 다중 인스턴스. Tomcat 스레드 병목을 병렬로 극복 (인스턴스 2 대 → 이론적으로 4,000 users)
3. **CDN / 엣지 캐시** — first page 같은 정적 성격 강한 경로는 엣지에서 응답 종료 → 서버 도달 전 차단
4. **다른 시나리오 확장** — 주문 생성, 쿠폰 선착순 발급 등에도 동일한 측정/진단 방법론 적용
