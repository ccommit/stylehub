## 1. 프로젝트 전반

**Q1. 왜 하필 대용량 트래픽·동시성을 포트폴리오 주제로 잡았나요?**

기능을 많이 만드는 것보다, 실무에서 실제로 부딪히는 "동시에 여러 요청이 몰릴 때 데이터가 틀리지 않는가"라는 문제를 직접 겪어보고 싶었습니다. 재고 1개짜리 상품에 10명이 동시 주문하면 실제로 2명이 성공하는 Lost Update가 재현된다는 걸 테스트로 직접 확인한 순간, 이론으로만 알던 문제를 몸으로 이해하게 됐고, 그 이후로 이 프로젝트의 축을 "기능 완성"에서 "동시성·성능 문제를 얼마나 근거 있게 풀어내는가"로 바꿨습니다.

**Q2. 왜 혼자 진행했나요? 협업 경험은 어떻게 쌓았나요?**

리소스 제약으로 혼자 진행했지만, 협업이 안 되는 프로젝트로 만들고 싶지 않아서 실무와 동일한 프로세스를 인위적으로 적용했습니다. 이슈 단위로 브랜치를 만들고 PR에 설계 결정과 트레이드오프를 남겼고, 멘토에게 정기적으로 코드 리뷰를 받았습니다. 예를 들어 스토어 입점 신청 로직에서 "User/Store가 별도 트랜잭션이라 원자성이 깨질 수 있다"는 지적을 받고 근거를 가지고 논의한 뒤 구조를 바꾼 경험이 있습니다(현재는 아예 User로 통합해 문제 자체를 없앴습니다).

**Q3. 이 프로젝트에서 가장 자신 있는 부분과 가장 아쉬운 부분은?**

가장 자신 있는 부분은 선착순 쿠폰에서 "다중 인스턴스면 분산 락이 유리하다"는 통념을 4가지 메커니즘을 직접 구현해 측정으로 반박한 부분입니다. 데이터로 통념을 깬 경험이라 가장 설명하고 싶은 사례입니다. 가장 아쉬운 부분은 그렇게 측정으로 검증한 Redis DECR 방식이 아직 실제 `CouponService` 코드에는 연결되지 않았다는 점입니다. 측정과 실제 반영 사이에 시간차가 있다는 걸 숨기지 않고 포트폴리오에도 그대로 남겼습니다.

## 2. DB 설계

**Q4. User와 Store를 왜 하나의 테이블로 합쳤나요? 트래픽이 커지면 다시 분리해야 하지 않나요?**

처음엔 분리돼 있었는데, 스토어 승인 흐름에서 User 생성과 Store 생성이 별도 트랜잭션으로 나뉘며 원자성이 깨지는 문제를 코드 리뷰에서 지적받았습니다. 스토어 역할이 회원 역할의 확장이라는 도메인 특성상 필드 통합이 더 단순한 해법이라 판단해 합쳤습니다. 트래픽이 커져서 스토어 관련 쓰기가 회원 조회와 부하 특성이 크게 갈리는 시점이 오면 다시 분리를 고려하겠지만, 지금 규모에서는 트랜잭션 경계 문제를 없애는 이득이 더 컸습니다.

**Q5. 애플리케이션에서 이미 중복 발급 체크를 하는데 왜 DB 유니크 제약도 걸었나요?**

애플리케이션 레벨 체크(`existsBy...`)는 두 요청이 동시에 그 체크를 통과할 수 있는 TOCTOU(Time-Of-Check-Time-Of-Use) 문제가 있습니다. 두 스레드가 거의 동시에 "아직 발급 안 됐다"를 확인하고 둘 다 저장을 시도하면 중복이 뚫립니다. `(user_id, coupon_event_id)` 복합 유니크 제약은 애플리케이션 로직이 뚫리더라도 DB가 두 번째 INSERT를 예외로 거부하게 만드는 최후 방어선이라, 성능 최적화(빠른 실패)와 정합성 보장(최종 방어)을 계층별로 나눠 가진 셈입니다.

**Q6. 스키마를 SQL DDL로 관리하지 않고 JPA 엔티티에서 파생시키는데, 운영에서 위험하지 않나요?**

맞는 지적이고, 그래서 dev 환경은 `ddl-auto=update`로 편의를 취했지만 prod 환경은 `ddl-auto=validate`로 다르게 설정했습니다. validate는 엔티티와 실제 DB 스키마가 다르면 애플리케이션이 아예 기동을 거부하게 만들어서, 스키마 불일치를 배포 시점에 막는 최소한의 안전장치입니다. 다만 실제 마이그레이션 이력 관리(Flyway/Liquibase 같은 도구)는 아직 도입하지 않았고, 이건 명확히 남은 과제로 인지하고 있습니다.

**Q7. 주문 상태와 배송 상태를 OrderStatus 하나로 합친 게 SRP(단일 책임 원칙) 위반 아닌가요?**

두 상태를 분리했을 때 실제로는 항상 함께 전이됐고, 조합 검증 로직(이 주문 상태에서 이 배송 상태가 가능한가)만 늘어나는 걸 보고 하나로 합쳤습니다. SRP는 "클래스가 하나의 이유로만 변경돼야 한다"는 원칙인데, 이 경우엔 오히려 상태를 둘로 쪼갠 게 "두 enum이 항상 같이 변경돼야 하는" 인위적인 결합을 만들고 있었습니다. 상태 전이 자체는 `Order` 엔티티 내부 메서드로 캡슐화해서, 책임은 여전히 한 곳(Order)에만 있습니다.

## 3. 도메인 간 연관관계 해결

**Q8. 왜 굳이 Port 인터페이스를 도입했나요? Service를 직접 호출하는 것과 뭐가 다른가요?**

인터페이스 자체가 주는 이득보다 "이 경계를 넘는 호출은 여기서만 일어난다"는 걸 강제하는 게 목적이었습니다. `OrderService`가 `ProductPort.decreaseStockWithLock()`만 알고 `ProductOptionRepository`를 직접 모르면, 상품 도메인이 재고 차감 방식을 비관적 락에서 다른 방식으로 바꿔도 주문 도메인 코드는 건드릴 필요가 없습니다. Service를 직접 호출해도 비슷한 효과를 볼 수는 있지만, 인터페이스로 명시하면 "이 메서드들이 도메인 간 계약이다"라는 게 코드로 드러나는 차이가 있습니다.

**Q9. ApplicationService와 Service를 나눈 기준이 뭔가요?**

다른 도메인의 엔티티나 Port를 참조하는지가 기준입니다. `ProductApplicationService`는 `UserPort`로 스토어 소유권을 검증한 뒤 `ProductService`에 위임하고, `ProductService`는 `Product`, `ProductOption`만 알고 다른 도메인은 전혀 모릅니다. 순수 도메인 서비스에 다른 도메인 엔티티가 파라미터로 들어오는 순간 "이 로직이 잘못된 계층에 있다"는 신호로 삼기로 팀 컨벤션(제 안의 규칙)을 정했습니다.

**Q10. Order-Payment를 이벤트로 분리했는데, 동기 이벤트와 AFTER_COMMIT 이벤트를 왜 나눠 썼나요?**

원자성이 필요한지 여부로 나눴습니다. 결제 승인/실패에 따라 주문 상태를 바꾸는 건 결제 트랜잭션과 원자적으로 같이 처리돼야 해서 동기 `@EventListener`를 썼습니다. 반면 Redis에 주문 타임아웃 타이머를 등록하는 건 만약 주문 저장 트랜잭션이 롤백되면 절대 실행되면 안 되는 외부 부수효과라, 커밋이 확정된 이후에만 실행되는 `@TransactionalEventListener(AFTER_COMMIT)`으로 뒀습니다. 커밋 전에 Redis에 등록해버리면 롤백된 주문의 타이머가 남아 있는 유령 데이터가 생깁니다.

**Q11. 동기 이벤트 리스너가 예외를 던지면 어떻게 되나요? 이벤트 기반이라 오히려 실패가 묻히지 않나요?**

동기 `@EventListener`는 같은 스레드·같은 트랜잭션에서 실행되기 때문에 리스너가 예외를 던지면 발행자 쪽 트랜잭션도 함께 롤백됩니다. 즉 완전한 비동기가 아니라 "메서드 호출을 이벤트로 형식만 바꾼" 것에 가깝고, 그래서 원자성이 필요한 Order-Payment 상태 변경에 이 방식을 쓴 겁니다. 진짜 비동기 이벤트(`@Async`)는 쿠폰 발급 저장처럼 실패해도 즉시 롤백이 필요 없는 경우에만 썼습니다.

**Q12. OrderPort/PaymentPort가 고아가 됐다고 문서에 적혀 있던데, 왜 아직 안 지웠나요?**

일부러 남겨둔 건 아니고, 우선순위상 뒤로 밀린 정리 작업입니다. 이벤트 기반으로 리팩터링하면서 자연스럽게 구현체와 호출부가 사라졌는데, 삭제 자체는 몇 분이면 되는 일이라 다음 정리 PR에서 처리할 계획입니다. 오히려 이 시점에 강조하고 싶은 건, 이런 리팩터링 잔재를 "코드에 있으니까 잘 만든 것"이라고 방치하지 않고 스스로 인지해서 문서에 남겼다는 점입니다.

## 4. 동시성 제어 — 재고

**Q13. 재고 차감에 왜 비관적 락을 선택했나요? 원자적 UPDATE가 더 빠르지 않나요?**

원자적 UPDATE(`UPDATE ... WHERE stock_quantity >= 1`)가 순수 차감 속도는 가장 빠른 게 맞습니다. 하지만 주문 생성은 재고 차감만 하는 게 아니라 상품가·스토어 정보가 같은 트랜잭션 안에서 함께 필요합니다. UPDATE만으로는 이 정보를 못 가져오고, 별도 SELECT를 추가하면 그 사이에 동시성 문제가 다시 생깁니다. `SELECT ... FOR UPDATE`에 fetch join을 걸면 락 획득과 부가 데이터 조회를 한 쿼리로 끝낼 수 있어서, 이 케이스에는 비관적 락이 더 적합하다고 판단했습니다.

**Q14. Deadlock을 TreeMap 정렬로 막았다고 했는데, 원리를 설명해주세요.**

여러 옵션을 한 주문에서 동시에 잠글 때, 스레드 A가 옵션1→옵션2 순서로, 스레드 B가 옵션2→옵션1 순서로 락을 걸면 서로 상대가 가진 락을 기다리며 교착 상태에 빠집니다. 모든 트랜잭션이 항상 같은 순서로 락을 요청하면 이 순환 대기 자체가 발생할 수 없습니다. `TreeMap`은 키(optionId) 기준으로 항상 오름차순 순회가 보장되니, 주문 항목을 이 자료구조에 담아 순서대로 락을 걸도록 강제했습니다. 부가적으로 같은 옵션이 중복 주문된 경우 수량을 합산하는 역할도 같은 자료구조로 처리했습니다.

**Q15. 동시 1000명이 같은 옵션을 주문하면 비관적 락은 어떻게 되나요?**

DB row lock 대기열에 순서대로 쌓여서 순차 처리됩니다. 트랜잭션 하나가 약 10ms라면 1000번째 사용자는 대략 10초를 기다려야 하는데, 이건 사용자가 이탈할 만한 수준입니다. 재고 동시성 문서에도 이 한계를 명시해뒀고, 대응 계획으로 Redis DECR 원자적 연산으로 전환할 수 있는 구조를 미리 준비해뒀습니다. 다만 지금 규모에서 타임세일이 아닌 이상 같은 옵션에 1000명이 몰리는 상황이 흔치 않다고 판단해 지금은 비관적 락을 유지하고 있습니다.

**Q16. 락으로 잠근 상태에서 fetch join으로 Product·Store까지 같이 가져오면 락을 더 오래 잡는 거 아닌가요?**

맞습니다, 트레이드오프입니다. fetch join 없이 락만 걸고 나중에 Product/Store를 조회하면 락 점유 시간은 짧아지지만 N+1 쿼리가 추가로 발생합니다. 반대로 fetch join을 쓰면 쿼리 수는 줄지만 그 추가 조회 시간만큼 락을 더 오래 잡습니다. 재고 차감처럼 락 경합이 상대적으로 좁은 범위(단일 row)에 집중되는 경우엔 쿼리 왕복 횟수를 줄이는 게 전체 처리량에 더 유리하다고 판단해 fetch join을 선택했는데, 이건 실측으로 완전히 정량 비교한 부분은 아니라서 트래픽이 늘면 다시 검증이 필요한 지점이라고 생각합니다.

**Q17. 재고 복구(increaseStock)에도 락이 필요한 이유를 설명해주세요.**

주문 취소로 재고를 복구하는 시점에도 다른 사용자가 같은 옵션을 동시에 주문 중일 수 있습니다. 복구 로직이 락 없이 `findById()`로 읽고 증가시키면, 그 사이 다른 트랜잭션의 `decreaseStockWithLock()` 결과가 유실되는 Lost Update가 똑같이 발생합니다. 코드 리뷰에서 이 부분을 놓쳤다는 걸 지적받고 나서, 재고를 변경하는 모든 경로가 동일한 락 전략을 써야 정합성이 보장된다는 걸 배워 `increaseStock()`도 `findByIdWithLock()`으로 통일했습니다.

## 5. 동시성 제어 — 선착순 쿠폰

**Q18. 재고는 비관적 락, 쿠폰은 Redis DECR로 결론이 다른데 왜 그런가요?**

두 문제의 성격이 다릅니다. 재고 차감은 락을 잡은 김에 상품가·스토어 같은 부가 데이터를 같은 트랜잭션에서 읽어야 해서 비관적 락이 자연스러웠습니다. 반면 선착순 쿠폰은 "카운터 차감 + 중복 검증"이라는 단순한 조합이고 부가 데이터 조회가 필요 없어서, 락 없이 Redis의 단일 스레드 원자성만으로 처리할 수 있는 여지가 있었습니다. 실제로 측정해보니 DB 비관적 락(630 RPS)보다 Redis DECR+Lua(640+ RPS, 다중 인스턴스 기준)가 더 나았고, 무엇보다 5xx가 0%라는 게 결정적이었습니다.

**Q19. Redis 분산 락(SETNX)이 왜 비관적 락보다 느렸나요?**

두 가지 이유입니다. 첫째, SETNX 폴링 방식은 50ms 간격으로 락을 재시도하는데 이건 순서 보장(fairness)이 없어서 비효율적입니다. 둘째, DB 비관적 락은 커널 레벨 FIFO 대기열을 쓰지만 분산 락은 waitTime(5초)을 넘기면 그냥 예외를 던지는 구조라, 대기하던 요청이 성공하지 못하고 500 에러로 이어졌습니다. 그 결과 RPS는 630에서 190으로 떨어지고 5xx가 24.7%까지 치솟았습니다. "분산 락이 더 견고할 것"이라는 처음 가설이 측정으로 완전히 반박된 경우입니다.

**Q20. Redis DECR + Lua 방식은 왜 안전한가요? Redis가 죽으면 어떻게 되나요?**

Lua 스크립트는 Redis 내부에서 원자적으로 실행되기 때문에, "중복 체크 → 카운터 차감 → 발급 세트 추가"가 중간에 다른 요청이 끼어들 여지 없이 한 번에 처리됩니다. 다만 Redis가 단일 노드라 장애가 나면 발급 자체가 막힙니다. 지금은 단일 Redis 노드로 이 리스크를 감수하고 있고, Redis Cluster나 Sentinel 구성은 다음 단계로 남겨뒀습니다 — 지금 규모에서 그 복잡도까지 감당할 이유가 아직은 없다고 판단했습니다.

**Q21. 비동기 저장을 도입했는데 RPS가 안 올랐다면서 왜 채택했나요?**

측정 결과 RPS는 640에서 632로 거의 그대로였습니다. 처음엔 "DB INSERT가 병목일 것"이라는 가설이었는데, 측정해보니 실제 병목은 다른 곳(Locust wait_time, 단일 머신 CPU)에 있었다는 걸 알게 됐습니다. 그럼에도 채택한 이유는 처리량 향상이 아니라 다른 이점 때문입니다 — 트래픽 피크를 흡수하고, DB 저장 실패가 즉시 응답 실패로 이어지지 않게 장애를 격리하는 효과는 이 측정 환경(1~2분 단발 부하)에서는 드러나지 않지만 실제 운영에서는 의미가 있다고 판단했습니다. 다만 이건 측정으로 입증된 게 아니라 설계 판단이라는 걸 면접에서도 그대로 말씀드릴 수 있습니다.

**Q22. 측정에서 Redis DECR이 가장 좋았다면서, 왜 지금 CouponService는 아직 비관적 락인가요?**

측정은 별도 성능 측정 사이클에서 진행했고, 그 결과를 근거로 `CouponIssuedEvent`/`CouponIssuedEventListener` 골격까지는 만들어뒀습니다. 하지만 아직 `CouponService.issueCoupon()`에 실제로 연결하지는 않았습니다. 측정 환경과 실제 트랜잭션 경계, 장애 시나리오(Redis 다운, 이벤트 유실)까지 충분히 검증하지 못한 상태에서 성능이 좋다는 이유만으로 운영 경로를 바꾸는 건 성급하다고 판단했습니다. 좋은 결과를 냈다고 검증 안 된 코드를 바로 메인에 흘려보내지 않는다는 원칙을 지킨 겁니다.

## 6. 결제

**Q23. 금액 위변조 검증이 서명 검증이 아니라 단순 비교라고 하셨는데, 이게 왜 안전한가요? 한계는요?**

핵심은 "서버가 신뢰하는 값의 출처"입니다. 결제 승인 시점에 클라이언트나 PG사가 보내는 금액을 그대로 믿지 않고, 주문 생성 시점에 서버가 이미 DB에 저장해둔 금액과 비교합니다. 클라이언트가 요청 값을 조작해도 서버가 참조하는 기준값 자체는 클라이언트 입력과 무관하니 최종 승인 금액은 조작될 수 없습니다. 다만 이건 금액 위변조에 대한 방어이지, PG사가 보내는 콜백/웹훅 자체가 진짜 토스에서 왔는지를 검증하는 암호화 서명 검증은 아닙니다. 이 부분은 명확히 구분해서 알고 있고, 다음 단계로 웹훅 서명 검증을 추가하는 게 맞다고 생각합니다.

**Q24. 멱등성 처리가 없다는데, 토스 콜백이 네트워크 재시도로 중복 오면 어떻게 되나요?**

현재 이 브랜치의 구조에서는 `confirmPayment()`가 중복 호출되면 이미 `DONE` 상태인 결제에 다시 승인 처리를 시도할 위험이 있습니다. 다만 별도 성능 측정 브랜치에서 이 문제를 실제로 재현하고 고친 적이 있습니다 — `PaymentIdempotencyTest.concurrentIdempotency`로 동시 중복 승인 요청을 재현했고, `findByOrderPgOrderIdWithLock()`(비관적 락)으로 조회 방식을 바꿔서 두 번째 요청이 첫 번째 요청의 커밋이 끝난 뒤 `DONE` 상태를 보고 `PAYMENT_ALREADY_PROCESSED`로 자연스럽게 거절되도록 만들었습니다. 검증까지 끝난 해결책이지만 아직 이 브랜치에는 반영하지 않았다는 게 정확한 상태입니다 — 성능 측정 사이클에서 나온 결과를 검증 없이 바로 운영 경로에 흘려보내지 않는다는 원칙(3.2절 쿠폰 사례와 동일)을 여기서도 지켰습니다.

**Q25. 결제 실패/취소를 이벤트로 처리하는데, 이벤트가 유실되면 주문 상태는 어떻게 되나요?**

현재 Spring의 인메모리 `ApplicationEventPublisher`를 쓰고 있어서, 리스너가 처리하기 전에 서버가 죽으면 이벤트 자체가 유실될 수 있습니다. 이건 주문 타임아웃 처리에서 이미 한 번 겪은 문제라서, 그때 만든 것과 같은 패턴 — 1시간 주기 DB 기반 보정 스케줄러 — 을 결제-주문 상태 불일치에도 확장 적용할 수 있다고 생각합니다. 지금은 아직 결제 이벤트 유실에 대한 별도 보정 로직까지는 없고, 이건 인지하고 있는 개선 지점입니다.

**Q26. 부분 취소에서 배송 상태별로 취소 가능 범위를 다르게 한 이유는?**

배송이 이미 시작된 상품을 취소하면 물류 프로세스와 충돌이 생기기 때문에, 배송 중(SHIPPING)에는 취소를 아예 막았습니다. 반대로 배송 완료 후에는 소비자 보호 관점에서 일정 기간(7일) 취소 창구를 열어뒀습니다. 이 규칙을 `PaymentValidator`에서 한 곳에 모아 관리해서, 취소 가능 여부 판단이 여러 곳에 흩어지지 않도록 했습니다.

## 7. 대용량 트래픽 대응

**Q27. 커서 페이징이 20배나 빠른데 왜 처음부터 안 쓰고 offset을 썼나요? 커서 페이징의 단점은요?**

처음엔 데이터가 적어서 offset의 성능 문제가 드러나지 않았고, 구현도 더 단순해서 offset으로 시작했습니다. 데이터가 100만 건을 넘어가면서 뒤쪽 페이지 조회가 2초 가까이 걸리는 걸 보고서야 구조적 한계를 체감했습니다. 커서 페이징의 단점은 "몇 번째 페이지로 바로 이동"같은 임의 페이지 점프가 불가능하다는 겁니다. 무한 스크롤 UX에는 이 단점이 문제가 안 되지만, 페이지 번호 기반 UI가 필요하면 커서 방식이 안 맞을 수 있다는 것도 알고 있습니다.

**Q28. Redis ZSET 타임아웃 처리에서 왜 Lua 스크립트가 필요했나요?**

원자성 때문입니다. `ZRANGEBYSCORE`로 만료된 주문을 조회하고 `ZREM`으로 제거하는 걸 별도 명령으로 하면, 그 사이에 다른 서버 인스턴스가 같은 데이터를 읽어서 중복 처리를 시도할 수 있습니다. Lua 스크립트로 조회와 제거를 하나의 원자적 명령으로 묶으면 여러 인스턴스가 동시에 폴링해도 한 주문이 정확히 한 번만 처리됩니다.

**Q29. 단일 서버 상한이 약 1,003 RPS라고 했는데, 병목이 뭐였나요?**

정확히 특정 자원 하나로 못 박아 말씀드리긴 어렵고, HikariCP 커넥션 풀, CPU, Locust 자체의 부하 생성 한계가 섞여 있었습니다. 실제로 부하 테스트 중 Locust 프로세스 자체가 CPU 90% 이상을 찍는 경고가 나온 적이 있어서, 측정된 상한이 "서비스의 진짜 한계"인지 "부하 생성 클라이언트의 한계"인지 완전히 분리하지 못한 부분이 있습니다. 이 한계를 포트폴리오에도 그대로 밝혔고, 진짜 한계를 보려면 부하 생성기를 별도 머신으로 분리해야 한다는 걸 다음 단계로 인지하고 있습니다.

**Q30. 부하테스트를 로컬 단일 머신에서 했다고 했는데, 이게 왜 신뢰도에 한계가 있나요?**

앱, DB, Redis, Locust가 전부 한 머신에서 CPU와 메모리를 나눠 쓰기 때문에, 측정된 수치에 애플리케이션의 진짜 한계와 리소스 경합으로 인한 왜곡이 섞여 있습니다. 그래서 "RPS 1,003"이라는 숫자 자체보다, 그 숫자를 얻어낸 방법론 — 가설을 세우고, 측정하고, 이상하면 환경부터 의심하고, 재현해서 원인을 좁혀가는 과정 — 에 더 의미를 두고 있다고 설명합니다. 실제 서비스 규모의 신뢰도 있는 숫자를 얻으려면 클라우드 환경에서 부하 생성기와 대상 서버를 분리한 측정이 필요하다는 것도 포트폴리오에 명시했습니다.

## 8. 운영/배포

**Q31. 완전한 무중단 배포를 왜 못했나요? 어떻게 하면 될까요?**

지금은 배포 시 기존 컨테이너를 내리고 새 컨테이너를 올리는 방식이라 새 컨테이너가 healthy가 될 때까지 수 초의 공백이 생깁니다. 진짜 무중단을 하려면 nginx 같은 리버스 프록시 뒤에 앱 인스턴스를 2개 이상 두고, 트래픽을 한쪽으로 흘리면서 다른 쪽을 순차적으로 교체하는 rolling 방식이 필요합니다. 이미 선착순 쿠폰 다중 인스턴스 실험을 하면서 세션을 Redis로 외부화해뒀기 때문에, 인스턴스를 늘려도 로그인이 깨지지 않는 전제 조건은 마련돼 있어서 다음 단계로 nginx + 인스턴스 2대 구성을 계획하고 있습니다.

**Q32. t3.micro처럼 작은 인스턴스를 왜 선택했나요? 트래픽이 늘면 어떻게 확장할 건가요?**

포트폴리오 프로젝트 규모에서 비용 대비 충분한 사양이라 t3.micro를 선택했습니다. 메모리가 넉넉하지 않아서, JVM이 컨테이너 메모리 한도를 인식 못 하고 호스트 전체 메모리 기준으로 힙을 잡아 OOMKill 당하는 문제를 미리 막기 위해 `-XX:MaxRAMPercentage=75.0`으로 컨테이너 메모리 한도 대비 비율로 힙을 산정하도록 설정했습니다. 트래픽이 늘면 먼저 인스턴스 사양을 올리는 수직 확장을 검토하고, 그다음은 로드밸런서 뒤에 인스턴스를 늘리는 수평 확장으로 가는 게 자연스러운 순서라고 생각합니다. 세션 외부화는 이미 돼 있어서 수평 확장의 걸림돌은 상당 부분 없앤 상태입니다.

**Q33. CloudWatch 알람은 어떤 기준(임계치)으로 설정했나요?**

EC2 인스턴스의 CPU 사용률과 메모리 사용률에 알람을 걸어뒀습니다. t3.micro처럼 리소스가 제한된 인스턴스는 트래픽이 조금만 몰려도 임계치에 먼저 닿기 때문에, 장애가 사용자에게 보이기 전에 신호를 받을 수 있는 최소한의 관측 장치로 마련했습니다. 정확한 임계값(%)은 이 자리에서 바로 확인해서 답변드리겠습니다 — (※ 본인 실제 설정값을 면접 전에 다시 한번 확인해두시길 권합니다.)

## 9. 이 포트폴리오의 약점을 정면으로 찌르는 질문

**Q34. 신입인데 왜 이렇게 인프라·성능까지 손댔나요? 실무에서는 이런 권한이 잘 없을 텐데, 이 경험이 실제로 의미가 있나요?**

맞습니다, 실무 신입은 보통 인프라 설계 권한을 갖지 않습니다. 그래서 이 프로젝트로 "저에게 인프라 설계 경험이 있다"고 주장하려는 게 아니라, "문제가 생겼을 때 어느 계층을 의심해야 하는지 감이 있다"는 걸 보여주려는 목적입니다. 예를 들어 API 응답이 느려졌을 때 이게 쿼리 문제인지, 락 경합인지, 커넥션 풀 문제인지, 측정 환경 자체의 노이즈인지를 구분해본 경험이 있으면, 실무에서 시니어와 대화할 때 "이 부분을 확인해봐야 할 것 같다"는 가설을 스스로 세울 수 있다고 생각합니다.

**Q35. 모든 걸 혼자 했다면서 코드 리뷰는 실제로 어떻게 받았나요?**

멘토링 형태로 정기적인 코드 리뷰를 받았습니다. 포트폴리오에도 여러 번 언급했듯이, 스토어 트랜잭션 원자성 문제, 재고 복구 로직의 락 누락, N+1 문제 같은 걸 리뷰에서 지적받고 수정한 이력이 실제 커밋/문서에 남아 있습니다. 혼자 설계하고 혼자 구현했지만, 검증은 외부 시선을 거쳤다는 게 정확한 표현이라고 생각합니다.

**Q36. 측정한 숫자들이 실서비스 규모(수만~수십만 동시 사용자)에 비하면 작은데, "대용량 트래픽"이라고 부를 수 있나요?**

정직히 말씀드리면, 이 프로젝트의 측정치(RPS 수백~1,000대)는 실제 대형 커머스의 피크 트래픽 규모에는 못 미칩니다. 그래서 포트폴리오에서도 "대용량을 이미 처리해봤다"보다는 "대용량 환경에서 나타나는 문제 유형(락 경합, 커넥션 고갈, 인덱스 비효율)을 축소된 환경에서도 동일한 방법론(가설→측정→검증)으로 재현하고 풀어봤다"는 쪽으로 프레이밍하고 있습니다. 문제의 종류는 같고 규모만 다르기 때문에, 방법론 자체는 규모가 커져도 유효하다고 생각합니다.

**Q37. 쿠폰 동시성 측정 결과가 좋았는데 왜 아직도 실제 코드에 반영 안 했나요? 그냥 게을렀던 거 아닌가요?**

성능이 좋다고 검증되지 않은 채로 결제·재고와 맞물린 운영 경로를 바꾸는 게 더 위험하다고 판단했습니다. Redis DECR 방식은 카운터의 source of truth가 DB가 아니라 Redis로 바뀌는 구조적 변화라서, DB와 Redis 간 정합성이 깨지는 장애 시나리오(Redis 재시작, 네트워크 분단)까지 검증한 뒤에 반영하는 게 맞다고 생각했습니다. 다만 이 판단이 "안전하니까 미룬다"는 핑계가 되지 않도록, 다음 스프린트에서 우선순위 1번으로 처리할 계획이라는 것도 답할 수 있어야 합니다.

**Q38. Redis에 이렇게 많은 로직(분산 락, DECR, ZSET, 세션)이 몰려 있는데, Redis가 죽으면 전체 서비스가 죽는 거 아닌가요?**

현재 구조에서는 맞습니다, Redis가 단일 장애점(SPOF)입니다. 주문 타임아웃은 Redis가 죽어도 1시간 주기 DB 보정 스케줄러가 있어서 완전히 유실되진 않지만, 세션 외부화나 선착순 쿠폰 카운터는 Redis 장애 시 직접적인 영향을 받습니다. 이건 지금 규모에서 감수하고 있는 트레이드오프이고, 실제 운영 단계로 가면 Redis Sentinel이나 Cluster로 고가용성을 확보하는 게 우선순위 높은 다음 과제라고 생각합니다.

**Q39. 이 프로젝트에서 실패하거나 폐기한 시도가 있나요?**

네, 두 가지가 대표적입니다. 첫째, Redis 분산 락(SETNX 폴링)을 선착순 쿠폰에 적용했다가 5xx가 24.7%까지 치솟는 걸 보고 폐기했습니다 — 인프라 코드는 남겨뒀지만 이 도메인에는 적용하지 않기로 결론냈습니다. 둘째, atomic UPDATE 이후 P99가 늘어난 걸 보고 "OrderDetail 생성 시그니처를 바꿔야겠다"는 가설을 세웠는데, 재측정으로 원인이 코드가 아니라 측정 환경 노이즈였다는 게 밝혀지면서 그 코드 변경 자체를 하지 않기로 했습니다. 둘 다 "시도했다가 데이터로 아니라고 판명 나서 되돌린" 경험이라, 실패를 인정하고 방향을 바꾸는 게 어렵지 않았습니다.
