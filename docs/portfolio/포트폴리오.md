# StyleHub

## 프로젝트 개요

무신사, 29CM과 같은 패션 도메인의 이커머스 서비스를 개발한 프로젝트입니다. 서비스 전반적인 개발을 진행하기보다 대용량 트래픽 처리, 재고 동시성 이슈, 주문 타임아웃 관리 같은 기술적으로 어려운 문제들을 해결하기 위한 백엔드 개발을 중점적으로 진행했습니다.

객체지향의 특징을 극대화시킨 Spring을 사용하면서 확장 가능한 구조를 계속 고민했습니다. 도메인 간 의존은 Repository를 직접 참조하지 않고 Service 레이어를 통해서만 소통하도록 설계했고, 등록과 조회의 책임이 다른 서비스는 CQRS 패턴으로 분리하여 각각 독립적으로 최적화할 수 있게 했습니다. 이런 구조 덕분에 동시성 테스트를 작성할 때도 각 서비스를 독립적으로 검증할 수 있었습니다.

300만건의 테스트 데이터를 직접 생성하여 성능을 실측했고, 10명이 동시에 주문하는 동시성 테스트로 재고 정합성을 검증했습니다. 숫자로 증명할 수 없는 개선은 개선이 아니라는 생각으로, 모든 의사결정에 실측 데이터를 근거로 삼으려 했습니다.

Java 17 / Spring Boot 4 / Spring Data JPA / QueryDSL / MySQL / Redis / Gradle

## 100만건 상품 목록 조회 — Offset에서 커서 페이징으로

상품 데이터가 100만건으로 늘어나면서 목록의 뒤쪽 페이지를 조회할 때 응답이 2초 가까이 걸리기 시작했습니다. Offset 페이징의 `LIMIT 20 OFFSET 999980`은 DB가 앞에서부터 999,980건을 하나씩 세면서 건너뛰어야 하는 구조적 한계가 있었습니다. 무신사처럼 무한 스크롤 기반의 패션 이커머스에서 뒤쪽 페이지가 2초씩 걸리면 사용자 이탈로 이어집니다.

커서 기반 페이징으로 전환하여 `WHERE product_id < cursor LIMIT 20`으로 PK 인덱스를 타고 바로 점프하도록 변경했습니다. 다음 페이지 존재 여부는 요청한 size보다 1건 더 조회하는 방식으로 판별하여 COUNT 쿼리 비용도 제거했습니다.

구현 과정에서 JPQL로 동적 필터링(스토어별, 카테고리별)을 작성했을 때 Hibernate가 Long 타입의 null 파라미터를 IS NULL로 정확히 평가하지 못하는 문제를 겪었습니다. QueryDSL의 BooleanBuilder로 전환하여 null인 조건은 쿼리에 아예 포함하지 않도록 해결했고, 이후 추가되는 필터 조건도 한 줄만 추가하면 되어 확장성도 좋아졌습니다.

100만건 실측에서 Offset과 커서의 차이가 명확히 드러났습니다.

**100만건 실측**

| 조회 위치 | Offset | 커서 | 개선 |
|----------|--------|------|------|
| 50만번째 | 1,254ms | 156ms | 8배 |
| 100만번째 | 1,945ms | 94ms | **20배** |

데이터가 늘어날수록 Offset은 앞쪽 행을 건너뛰는 비용이 선형으로 늘어나 계속 느려지지만, 커서는 인덱스로 시작점을 바로 찾기 때문에 위치와 무관하게 일정합니다.

> 참고: 이전 버전 문서에 있던 "300만건, 6,896ms → 14ms, 492배" 수치는 뒷받침하는 원본 로그를 찾을 수 없어 제외했습니다. 100만건 실측(20배)만 근거로 사용합니다.

## 동시 주문 재고 정합성 — deadlock 방지와 락 최적화

동시성 테스트를 작성하여 재고 1개인 상품에 10명이 동시에 주문하는 상황을 재현했을 때, 2명 이상이 주문에 성공하는 Lost Update 문제를 발견했습니다. 재고 차감은 충돌이 빈번하므로 비관적 락(SELECT FOR UPDATE)을 적용하여 해결했습니다.

비관적 락 적용 후 고민한 부분은 **여러 옵션을 동시에 잠글 때 발생하는 deadlock**이었습니다. 스레드 A가 옵션 1을 잠그고 옵션 2를 대기하는데, 스레드 B가 옵션 2를 잠그고 옵션 1을 대기하면 서로 무한 대기에 빠집니다. TreeMap을 활용하여 optionId를 오름차순으로 정렬한 뒤 순서대로 락을 획득하도록 하여, 모든 트랜잭션이 같은 순서로 잠금을 걸어 deadlock을 원천 차단했습니다. TreeMap은 같은 옵션이 중복으로 들어온 경우 수량을 합산하는 역할도 동시에 수행하여 불필요한 락 횟수를 줄입니다.

재고 차감 로직은 ProductOption 엔티티의 `decreaseStock()` 메서드에 캡슐화하여, 서비스에서 검증을 반복하지 않아도 엔티티가 스스로 규칙을 보장합니다. 비관적 락 조회 시 fetch join으로 Product와 Store까지 한 쿼리에 가져와 N+1도 방지했습니다.

추후 트래픽이 늘어나 DB 락 대기가 병목이 되면, Redis DECR 원자적 연산으로 전환할 수 있도록 `@DistributedLock` AOP를 미리 준비해두었습니다.

테스트 결과 재고 10개에 10명 동시 주문 시 정확히 10명 성공, 재고 0. 재고 5개에 10명 동시 주문 시 5명 성공, 5명 INSUFFICIENT_STOCK, 재고 정확히 0으로 정합성 100%를 확인했습니다.

## 트랜잭션 범위 설계 — 세 번의 고민

회원가입에서 BCrypt 해싱(~100ms)이 `@Transactional` 안에서 실행되어 DB와 무관한 CPU 작업 동안에도 커넥션을 점유하는 문제를 발견했습니다. 동시 100명이 회원가입하면 커넥션 풀이 고갈될 수 있는 상황이었습니다. TransactionTemplate으로 해싱을 트랜잭션 밖에서 실행하도록 분리하여 커넥션 점유 시간을 110ms → 10ms로 11배 개선했습니다.

주문 생성에서는 트랜잭션 밖 작업이 없어 `@Transactional`로 전환하여 코드를 깔끔하게 유지했습니다. 그런데 토스페이먼츠 결제를 설계하면서, `@Transactional`이 메서드 전체에 걸리면 외부 결제 API 호출(수초) 동안에도 커넥션이 잠기는 문제를 발견했습니다. 같은 클래스 내에서 메서드를 분리하려 했으나 Spring 프록시가 내부 호출에서는 적용되지 않아 트랜잭션이 걸리지 않는 문제가 있었습니다.

OrderService(흐름 관리)와 OrderTransactionService(트랜잭션)로 클래스를 분리하여 해결했습니다.
DB 작업만 @Transactional로 묶고, 결제 API와 Redis 타이머 등록은 트랜잭션 밖에서 처리합니다.
외부 API가 수초 걸려도 커넥션 점유가 0이 되는 구조이고, 각 트랜잭션을 독립적으로 테스트할 수 있게 되었습니다.

## 미결제 주문 타임아웃 — Scheduler에서 Redis ZSET으로

주문 생성 시 재고를 미리 차감하는 구조에서, 사용자가 결제를 안 하면 PENDING 상태로 영원히 남아 재고가 복구되지 않는 문제가 있었습니다. 처음에는 Spring Scheduler로 5분마다 DB를 스캔하여 만료 주문을 찾아 취소했으나, 대용량 환경에서 주기적 DB 전체 스캔은 부하가 크고 최대 5분의 오차도 문제였습니다.

Redis ZSET Delay Queue로 전환했습니다. 주문 생성 시 score를 만료 시각(현재 + 30분)으로 등록하고, 1초마다 `ZRANGEBYSCORE`로 만료된 주문만 정확히 찾아 취소합니다. Redis는 메모리 기반이라 100만건이어도 ~1ms로 조회되고 DB를 전혀 건드리지 않습니다. 결제 완료 시 `ZREM`으로 타이머를 즉시 제거하고, ZREM이 원자적 연산이라 멀티 서버에서도 중복 처리가 방지됩니다.

DB 전체 스캔이 완전히 제거되었고, 만료 오차가 최대 5분에서 최대 1초로 줄었습니다.

## DDD 도메인 경계 — Service 레이어를 통한 소통

처음 OrderService를 구현했을 때 UserRepository, AddressRepository, ProductOptionRepository를 모두 직접 참조하여 의존성이 6개였고, 3개 도메인이 뒤섞여 있었습니다.

코드 리뷰를 통해 DDD 위반을 인지하고, 각 도메인의 검증 로직을 해당 Service로 분리했습니다. UserService의 `findAddressByOwner()`는 배송지 조회 + 본인 검증을, ProductService의 `decreaseStockWithLock()`은 비관적 락 재고 차감을 담당합니다. 이 메서드들에 `@Transactional`을 붙이지 않아서 호출자의 트랜잭션에 자연스럽게 참여합니다. 도메인 경계를 지키면서도 하나의 트랜잭션으로 묶이는 구조입니다.

## AOP — 서비스 코드를 오염시키지 않는 횡단 관심사

주문/결제처럼 민감한 도메인은 모든 요청과 응답을 기록해야 장애 추적이 가능합니다. `ApiLoggingAspect`로 order, payment 패키지의 모든 메서드에 요청/응답/실행시간을 자동 기록하고, `@ExecutionTimeCheck`로 임계값을 초과하는 슬로우 메서드를 자동 감지합니다.

`@DistributedLock` 커스텀 어노테이션은 Redis SETNX 기반 분산 락을 AOP로 투명하게 처리합니다. SpEL로 동적 락 키를 지원하여 `@DistributedLock(key = "'stock:' + #optionId")`처럼 파라미터 기반 락 키를 설정할 수 있고, 추후 쿠폰 선착순 발급 등에 어노테이션 하나만 붙이면 분산 락이 적용됩니다.

## 협업 방식 — 이슈, PR, 코드 컨벤션

혼자 진행하는 프로젝트였지만, 실무와 동일한 협업 프로세스를 적용했습니다.
기능 단위로 GitHub Issue를 생성하고, Issue 번호 기반으로 브랜치를 만들어 작업한 뒤 PR을 올리는 흐름을 유지했습니다. `[#11] feat: 입점 신청 및 승인 구현`처럼 커밋 메시지에 이슈 번호를 포함하여 변경 이력을 추적할 수 있게 했습니다.

PR에는 요약, 주요 설계 결정, 체크리스트, 리뷰어에게 공유할 사항을 템플릿으로 작성했습니다. 예를 들어 입점 신청 PR에서는 "User와 Store가 별도 트랜잭션으로 처리되는데, Store 실패 확률이 거의 없어 단순함을 우선했으며 필요 시 Facade로 전환 가능하다"는 트레이드오프를 명시했습니다. 멘토의 코드 리뷰에서 원자성 문제를 지적받았을 때 근거를 가지고 논의할 수 있었고, 최종적으로 Facade 패턴을 도입하여 해결했습니다.

코드 컨벤션은 프로젝트 초기에 정하고 일관되게 유지했습니다. 와일드카드 import를 금지하고 명시적 개별 import만 사용했으며, 모든 Java 파일에 `@author`, `@created`, `@modified` Javadoc 헤더를 작성하여 누가 언제 무엇을 변경했는지 추적할 수 있게 했습니다. DTO는 Java record로 통일하고, Response DTO는 `@Builder` + `from()` 정적 메서드 패턴으로 엔티티 → DTO 변환을 표준화했습니다. 엔티티는 `@SuperBuilder` + `@NoArgsConstructor(access = PROTECTED)` + `create()` 정적 팩토리 메서드 패턴을 적용하여 생성 의도를 명확히 했습니다.

리뷰에서 받은 피드백은 즉시 반영하되, 근거가 있으면 의견을 제시했습니다. AuthInterceptor에 `@LoginRequired` 어노테이션 방식을 제안받았을 때 "기존 `@RequiredRole`과 중복되고, 화이트리스트 방식이 보안상 더 안전하다"는 근거로 현재 구조를 유지했습니다. 스토어 상태 변경 API를 하나로 합치자는 제안에는 "상태가 4개로 고정되어 있고 각 상태별 로직이 달라 엔드포인트 분리가 적합하다"고 설명했습니다. 무조건 수용하는 것이 아니라 트레이드오프를 이해한 위에서 판단하려 했습니다.

구현한 API는 Notion 데이터베이스로 관리하여 각 API의 HTTP 메서드, URI, 상태, 도메인 태그, Request/Response Body를 정리했습니다.

```
   │  │  │  ├─ scheduler                                - OrderTimeoutScheduler (Redis ZSET 폴링), OrderTimeoutManager (타이머 등록/제거)
   │  │  │  └─ service                                  - OrderService (흐름), OrderTransactionService (@Transactional), OrderViewService (Query — CQRS)
   │  │  │
   │  │  ├─ payment                                   결제 도메인
   │  │  │  ├─ entity                                   - Payment (토스페이먼츠 연동 필드)
   │  │  │  └─ enums                                    - PaymentStatus (READY/DONE/CANCELED 등)
   │  │  │
   │  │  ├─ coupon                                    쿠폰 도메인
   │  │  │  ├─ entity                                   - CouponEvent, UserCoupon
   │  │  │  └─ enums                                    - CouponStatus, DiscountType
   │  │  │
   │  │  └─ point                                     포인트 도메인
   │  │     ├─ entity                                   - PointHistory
   │  │     ├─ enums                                    - PointType
   │  │     ├─ event                                    - LoginEventListener (이벤트 기반 도메인 분리)
   │  │     └─ service                                  - PointRewardService
   │  │
   │  └─ resources
   │     └─ application.properties                      - MySQL, Redis, Session, OAuth 설정
   │
   └─ test
      └─ java/ccommit/stylehub
         └─ order/service
            └─ OrderConcurrencyTest.java                - 재고 동시성 테스트 (10명 동시 주문)
```

도메인별로 패키지를 분리하고, 각 도메인 안에서 controller → dto → entity → enums → repository → service 구조를 일관되게 유지했습니다. 주문 도메인은 scheduler 패키지를 추가하여 Redis ZSET 타임아웃 관련 클래스를 분리했고, 상품/주문 도메인은 Command(ProductService, OrderTransactionService)와 Query(ProductViewService, OrderViewService)를 분리하여 CQRS를 적용했습니다.

## 앞으로 하고 싶은 것

토스페이먼츠 결제 연동은 트랜잭션 분리 구조와 위변조 검증 설계까지 완료했고 연동 예정입니다. 쿠폰 선착순 발급은 준비해둔 `@DistributedLock` AOP와 Redis DECR 원자적 연산을 활용할 계획입니다.

배포는 AWS EC2 + RDS + ElastiCache로 진행하고, GitHub Actions CI/CD와 Spring Actuator + Grafana 모니터링을 추가하여 운영 환경까지 경험하고 싶습니다.
