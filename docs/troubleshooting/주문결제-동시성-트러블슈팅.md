## 사건 1 — 측정 4 의 P99 미스터리: 130 → 210 ms

### 증상

측정 3 (비관적 락) → 측정 4 (atomic UPDATE) 로 *코드를 개선* 했는데:

| 지표 | 측정 3 (비관적 락) | 측정 4 (atomic UPDATE) | 변화 |
|---|---|---|---|
| RPS | 39.6 | 39.9 | +0.3 (거의 변화 없음) |
| Median | 11 ms | 11 ms | 0 |
| **P99** | **130 ms** | **210 ms** | **+80 ms** ⚠ |

*"성능 개선했는데 P99 가 *늘어났다*"* — 직관에 반하는 결과.

### 첫 가설 (잘못됨)

> *"atomic UPDATE 후 OrderDetail 생성을 위해 `findById` 한 번 추가 — 추가 SELECT 의 비용이 P99 에 그대로 더해짐"*

근거:
- atomic UPDATE 가 영속성 컨텍스트와 분리됨 (entity 가 1차 캐시에 없음)
- `findById` 한 번 추가 = SELECT 1 round-trip 추가
- 평균 응답 시간엔 묻히지만 P99 (느린 케이스) 에 영향

→ 다음 후보로 *"OrderDetail.create 시그니처 단순화 (productOptionId + price 만 받기) 로 SELECT 제거"* 를 적었다.

### 추적 — 측정 5 의 데이터가 가설을 반박

측정 5 에서 JDBC 튜닝 + wait_time 단축을 함께 적용:

| 지표 | 측정 4 | 측정 5 |
|---|---|---|
| RPS | 39.9 | 352.9 |
| **P99** | **210 ms** | **70 ms** ⭐ |

→ **P99 가 *오히려 단축*** (210 → 70 ms, 3 배). *"추가 SELECT 가 P99 늘렸다"* 가설이 맞다면 측정 5 에서도 늘어나야 함. 그런데 *오히려 줄어듦*.

### 진짜 원인 — *측정 환경의 idle 노이즈*

- 측정 4: `wait_time = between(0.5, 2.0)` → 평균 1.25 초마다 *띄엄띄엄 트랜잭션*
- 트랜잭션 사이의 *대기 구간* 동안 *GC, OS 스케줄링, idle connection eviction* 등 *외부 노이즈* 가 발생할 시간이 있음
- 그 노이즈가 *다음 트랜잭션의 응답 시간을 잠깐 늘림* → P99 (상위 1%) 에 잡힘
- 측정 5: `wait_time = between(0.05, 0.2)` → *연속 부하* → 노이즈가 평균에 묻힘

### 깨달음

**약한 부하의 P99 는 노이즈에 오염될 수 있다.** 진짜 P99 를 보려면 *연속 부하* 가 필요하다. 측정 4 의 P99 증가는 *코드 문제가 아니라 측정 환경 문제* 였다.

→ *"P99 가 늘어난 게 코드 탓"* 으로 넘겨서 *불필요한 OrderDetail 시그니처 변경* 을 했다면 측정 5 에서 그게 효과 있었는지 검증할 수도 없었을 것. **측정으로 가설을 반박** 한 것이 잘못된 코드 변경을 막았다.

### 코드 변경 — *없음*

가설이 반박되어 *"OrderDetail 시그니처 단순화"* 는 보류. 측정 5 의 P99 70 ms 가 충분히 좋아 *작은 ROI* 로 판단.

## 사건 2 — 측정 6 의 5xx 13.28 % 추적

### 증상

측정 5 의 RPS 352.9 가 진짜 시스템 한계인지 확인하려고 *100 users* 측정 (측정 6) 진행.

| 지표 | 값 |
|---|---|
| Total reqs | 44,359 |
| **Fails** | **5,892 (13.28 %)** ⚠ |
| Total RPS | 431.9 |
| Avg | 31 ms |

*"100 users 에서 시스템이 13 % 의 비율로 무너진다"* — *겉보기로는 한계 발견 신호*.

### 첫 가설 — *시스템 한계 도달*

가능성 후보들:
1. HikariCP pool 100 한도 초과 → connection wait timeout → 500
2. DB DeadlockException
3. JPA persistence context 관련 예외
4. OrderDetail.create 내부 NPE

actuator 메트릭 확인 — *비활성화 상태* (N/A). Spring Boot 콘솔 로그도 ERROR 가 안 보임 (콘솔만 띄운 상태).

→ 직접 추적 필요.

### 결정적 단서 — endpoint 별 fail 분리

```python
# Locust UI Statistics 표
POST /orders (hot)     reqs=35,572  fail=0      (0%)
POST /orders (random)  reqs=8,787   fail=5,892  (67%)
```

→ **hot option (단일 옵션 락 경합) 은 0 % / random option (여러 옵션 분산) 만 67 % 실패**. *"같은 시스템에 같은 부하인데 왜 random 만 무너지는가"* 가 핵심 질문. 시스템 한계라면 *둘 다 무너져야* 함.

### 추적 — 직접 재현 시도

콘솔 로그에 정보가 없으니 *재현* 으로:

```bash
# perf_buyer 로 로그인 → 풀 200 옵션 중 무작위 5 개에 주문 시도
$ for OPT in 65291 38272 39491 62789 34378; do
    curl -b cookie.txt -X POST http://localhost:8080/api/v1/orders/orders \
         -H "Content-Type: application/json" \
         -d "{\"addressId\":50,\"details\":[{\"productOptionId\":$OPT,\"quantity\":1}]}"
  done

option_id=65291  → HTTP 201
option_id=38272  → HTTP 500 ← 응답: "code":"C002","message":"서버 내부 오류"
option_id=39491  → HTTP 500
option_id=62789  → HTTP 201
option_id=34378  → HTTP 500
```

옵션별로 결과가 *결정적* 으로 갈렸다 (같은 옵션은 항상 같은 결과). 즉 *경합 / 타이밍 문제가 아니라 옵션의 데이터 차이*.

### 데이터 비교 — 무엇이 다른가

```sql
SELECT po.product_option_id AS opt_id,
       po.product_id, p.user_id AS store_user_id, p.name,
       u.role, u.is_active
FROM products_options po
LEFT JOIN products p ON p.product_id = po.product_id
LEFT JOIN users u ON u.user_id = p.user_id
WHERE po.product_option_id IN (65291, 38272, 39491, 62789, 34378);
```

| opt_id | store_user_id | u.role | 결과 |
|---|---|---|---|
| 34378 | 14 | **NULL** ← user_id=14 가 users 에 *없음* | 500 |
| 38272 | 15 | **NULL** | 500 |
| 39491 | 15 | **NULL** | 500 |
| 62789 | 18 | STORE | 201 |
| 65291 | 19 | STORE | 201 |

→ **`products.user_id` 가 가리키는 user 가 `users` 테이블에 없음** (FK 제약 없는 테스트 시드 데이터의 무결성 결함). atomic UPDATE 는 정상 동작했지만, 그 후 OrderDetail / 응답 빌드 단계에서 store(user) 를 LAZY 로드할 때 NPE → 500.

### 결정적 검증 — 비율이 *정확히* 일치하는가

가설이 맞다면 *"풀 200 옵션 중 dangling FK 비율 = random option fail 비율"* 이어야 한다.

```sql
SELECT
    SUM(CASE WHEN u.user_id IS NULL THEN 1 ELSE 0 END) AS dangling_fk,
    COUNT(*) AS total
FROM (
    SELECT po.product_option_id, p.user_id AS p_user_id
    FROM products_options po
    JOIN products p ON p.product_id = po.product_id
    WHERE po.stock_quantity > 0
    ORDER BY po.stock_quantity DESC LIMIT 200
) pool
LEFT JOIN users u ON u.user_id = pool.p_user_id;

→ dangling_fk = 134 / total = 200 = 67.0 %
```

| 측정 6 random fail 비율 | 풀 dangling FK 비율 |
|---|---|
| **67.0 %** (8,787 중 5,892) | **67.0 %** (200 중 134) |

**정확히 일치.** 인과 관계 *수치적 입증*.

### 해결 — locustfile 의 옵션 풀 쿼리 한 줄

```python
# Before — 단순 stock > 0 필터
SELECT product_option_id, stock_quantity
FROM products_options
WHERE stock_quantity > 0
ORDER BY stock_quantity DESC LIMIT 200

# After — 유효 store FK 가 살아있는 옵션만
SELECT po.product_option_id, po.stock_quantity
FROM products_options po
JOIN products p ON p.product_id = po.product_id
JOIN users u ON u.user_id = p.user_id
WHERE po.stock_quantity > 0 AND u.role = 'STORE'
ORDER BY po.stock_quantity DESC LIMIT 200
```

### 측정 6 재실행 — 검증

| 지표 | Before (오염 풀) | After (깨끗 풀) |
|---|---|---|
| 누적 reqs | 44,359 | 36,955 |
| **Fails** | **5,892 (13.28 %)** ⚠ | **0 (0 %)** ✅ |
| Total RPS | 431.9 | 308 |

**Fails 0 %.** 가설 *완전 입증*.

### 깨달음

- **측정 데이터의 무결성도 검증해야 한다** — 시드 데이터에 FK 제약 없으면 *측정 단계에서 결함이 드러남*. 5xx 를 *시스템 한계로 오해할 뻔* 했다
- **endpoint 별 비대칭 분리가 데이터 결함의 신호** — *"같은 시스템 같은 부하인데 한쪽만 무너지는가"* 라는 질문이 핵심
- **수치가 정확히 일치하면 인과 관계가 입증된다** — 67 % = 67 %. *"FK 가 깨져서 5xx 가 났을 것"* 추측이 아닌 *"풀의 67% 가 정확히 그 비율로 fail 했다"* 의 차이

## 사건 3 — 100 users 가 50 users 보다 RPS 낮은 발견 → sweet spot 가설

### 증상

측정 6 재실행 결과:

| 측정 | Users | RPS | Median |
|---|---|---|---|
| 5 | 50 | **353** ⬆ | 10 ms |
| 6 재실행 | 100 | **308** ⬇ | 20 ms |

*user 수를 두 배 늘렸는데 RPS 가 *감소** (353 → 308). 이론값 (이론 RPS 800) 대비 *훨씬 낮음*.

### 가설 — *sweet spot 50 users*

해석 (측정 6 시점):
- 50 users — 시스템이 여유 있게 처리 (RPS 353 = 이론 400 의 88 %)
- 100 users — *contention 영역 진입*, RPS 못 늘고 응답 시간만 늘어남
- *"50 users 부근이 sweet spot"*
- atomic UPDATE 도 *동일 row 에 대한 DB row lock* 으로 자동 직렬화 → 그 한계가 보임

→ *전형적 throughput collapse 곡선의 정점* 으로 해석.

### 글에 쓴 결론 (잠정)

> *"시스템의 sweet spot 은 50 users 부근, 동일 row contention 한계는 atomic UPDATE 의 본질"*

이 가설이 맞다면 *200 users* 측정 시 RPS 가 *더 떨어지거나 비슷* 해야 함 (전형적 collapse 패턴).

### 검증 — 측정 7 (200 users) 진행

→ *사건 4 에서 가설이 반박됨*.

### 깨달음 (이 시점)

*잠정 가설* 임을 명시하고 측정 7 으로 검증 필요. *"한 측정점만 보고 곡선을 단정하지 않는다"* 의 출발.

## 사건 4 — 측정 7 의 가설 반박 → throughput-latency trade-off 발견

### 증상

측정 7 (200 users / wait 0.05~0.2 / 2 분):

| 지표 | 값 |
|---|---|
| Total reqs | 60,332 |
| Fails | **1** (실질적 0 %) ✅ |
| Total RPS | **502.3** |
| **Median** | **89 ms** ⬆⬆ |
| Avg | 93.5 ms |
| Max | 605 ms |

*sweet spot 가설 반박*:

| 측정 | Users | RPS | Median |
|---|---|---|---|
| 5 | 50 | 353 | 10 |
| 6 재 | 100 | **308** ⬇ | 20 |
| **7** | **200** | **502** ⬆⬆ | **89** |

→ 200 users 에서 RPS 가 *오히려 +63 %* 회복 (308 → 502). *"sweet spot 50 users"* 가설은 틀림.

### 새 해석 — *throughput-latency trade-off*

| 측정 | Users | RPS | Median | RPS/user |
|---|---|---|---|---|
| 5 | 50 | 353 | 10 ms | 7.06 |
| 6 재 | 100 | 308 | 20 ms | 3.08 |
| **7** | **200** | **502** | **89 ms** | **2.51** |

→ user 수를 늘리면:
- throughput (RPS) 은 *서서히* 늘어남
- latency (Median) 가 *그 이상으로* 늘어남
- RPS/user 는 *계속 떨어짐*

= *전형적 saturation 곡선*. *RPS 가 늘어 보이지만 사용자별 응답 시간으로 갚는다*. 200 users 의 RPS 502 는 좋아 보여도 *모든 user 가 평균 89 ms 씩 기다려서 얻은 throughput*.

### 부가 발견 — Locust CPU 90 %+ 경고

```
[2026-05-03 22:45:38] WARNING/root: CPU usage above 90%! This may constrain
your throughput and may even give inconsistent response time measurements!
```

→ **부하 클라이언트 측 단일 머신 한계 도달**. 측정 7 의 데이터는 *시스템 한계* 와 *측정 환경 한계* 가 섞여 있을 가능성. 진짜 곡선은 *별도 머신 분리* 후의 영역.

### 깨달음

- **하나의 측정점으로 곡선을 단정하지 마라** — 50 → 100 의 dip 만 보고 *"sweet spot"* 으로 결론 내릴 뻔. 200 users 의 *세 번째 점* 이 곡선을 *완전히 다르게* 보여줌
- **RPS 만 보지 말고 Latency 와 함께 보라** — RPS *겉보기 회복* 의 이면에 *Latency 4 배 폭증*. RPS/user 같은 파생 지표가 saturation 영역을 드러냄
- **단일 머신 측정의 신뢰도 천장을 인정하라** — 측정 3 (서버 측 status=0) + 측정 7 (Locust CPU 90%+) 이 다른 모습으로 같은 한계를 가리킴

### 코드 변경 — *없음*

이건 *코드 한계가 아니라 측정 환경 한계 + 시스템 saturation 의 자연스러운 모양*. 코드 수정 없이 *narrative 와 다음 단계 정의* 로 풀어냄 (별도 머신 / 샤딩).

## 사건 5 — *"다음은 분산 락"* 가설의 reframing

### 가설 (측정 전, 락 후보 검토 단계)

처음 락 후보를 검토할 때 (글 2 장):

| 후보 | 평가 | 결정 |
|---|---|---|
| `synchronized` | 단일 인스턴스만 / 다중 인스턴스 X | 부적합 |
| 낙관적 락 | 충돌 잦으면 retry 폭주 | 부적합 |
| **DB 비관적 락** | 정합성 완벽, 단일/다중 인스턴스 OK | ⭐ **선택** |
| Redis 분산 락 | 다중 인스턴스 환경 표준, *"다음 단계"* | 가설로 두고 인프라 미리 만듦 |

→ **`@DistributedLock` AOP 인프라** (StringRedisTemplate SETNX + UUID 자기 락 해제 + SpEL 동적 키 + Expression 캐싱) 까지 미리 완성. *"다중 인스턴스 가면 분산 락"* 가설 *확신*.

### 측정 사이클이 가설을 흔들기 시작

**측정 4** (atomic UPDATE 전환):
- 락 점유 시간 0 으로 만들어버림 → *비관적 락의 *DB 커넥션 점유* 이슈 자체 사라짐*
- 분산 락의 핵심 가치 (*"DB 커넥션 안 점유"*) 가 *atomic UPDATE 만으로 달성됨*

**측정 6 / 7**:
- 동일 row contention 의 직렬화 한계는 *atomic UPDATE 도 같음* — DB row lock 자동 직렬화
- 분산 락 추가해도 *DB row lock 은 그대로 잡힘* + *Redis 라운드 트립 비용만 추가*

### 추적 — *분산 락이 이 영역에서 무엇을 해결하나?*

질문을 *원점에서* 다시 던졌다:

> 분산 락이 *재고 차감* 영역에 무엇을 더해주는가?

| 메커니즘 | 어떻게 직렬화 | 추가 비용 |
|---|---|---|
| atomic UPDATE | DB row lock (자동) | 0 |
| 분산 락 + atomic UPDATE | Redis SETNX → DB row lock | Redis 라운드 트립 |
| 분산 락 + 비관적 락 | Redis SETNX → DB row lock (SELECT FOR UPDATE) | Redis + DB 락 점유 시간 |

→ **모든 케이스에서 결국 DB row lock 이 직렬화한다**. 분산 락은 *그 위에 한 겹을 덧씌우는* 형태. 단일 SQL 차감 영역에서는 *추가 효과 없음 + 비용만 추가*.

### 진짜 분산 락의 영역

```
✓ 분산 락이 가치 있는 영역:
   - 선착순 쿠폰 발급 (여러 단계 묶음 — 카운터 검증 + 발급 + 알림)
   - 배송 작업 큐 클레임 (워커 N 대 중 하나만 작업 잡기)
   - 외부 API 중복 호출 방지 (DB row 가 없는 단계)
   - 트랜잭션 외부 자원 락 (캐시 invalidation 순서 등)

✗ 분산 락이 답이 아닌 영역:
   - 단일 SQL 의 row 차감 (atomic UPDATE 만으로 충분)
   - 결제 콜백 멱등성 (DB 비관적 락이 깔끔)
```

### 새 결론 — 분산 락 인프라는 *보존*, 적용은 *다른 도메인*

- `@DistributedLock` AOP 코드 *그대로 유지* — *주문/결제 영역에는 안 붙임*
- 미래 도메인 (선착순 쿠폰, 작업 큐 등) 추가 시점에 적용
- *주문/결제 영역에서 진짜 다음 단계* = *인기 옵션 샤딩 (단일 row 자체 분해)* + *다중 인스턴스 환경 측정*

### 글 안의 표현 변경

이 *가설 reframing* 을 글 12 장에 *narrative arc 의 핵심* 으로 명시:

> *"처음 가설은 비관적 락 → 다음은 분산 락 이었다. 측정 사이클을 거치며 *그 가설 자체가 틀렸음* 을 깨달았다. 진짜 다음 단계는 *단일 row 자체를 분해 (샤딩) — 분산 락 영역이 아님*."*

### 깨달음

- **가설을 *측정으로 검증* 하지 않으면 잘못된 방향으로 한 사이클 더 쓴다** — *"다음은 분산 락"* 으로 확신해 분산 락 적용 + 비교 측정에 시간을 썼다면 *추가 성과 없는* 작업이 됐을 것
- **인프라는 *적용 결정과 분리* 해서 보존 가능** — 분산 락 인프라는 다른 도메인을 위해 *그대로 둠*. *코드를 만들었다고 해서 모든 도메인에 적용해야 하는 건 아님*
- **락의 *영역과 한계* 를 구분할 줄 아는 게 진짜 락 이해** — *"좋은 락"* 이 따로 있는 게 아니라 *"이 영역에 맞는 락"* 이 있다

## 종합 — 트러블슈팅에서 얻은 5 가지 원칙

### 1. 직관에 반하는 결과는 *측정 환경* 부터 의심

사건 1 의 P99 증가, 사건 3 의 RPS dip 모두 *처음엔 코드 탓* 으로 봤지만 *측정 환경 (wait_time, 부하 패턴)* 이 진짜 원인. **개선 후 결과가 이상하면 *측정 자체* 가 무엇을 보고 있는지부터 점검**.

### 2. 비대칭은 *데이터/환경 결함* 의 신호

사건 2 의 *hot 0 % vs random 67 %* 가 결정적 단서. *같은 시스템 같은 부하* 인데 결과가 *체계적으로 갈리면* 시스템이 아니라 *입력 데이터의 특성 차이*. **endpoint / 카테고리 / 케이스별로 메트릭을 분리해서 보는 습관**.

### 3. 수치적 매치가 인과 관계 입증

사건 2 의 *"풀 dangling FK 67 % = random fail 67 %"* 가 가설을 *추측에서 증명으로* 만듦. **가설 검증 시 *수치 자체가 일치하는지* 까지 확인**. 그래야 글에 *"~로 추정된다"* 가 아니라 *"정확히 ~ 비율로 일치"* 라고 쓸 수 있다.

### 4. 한 측정점으로 곡선을 그리지 마라

사건 3 → 사건 4 의 흐름. *"50 → 100 dip 으로 sweet spot 50"* 가설을 *200 users 측정으로 반박*. **가설은 *최소 세 점* 으로 곡선을 그리고 검증**. 두 점은 *우연/노이즈* 일 가능성.

### 5. 가설을 *측정으로 검증/반박* 하면 잘못된 방향을 막는다

사건 5 의 *"다음은 분산 락"* 이 측정으로 *reframing*. 가설을 *주장* 으로 두면 잘못된 작업에 시간을 쓰지만, *검증 가능한 형태* 로 두면 *측정이 답을 줌*. **모든 다음 단계 결정에 *"이 가설이 측정으로 검증 가능한가"* 를 먼저 자문**.
