## 누적 측정 — *invariant 0 건*

```
누적 reqs:    ~100 만+ (모든 시나리오 합)
음수 재고:     0 건 ✅
중복 발급:     0 건 ✅
Lost Update:  0 건 ✅ (혼합 환경 1 회 발생 — 즉시 발견 + 수정)
정합성 깨짐:    0 건 ✅
```

→ ***모든 측정에서 정합성 invariant 100% 유지***. 데이터 무결성 *완벽*.

## 완료한 시나리오별 *핵심 발견*

### 시나리오 1 — 상품 조회 (읽기 부하)

```
단일 서버 RPS 1,003 (실용 상한) — 7 단계 개선 누적
- 인덱스 + Projection + HikariCP 풀 + Covering Index + Redis 캐시 계층화
- 10,000 user 까지 graceful degradation (104K reqs / 0 fails)
- @Cacheable(sync=true) 로 cache stampede 차단
```

### 시나리오 2 — 주문 결제 (재고 차감)

```
비관적 락 → atomic UPDATE 전환
- RPS 8.8 × 향상 (39.9 → 352.9)
- P99 3 × 단축 (210 → 70 ms)
- 사이클 narrative: 가설 → 측정 → 반박 → 새 가설 (4 회 반복)
- "throughput-latency trade-off" 발견 (50/100/200 user 곡선)
```

### 시나리오 2-2 — 쿠폰 사용 주문 (보상 트랜잭션)

```
- 쿠폰 적용 오버헤드 ~1 ms 미만 (정상 13 ms vs no coupon 14 ms)
- 정합성 5 케이스 모두 검증 (재사용/만료/최소금액/동시사용/보상)
- cancelOrder 의 일관 처리 + markUnused 멱등 = 보상 누락 위험 0
```

### 시나리오 4 — 선착순 쿠폰 발급 ⭐

```
4 가지 메커니즘 정량 비교 매트릭스:
- 비관적 락:           RPS 526~630
- 분산 락 (SETNX):    RPS 190~195 (24~28 % 5xx — 의외 결과)
- Redis DECR + Lua:   RPS 640+ ⭐ (정점)
- + 비동기 저장:        RPS 632 (정합성 100%)

핵심 narrative: "분산 락이 다음 단계" 가설을 *측정으로 세 번 뒤집음*
다중 인스턴스 환경 + Spring Session 도입까지 진행
```

### 시나리오 6 — 결제 콜백 멱등성

```
비관적 락 (Order row FOR UPDATE)
- 같은 paymentKey 재호출 시 첫 번째만 markPaid()
- 이중 처리 / 재고 이중 차감 / 포인트 이중 적립 차단
- "교과서 패턴" 으로 정착
```

## 안 한 시나리오 — *각 케이스별 멈춘 이유*

### 시나리오 3 — 로그인 폭주 (BCrypt CPU 전염)

| 영역 | 평가 |
|---|---|
| 측정 가치 | 중 — *전염 효과* 정량화 가치 |
| ROI | **낮음** — 다른 시나리오 (Spring Session 도입 등) 에서 *세션 외부화* 영역은 다룸. CPU 한계는 *별도 영역* |
| 결정 | **별도 시리즈** (인증 도메인 글) 영역으로 미룸 |

### 시나리오 5 — 결제 타임아웃 스케줄러

| 영역 | 평가 |
|---|---|
| 측정 가치 | 낮음 — *코드 (Redis ZSET + Lua) + 글 ([blog-Redis타임아웃.md](../blog/blog-Redis타임아웃.md))* 이미 존재 |
| ROI | **낮음** — 측정 추가해도 narrative 약간 보강만 |
| 결정 | **현재 글로 충분** — 부하 측정은 *별도 보강 가능 영역* 으로 명시 |

### 시나리오 7 — DB 풀 고갈 / 전염 효과

| 영역 | 평가 |
|---|---|
| 측정 가치 | 낮음 (현재 영역 한정) — *비관적 락 → atomic UPDATE / Redis DECR* 전환으로 *전염 영역 자체가 줄어듦* |
| ROI | **낮음** — 비관적 락 영역 (재고 수동 변경 / 결제 멱등성 등) 만 남아 *측정 의미 작음* |
| 결정 | **운영 모니터링 영역** (Prometheus / Grafana 등) 에서 다룰 영역 |

### 시나리오 8 — 복합 트래픽 (모든 API 동시)

| 영역 | 평가 |
|---|---|
| 측정 가치 | 중 — *시스템 전체 균형 성능* 검증 |
| ROI | **낮음** — 시나리오 3/5/7 다 끝나야 의미 + 단일 머신 환경에서는 *측정 한계 (Locust CPU 등)* 가 먼저 옴 |
| 결정 | **마지막 영역** — 별도 머신 분리 + 다중 인스턴스 환경 구축 후 가능 |

## 측정 멈춘 *진짜 이유* — *무한 측정의 함정 회피*

### 1) ROI 가 급격히 떨어지는 영역 진입

| 사이클 | 효과 | ROI |
|---|---|---|
| atomic UPDATE 전환 | RPS 8.8 ×, P99 3 × 단축 | 매우 높음 ⭐ |
| Redis DECR + Lua atomic | 4 메커니즘 비교 narrative 정점 | 매우 높음 ⭐ |
| 쿠폰 사용 + 보상 트랜잭션 | 시나리오 문서 의미 살림 | 높음 |
| **남은 시나리오 (3/5/7/8)** | *narrative 보강 약간* | **낮음** → 멈춰야 함 |

### 2) 측정 환경의 신뢰도 천장 도달

```
단일 머신 한계:
- 측정 3 (주문결제 100 user): 서버측 status=0 (TCP 한계)
- 측정 7 (주문결제 200 user): Locust CPU 90%+ 경고
- Phase J (선착순 쿠폰 1000 user): RPS 떨어짐, fails 1.42%

→ 200 user 부근부터 *측정값이 시스템 한계 vs 측정 환경 한계* 분리 어려움
→ 추가 측정해도 *데이터의 의미가 약해짐*
```

### 3) 균형 잡힌 포트폴리오 우선

```
✅ 측정 영역: 시리즈 3 부작 + 쿠폰 trilogy = 압도적 강함
⚠ 약점 영역:
   - CI/CD (없음)
   - 모니터링 / 옵저버빌리티 (없음)
   - 클라우드 배포 (없음)
   - 프론트엔드 (없음)

→ 백엔드 측정 더 파면 *한 영역만 강해지고 균형 깨짐*
→ 운영 / 배포 영역으로 균형 보강이 ROI 더 좋음
```

## 측정의 한계 — *정직하게*

### 측정한 것 ✅

| 차원 | 검증 데이터 |
|---|---|
| RPS / 응답시간 / 5xx | 누적 ~100 만 reqs |
| 정합성 invariant | 0 건 (음수 재고 / 중복 발급 / Lost Update) |
| 4 가지 동시성 메커니즘 비교 | 비관적 락 / 분산 락 / atomic UPDATE / Redis DECR |
| 단일 + 다중 인스턴스 환경 | 4 인스턴스 + nginx LB + Spring Session |
| 부하 4 단계 곡선 (선착순) | 50 / 200 / 500 / 1000 user |
| fast-fail 경로 | 정상 처리보다 10~15 × 빠름 정량 입증 |
| 보상 트랜잭션 | cancelOrder 의 일관 처리 |

### 측정 못 한 것 ⚠

| 차원 | 측정 환경 한계 |
|---|---|
| 5,000+ user 대용량 부하 | 단일 머신 환경의 측정 신뢰도 천장 |
| 수평 확장성 (수십 인스턴스) | 클라우드 환경 + 다중 머신 필요 |
| 장애 내성 (chaos test) | Redis / DB 죽이기 시나리오 미구성 |
| Redisson `RLock` 비교 | 단순 SETNX 폴링만 측정. Redisson 미적용 |
| Redis Cluster | 단일 노드 환경만 |
| 장기 안정성 | 1~2 분 측정. 수시간/수일 부하 X |
| DB 부하 메트릭 | HikariCP / MySQL slow log 별도 수집 X |

→ *측정한 영역 / 못 한 영역 분리해서 인정* 하는 것이 *측정 기반 의사결정의 진정성*.

## 우리 서버의 *capacity* (단일 머신 측정 기준)

| 영역 | 안전 처리량 | 등급 |
|---|---|---|
| 상품 조회 | RPS 1,003 / 일일 2,200 만 | 무신사 일반 시간대 진입 |
| 쿠폰 발급 | RPS 640 / 일일 1,400 만 | 11번가급 단일 서버 |
| 주문 생성 | RPS 350~502 / 일일 750 만 | 11번가급 단일 서버 |
| 쿠폰 사용 주문 | RPS 62 (작은 부하 측정만) | 11번가급 충분 |

→ ***단일 서버 *11번가 ~ 무신사 일반 시간대* 수준 검증***.

진짜 *대용량 (쿠팡 / 카카오 선물하기 이벤트급)* 은 *별도 인프라 영역*:
- 다중 머신 + 인스턴스 수십 대
- Redis Cluster
- Read Replica
- Kafka 비동기 큐
- CDN / 엣지 캐시

## 다음 단계 — *측정이 아닌 영역*

```
✅ 끝:
   - 백엔드 동시성 / 성능 측정 (6 시나리오)
   - 코드 변경 (atomic UPDATE / Redis DECR / Spring Session / 비동기 저장 등)
   - 글 작성 (~6,000 줄, 8 문서)
   
⏳ 다음 단계 (별도 영역):
   - PR / README / 멘토 피드백 (마무리, 1 시간)
   - 운영 영역 — CI/CD / 모니터링 / 클라우드 배포 (1~3 일)
   - 프론트엔드 (간단한 관리자 페이지, 옵션)
   - 별도 시리즈 — Redisson / Cluster / 다중 머신 측정 (포트폴리오 V2)
```

→ ***"측정 멈출 시점도 안다"*** 가 면접관에게 *균형 잡힌 인식 + 학습 자세* 시그널.
