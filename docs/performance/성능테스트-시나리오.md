
## 개요

이 문서는 StyleHub 서버가 대용량 트래픽 상황에서 어떻게 동작하는지를 확인하기 위한 Locust 기반 부하 테스트 시나리오를 정리한다.

측정 대상은 크게 일곱 가지로 각기 다른 성격의 트래픽과 장애 상황을 커버한다.

상품 조회는 읽기 부하의 대표이고, 주문과 결제는 비관적 락 기반 쓰기 부하와 동시성을 검증한다.

쿠폰 사용 주문은 여기에 트랜잭션 보상 로직이 추가된 복합 케이스이고, 로그인 폭주는 DB I/O 가 아닌 BCrypt 해싱에서 오는 CPU 집약 부하를 재현한다. 선착순 쿠폰 발급은 수량 제한 이벤트에서 발생하는 극한 동시성을 재현한다.

여기에 장애 복원력을 검증하는 세 가지를 추가로 둔다.

결제 타임아웃 스케줄러는 대량 주문 이탈 후 배치 복구가 정합성을 지키는지 확인하고, 결제 콜백 멱등성은 PG 가 같은 요청을 여러 번 보낼 때 이중 처리를 방어하는지 검증하며, DB 커넥션 풀 고갈은 비관적 락의 구조적 약점이 무관한 API 까지 전염시키는지를 관찰한다.

테스트는 모두 로컬에서 띄운 StyleHub API 서버를 대상으로 진행하며 Locust를 도구로 사용한다.

인증은 HTTP 세션 기반이고 각 시나리오는 로그인한 세션을 유지한 채로 API를 호출한다.

측정에서 가장 중요한 원칙은 **TPS 같은 양적 지표만 보지 말고 데이터 정합성도 검증 쿼리로 함께 확인한다는 것**이며, 응답 시간은 평균이 아닌 P95/P99를 기준 지표로 삼는다.
평균은 꼬리 지연을 감추고, 꼬리 지연이 실제 사용자 경험을 망치기 때문이다.

## 테스트 대상 API

부하를 걸 API는 일곱 개다. 상품 목록과 상세 조회는 비인증 공개 API고, 주문 생성은 쿠폰 없는 경우와 있는 경우 두 가지로 나눈다.

결제 승인은 토스 결제창에서 successUrl로 리다이렉트되어 호출되는 GET 엔드포인트이고, 선착순 쿠폰 발급과 내 쿠폰 목록 조회는 로그인 상태의 USER가 호출한다.

- `GET /api/v1/products` (목록 조회, 비인증)
- `POST /api/v1/users/login` (로그인, 비인증)
- `GET /api/v1/products/{productId}` (단건 조회, 비인증)
- `POST /api/v1/orders/orders` (주문 생성, USER)
- `POST /api/v1/orders/orders` (쿠폰 사용 주문 생성, USER)
- `GET /api/v1/payments/success` (결제 승인, 비인증)
- `POST /api/v1/coupon-events/{couponEventId}/issue` (선착순 발급, USER)
- `GET /api/v1/coupon-events/my` (내 쿠폰 목록, USER)

## 시나리오 1: 상품 조회 (읽기 부하)

상품 조회 시나리오의 목표는 **커서 기반 페이지네이션과 JOIN FETCH 쿼리가 실제 트래픽에서 얼마나 빠른지**를 확인하는 것이다.

이 API는 서비스 전체 트래픽의 절반 이상을 차지하는 영역이기 때문에, 여기서 응답 시간이 조금만 늘어져도 사용자는 서비스 전체가 느리다고 느낀다.

테스트 흐름은 다음과 같다.

먼저 `GET /api/v1/products`로 첫 페이지를 조회하고, 응답의 마지막 productId를 커서로 넘겨 다음 페이지를 요청한다.

그 다음 스토어 필터(`storeId`), 카테고리 필터(`mainCategory=CLOTHING`) 같은 조건을 붙여 쿼리 조합이 다양해질 때 성능이 어떻게 변하는지 본다.

마지막으로 `GET /api/v1/products/{productId}`로 단건 상세를 조회해 JOIN FETCH가 N+1 없이 한 번에 데이터를 가져오는지 확인한다.

부하는 Warm-up 단계에서 10명이 30초 동안 요청해 JVM JIT와 커넥션 풀을 예열하는 것으로 시작한다.

이후 Light(50명·100RPS·2분), Medium(200명·500RPS·3분), Heavy(500명·1000RPS·5분), Spike(1000명·2000RPS·1분)까지 단계적으로 끌어올린다.

단계별로 응답 시간이 어떻게 늘어나는지를 관찰해야 병목이 DB인지, JPA 직렬화인지, 아니면 네트워크 I/O인지를 추정할 수 있다.

측정 지표는 평균 응답 시간(목표 100ms 미만), P95(300ms 미만), P99(500ms 미만), 에러율(0.1% 미만), 그리고 TPS다.

이 목표는 대용량 트래픽 커머스 기준으로 잡은 상한이며, 목표 대비 어느 정도 여유가 있는지 혹은 턱없이 모자라는지가 다음 편 실측 분석의 주제가 된다.

## 시나리오 1-2: 상품 조회 캐시 cold-start (cache miss 측정)

시나리오 1이 캐시가 채워진 상태의 정상 부하를 측정하는 데 비해, 1-2의 목표는 **캐시가 비어 있을 때 DB가 그 부하를 버티는지**를 확인하는 것이다.

이 시나리오가 필요한 이유는 단순하다. 시나리오 1의 P95가 60ms로 좋게 나오더라도 그건 캐시가 가려준 결과일 뿐, TTL이 만료되는 순간이나 신규 인스턴스가 투입되는 순간엔 모든 요청이 DB로 직격한다. 그 순간 DB가 무너지면 평소 좋아 보이던 모든 수치가 의미를 잃는다. **캐시가 빠진 상태에서 시스템이 버티는지를 따로 측정해야 진짜 한계를 알 수 있다.**

흐름은 시나리오 1과 같지만 시작 조건만 다르다.

테스트 시작 시점에 Redis 에서 `products:firstPage*` , `products:detail*` 패턴의 캐시 키를 모두 삭제한다. Locust 의 `@events.test_start.add_listener` 로 이 작업을 한 번만 수행하므로 측정 stats 에는 잡히지 않고, 모든 가상 유저가 부하를 시작하는 순간 캐시는 완전히 비어 있다.

그 다음은 시나리오 1과 동일한 task 가중치(첫 페이지 / 다음 페이지 / 스토어 필터 / 카테고리 필터 / 단건 상세)를 그대로 사용하지만, 첫 1~2분 동안 들어오는 요청은 거의 모두 cache miss 로 떨어져 DB 쿼리를 발생시킨다. 시간이 지나면 캐시가 자연스럽게 채워져 hit 응답 시간으로 수렴하므로, 측정 시간을 짧게(1~2 분) 잡아 cold-start 구간만 집중 관찰한다.

부하는 짧고 강하게 건다.

cold-start spike 단계에서 0→500명을 200명/초의 속도로 빠르게 spawn 해 1분간 측정하고, cold-start heavy 단계에선 0→1000명을 500명/초로 더 빠르게 부어 1분간 측정한다. 천천히 스폰하면 그 사이에 캐시가 채워져 측정 의도가 흐려진다.

측정 지표는 시나리오 1과 동일하지만 해석 기준이 다르다.

P95 가 시나리오 1 베이스라인(30~70ms)보다 어느 정도 튀는지가 **캐시가 가려놓던 DB 부하의 크기**다. 시간이 지나도 P99 가 안정되지 않거나, 5xx 에러가 발생하거나, HikariCP connection pool 고갈 로그(`Connection is not available, request timed out`)가 찍히면 DB 가 버티지 못한다는 신호다. 이 신호가 나오면 다중 인스턴스 환경에서는 stampede 방어(Redisson 분산 락 기반 캐시 등) 도입을 검토해야 한다.

부하 도구는 별도 파일로 분리했다. `locustfile_product.py` 는 hit 베이스라인 전용으로 두고, `locustfile_product_cache_miss.py` 가 이 cold-start 측정을 담당한다. 같은 파일에 두 모드를 섞으면 결과 CSV 에서 어떤 측정인지 헷갈리고 hit/miss 비교가 어려워지기 때문이다.

```bash
# 사전 조건: redis-py 설치 (pip install redis)

# cold-start spike: 0→500 users
locust -f performance/locustfile_product_cache_miss.py --host=http://localhost:8080 \
       --headless -u 500 -r 200 -t 1m \
       --csv=performance/results/product_cache_miss_500

# cold-start heavy: 0→1000 users
locust -f performance/locustfile_product_cache_miss.py --host=http://localhost:8080 \
       --headless -u 1000 -r 500 -t 1m \
       --csv=performance/results/product_cache_miss_1000
```

## 시나리오 2: 주문 → 결제 (비관적 락, 쿠폰 없음)

이 시나리오의 목표는 **현재 비관적 락 기반 재고 차감이 어느 지점에서 한계를 드러내는지를 숫자로 확정**하는 것이다.

지금 구조가 얼마나 빠른지를 알아야 나중에 Redis 분산락으로 전환했을 때 개선 폭을 숫자로 비교할 수 있다.

측정 없이 "분산락이 빠를 것 같다"는 이론으로 학습한걸  인프라를 바꾸면 개선의 근거를 사후에 제시할 수 없다.

흐름은 현실적인 구매 플로우를 따라간다.

먼저 로그인으로 세션을 얻고, 상품 상세를 조회한 뒤, 주문 생성 API를 호출해 재고를 차감하며 Payment READY 레코드를 만든다.

---

그 다음 토스 성공 콜백을 흉내내는 `GET /api/v1/payments/success`를 호출해 결제 승인까지 마친다.

검증 케이스 중 가장 중요한 것은 **같은 상품 옵션에 동시 주문이 들어올 때 재고 정합성이 유지되는가** 이다.

재고 10개짜리 상품에 50명이 동시에 주문하면 10명은 성공하고 40명은 409 CONFLICT로 떨어져야 한다.


11명 이상이 성공했다면 락이 뚫린 것이고, 숫자가 아무리 예뻐도 이 테스트는 불합격이다. 한 주문에 옵션이 여러 개 포함된 케이스도 반드시 검증한다.

현재 구조는 deadlock을 막기 위해 `optionId` 오름차순으로 정렬한 뒤 락을 획득하는데, 이 설계가 실제 동시성 상황에서도 deadlock을 방지하는지를 확인한다.

부하는 기본 10명(2분)으로 정합성 확인부터 시작해 50명(3분)으로 같은 옵션에 집중시켜 경합을 일으키고, 100명(5분)으로 여러 옵션에 분산시키고, 마지막으로 300명(5분)까지 올려 한계 TPS를 측정한다.

단계가 올라갈수록 TPS가 동시 유저 수에 비례해서 올라가지 않는 지점이 나올 텐데 그 지점이 **락 대기 시간이 TPS를 제한하는 구간**이다.

측정 지표는 TPS, 재고 정합성(주문 수량의 합 = 차감된 재고 수량), 평균/P95/P99 응답 시간, 락 대기 시간, 그리고 DB 커넥션 풀 사용률이다.

비관적 락의 구조적 약점은 대기 중인 요청이 커넥션을 계속 점유한다는 점이라, 커넥션 풀 사용률이 어느 동시 유저 수부터 고갈되는지를 봐야 한다.

테스트가 끝난 뒤에는 아래 쿼리로 정합성을 검증한다.

```sql
-- 주문 수량 합 vs 차감된 재고
SELECT po.product_option_id, po.stock_quantity,
       (SELECT SUM(od.quantity)
        FROM order_details od
        WHERE od.product_option_id = po.product_option_id)
FROM products_options po
WHERE po.product_option_id = {테스트 옵션 ID};

-- 주문 상태별 건수
SELECT order_status, COUNT(*)
FROM orders
GROUP BY order_status;
```

## 시나리오 2-2: 쿠폰 사용 주문 → 결제 (복합 트랜잭션)

쿠폰을 적용한 주문은 로직이 더 많다.

쿠폰 유효성 검증, 할인 금액 계산, 재고 차감, UserCoupon 상태 전이(AVAILABLE → USED)까지 모두 같은 트랜잭션 안에서 원자적으로 처리돼야 한다. 하나라도 실패하면 전부 롤백돼야 하고, 특히 결제 승인이 실패했을 때 쿠폰이 USED로 남으면 사용자는 쿠폰도 잃고 주문도 못 한 이중 손해 상태가 된다.

이 시나리오의 목표는 이 원자성과 보상 로직을 부하 상황에서 검증하는 것이다.

또 하나 정량화하고 싶은 건 **쿠폰 적용이 주문 응답 시간에 얼마나 오버헤드를 주는가**이다.

쿠폰 있는 주문의 평균 응답 시간에서 쿠폰 없는 주문의 평균 응답 시간을 빼면 그 차이가 쿠폰 검증·할인 계산·상태 전이의 총 비용이다.

이 숫자가 30ms인지 300ms인지에 따라 쿠폰 로직에 최적화가 필요한지, 아니면 그대로 두어도 되는지가 결정된다.

---
흐름은 일반 주문과 비슷하지만 쿠폰 조회와 적용이 추가된다.

로그인 후 `GET /api/v1/coupon-events/my`로 사용 가능한 쿠폰을 확인하고 상품을 조회한 뒤 주문 생성 API에 `userCouponId`를 포함해 호출한다.
결제 성공 콜백에서는 UserCoupon이 USED로 정확히 한 번만 전이되는지를 확인한다.

검증 케이스는 크게 다섯 가지다.

같은 UserCoupon으로 동시 주문 2건이 들어올 때 1건만 성공하는지, 만료된 쿠폰 사용 시 400으로 거절되는지, USED 상태 쿠폰을 재사용하려 할 때 거절되는지, 최소주문금액 미달 시 거절되는지, 그리고 가장 중요하게 **결제 실패 시 UserCoupon이 AVAILABLE로 복구되는지** 이다.


마지막 케이스는 보상 트랜잭션의 정확성을 증명하는 핵심이다.

부하는 기본 20명(2분) 쿠폰 100% 사용으로 오버헤드를 측정하고 혼합 100명(3분)에서 쿠폰 사용률을 50%로 낮춰 있음/없음 비교가 가능한 데이터를 뽑는다.

경합 200명(3분)에서는 같은 쿠폰 유형을 집중해 UserCoupon 락 경합을 발생시키고, 스트레스 300명(5분)에서 한계 TPS를 본다.


검증 쿼리는 세 가지를 준비한다.

첫째는 UserCoupon 상태별 집계로 중복 USED가 0인지 확인한다.

둘째는 같은 UserCoupon이 여러 주문에 사용됐는지를 확인하는 쿼리로 여기서 결과가 하나라도 나오면 정합성이 깨진 것이다.

셋째는 결제 실패(ABORTED) 주문의 쿠폰이 AVAILABLE로 복구됐는지 확인하는 쿼리다.

```sql
-- 중복 USED 검출
SELECT status, COUNT(*)
FROM user_coupons
WHERE coupon_event_id = {테스트 쿠폰 ID}
GROUP BY status;

-- 같은 UserCoupon이 여러 주문에 쓰였는지
SELECT user_coupon_id, COUNT(*)
FROM order_details
WHERE user_coupon_id IS NOT NULL
GROUP BY user_coupon_id
HAVING COUNT(*) > 1;

-- 결제 실패 주문의 쿠폰 복구 여부
SELECT uc.status, COUNT(*)
FROM user_coupons uc
JOIN order_details od ON od.user_coupon_id = uc.user_coupon_id
JOIN payments p ON p.order_id = od.order_id
WHERE p.status = 'ABORTED'
GROUP BY uc.status;
```

## 시나리오 3: 로그인 폭주 (CPU 집약 부하)

로그인은 다른 API와 성격이 완전히 다르다.

DB I/O가 병목이 아니라 **BCrypt 해싱** 이 병목이 되는 유일한 API이기 때문이다.

평소에는 초당 몇 건 수준이라 문제가 없지만, **쿠폰 이벤트 오픈 5분 전** 같은 특수 시점에는 로그인이 폭주한다.

사용자들이 이벤트를 놓치지 않으려고 미리 로그인해두기 때문이다.

이때 서버 CPU가 먼저 터지면 이벤트 자체가 열리기도 전에 서비스가 마비된다.

이 시나리오의 목표는 그 순간을 시뮬레이션해 **로그인 API의 TPS 한계와 CPU 점유율 상관관계** 를 확인하는 것이다.

흐름은 사전에 생성한 테스트 유저 500명이 동시에 `POST /api/v1/users/login`을 호출한다.

요청 본문에 이메일과 비밀번호를 담으면 서버는 DB에서 해시된 비밀번호를 가져와 BCrypt로 검증하고 세션 쿠키를 발급한다.

이 경로에서 가장 비싼 연산이 BCrypt 검증이라 여기서 CPU가 얼마나 점유되는지를 본다. 실패 케이스(비밀번호 불일치)도 소수 섞어 실패 경로와 성공 경로의 CPU 비용 차이를 함께 확인한다.

---
검증 케이스는 세 가지다.

첫번째는 500명이 동시에 로그인할 때 모든 요청이 **타임아웃 없이 200 응답** 을 받는가.

두번쨰는 세션 쿠키가 정상적으로 발급되어 이후 쿠폰 발급 API 호출에서 `UNAUTHORIZED`가 발생하지 않는가.

그리고 가장 중요한 셋째는 **로그인 폭주 동안 다른 API(상품 조회 등)의 응답 시간이 얼마나 영향을 받는가** 이다.

BCrypt가 CPU를 잡아먹으면서 관련 없는 상품 조회까지 느려지는 **전염 효과** 가 있는지를 확인한다.

---

부하는 세 단계로 구성한다. 기본 100명(30초)은 로그인 단독 부하로 기본 TPS를 본다.

급증 500명(1분)은 이벤트 직전 로그인 폭주를 재현해 한계 TPS와 CPU 점유율을 측정한다. 혼합 500명 로그인 + 200명 상품 조회(2분)가 이 시나리오의 핵심 단계다.

로그인만 따로 돌리면 CPU가 문제라는 것까지만 보이지만, 다른 API와 섞어 돌려야 **BCrypt 해싱이 서비스 전체를 얼마나 전염시키는지** 가 드러난다.

만약 상품 조회 응답이 100ms에서 1초로 10배 느려진다면, 그게 바로 CPU 공유 자원의 경합 증거다.

측정 지표는 로그인 TPS, 평균/P95/P99 응답 시간, 서버 CPU 사용률의 단계별 추이, 그리고 로그인 폭주 중 동시 호출된 **상품 조회 API의 응답 시간 변화** 다.

마지막 지표가 이 시나리오의 가장 중요한 관전 포인트다. 만약 전염 효과가 크게 나타나면 개선 방향은 세 가지가 있다.

BCrypt strength 낮추기(현재 설정 확인 후 10~12 수준으로 조정), 로그인 전용 스레드 풀 분리(CPU 집약 작업 격리), 또는 동일 IP·유저의 과도한 로그인 시도를 차단하는 레이트 리미팅이다. 어느 방향을 택할지는 측정 결과에 따라 결정된다.

## 시나리오 4: 선착순 쿠폰 발급 (극한 동시성)

쿠폰 선착순 발급은 평상시 트래픽의 수십 배가 순간적으로 들어오기 때문에 이벤트 오픈 시점 = 서비스 장애로 연결되기 쉬운 구간이다.

이 시나리오의 목표는 **100장짜리 쿠폰에 500명이 동시에 몰렸을 때 정확히 100장만 발급되는가, 그리고 그때 TPS는 얼마인가** 를 측정하는 것이다.

현재 구조는 두 겹의 방어선을 쓴다.

1차는 비관적 락으로 CouponEvent 행을 잠그는 것(`SELECT FOR UPDATE`)이고, 2차는 DB UNIQUE 제약으로 같은 (userId, couponEventId) 쌍의 중복을 차단하는 것이다. 1차가 경쟁 조건을 막고 2차가 중복 이슈를 한 번 더 막는 이중 구조인데, 이게 실제로 동작하는지를 500명 시뮬레이션으로 확인한다.

각 가상 유저는 먼저 로그인해 세션을 확보하고, 테스트 시작 신호를 기다렸다가 일제히 `POST /api/v1/coupon-events/{couponEventId}/issue`를 호출한다.

동시 시작을 맞추지 않으면 실제 이벤트 오픈과 달라서 경합 조건이 약해진다.

검증 케이스 네 가지 중 가장 중요한 것은 **100장 쿠폰에 500명 요청 시 정확히 100명 성공, 400명 SOLD_OUT** 이다. 이 숫자가 어긋나면 락이 뚫린 것이다. 같은 유저가 중복 요청을 보냈을 때도 1번만 성공하고 나머지는 409 ALREADY_ISSUED로 떨어져야 한다.

만료된 쿠폰 이벤트에 대한 요청은 전원 400이어야 하고, 1000장 쿠폰에 1000명이 요청하면 경합은 많지만 SOLD_OUT 없이 전원 성공해야 한다.

부하는 기본 50명·100장(1분)으로 정합성부터 확인하고, 집중 200명·100장(1분)에서 경합을 일으켜 락 대기 시간을 관찰한다. 극한 500명·100장(1분)에서 한계 TPS를 측정하며, 대규모 1000명·1000장(3분)으로 실전 이벤트 상황을 시뮬레이션한다.

측정 지표에서 주의할 점은, 여기서 발생하는 400건의 SOLD_OUT 응답은 **의도된 실패지 버그가 아니다.** 이걸 에러율에 포함시키면 "에러율 80%"라는 허수가 나와 숫자 해석을 망친다. 그래서 성공(200), 의도된 실패(400 SOLD_OUT, 409 ALREADY_ISSUED), 진짜 에러(500, 타임아웃)를 각각 따로 카운트해야 올바른 해석이 가능하다.

또 **성공 응답보다 실패 응답이 평균적으로 빠르게 나와야 정상이다.** 쿠폰이 이미 소진된 시점에는 락을 잡자마자 `validateIssuable`에서 바로 튕겨 나오는 빠른 실패 경로가 있기 때문이다. 이 fast-fail 경로가 설계대로 동작하는지도 응답 시간 분포로 확인한다.

---
테스트 후 검증 쿼리는 두 가지다.

```sql
-- 발급 수량 정합성
SELECT ce.coupon_event_id, ce.issue_count, ce.issued_count,
       (SELECT COUNT(*)
        FROM user_coupons uc
        WHERE uc.coupon_event_id = ce.coupon_event_id)
FROM coupon_events ce
WHERE ce.coupon_event_id = {테스트 쿠폰 ID};

-- 중복 발급 여부 (있으면 안 됨)
SELECT user_id, coupon_event_id, COUNT(*)
FROM user_coupons
WHERE coupon_event_id = {테스트 쿠폰 ID}
GROUP BY user_id, coupon_event_id
HAVING COUNT(*) > 1;
```

## 시나리오 5: 결제 타임아웃 스케줄러 폭주 (배치 복구 정합성)

주문만 하고 결제를 안 하는 사용자는 항상 있다.

평소에는 드물게 발생하지만, **이벤트 시간대에 수백 명이 주문까지만 만들고 이탈**하면 10분 뒤 타임아웃 스케줄러가 한꺼번에 만료 처리를 돌린다.

이 시나리오의 목표는 **대량 타임아웃이 한 번에 터질 때 재고 복구가 정확히 되는가, 그리고 스케줄러가 버티는가**를 검증하는 것이다.

현재 구조는 주문 생성 시 Redis ZSET에 orderId를 `현재 시각 + 10분` 을 score로 저장해 두고, 스케줄러가 주기적으로 ZRANGEBYSCORE 로 만료된 주문을 꺼내 CANCELLED 로 전이하며 재고를 복구한다.

ZSET 조회 + 삭제는 Lua 스크립트로 원자 처리해 서버 여러 대가 돌아도 중복 처리가 생기지 않도록 막아둔 상태인데, **이게 실제 대량 부하에서도 깨지지 않는지**가 핵심 검증 포인트다.

흐름은 단순하지만 대기 시간이 있다.

먼저 500명이 동시에 주문 생성 API를 호출해 재고를 차감하고 Payment READY 를 만든다.

그리고 **아무도 결제를 하지 않는다.**

10분이 지나면 스케줄러가 발동하고, 이때부터 스케줄러의 처리 속도와 정합성을 관측한다.

검증 케이스는 네 가지다.

첫째, **차감된 재고 합 = 복구된 재고 합** 이어야 한다.

하나라도 누락되면 재고가 영영 잠긴 상태로 남아 실제 판매 가능한 수량이 계속 줄어드는 매출 손실이 발생한다.

둘째, **CANCELLED 로 전이된 주문 수 = 만료 대상 주문 수** 여야 한다.

셋째, **여러 서버가 동시에 돌아가도 같은 주문을 두 번 처리하지 않는다** — Lua 스크립트의 원자성이 깨지지 않는지 확인한다.

넷째, 스케줄러가 일괄 복구를 도는 동안 **다른 API(상품 조회, 신규 주문)의 응답 시간이 얼마나 영향을 받는가**를 관찰한다. 스케줄러가 커넥션 풀을 점유해 다른 트래픽까지 느려지면 구조적 개선이 필요하다는 신호다.

부하는 세 단계다.

기본 100명이 주문만 만들고 이탈 → 타임아웃 후 복구 정합성을 본다.

집중 500명이 같은 상품 옵션에 몰려 주문 후 이탈 → 대량 동일 옵션 재고 복구 시 deadlock 이나 락 대기가 발생하지 않는지 확인한다.

혼합 500명 타임아웃 복구 + 100명 신규 주문 동시 진행 → 스케줄러와 일반 트래픽이 경합할 때의 전염 여부를 본다.

측정 지표는 복구 소요 시간, 재고 정합성, 복구 중 일반 API 응답 시간 변화, 그리고 스케줄러 동작 중 발생한 예외 건수다.

```sql
-- 재고 복구 정합성 (초기 재고 == 만료 후 재고)
SELECT po.product_option_id, po.stock_quantity
FROM products_options po
WHERE po.product_option_id IN ({테스트 옵션 ID 목록});

-- 만료 주문 상태 검증
SELECT order_status, COUNT(*)
FROM orders
WHERE order_id IN ({테스트 주문 ID 목록})
GROUP BY order_status;
-- 기대: 전부 CANCELLED

-- Redis 타임아웃 키 잔존 여부 (남아있으면 Lua 원자성 깨짐)
-- Redis CLI: ZRANGEBYSCORE order:timeout 0 {현재시각 - 1분}
```

## 시나리오 6: 결제 콜백 멱등성 (중복 호출 방어)

토스페이먼츠 같은 PG 사는 네트워크 오류 시 **같은 paymentKey 로 콜백을 여러 번 보낸다.**

사용자가 결제를 1회 성공했는데 서버가 똑같은 승인 콜백을 2~3번 수신하면, 방어가 없으면 결제 승인이 중복 처리되고 재고가 이중 차감되고 포인트가 이중 적립된다.

이 시나리오의 목표는 **같은 paymentKey 로 콜백이 반복 도착해도 결제 승인·재고·포인트가 정확히 한 번만 반영되는지**를 증명하는 것이다.

현재 코드가 이 상황을 보장하는지 아직 실측으로 확인되지 않았고, 이 시나리오가 그 공백을 채운다.

흐름은 실패 상황을 재현하는 데 초점이 있다.

정상 결제 1건을 처음부터 끝까지 완료해 Payment 상태가 DONE 이 되도록 만든다.

이후 같은 paymentKey 와 orderId 로 `GET /api/v1/payments/success` 콜백을 **2~5회 반복 호출**한다.

서버는 이 반복 호출을 받아도:
- Payment 가 이미 DONE 이면 재승인 로직을 돌리지 않고 멱등 응답을 돌려줘야 한다
- 재고가 한 번 더 차감되면 안 된다
- PointHistory 에 같은 EARN 이 두 번 기록되면 안 된다
- Order 상태가 이미 PAID 이면 markPaid() 가 또 불리지 않아야 한다

검증 케이스는 세 가지다.

첫째, **n 번 호출했을 때 Payment 의 approved_at 이 한 번만 찍혔는지** 확인한다.

둘째, **PointHistory 에 같은 (userId, orderId, EARN) 레코드가 1건인지** 확인한다.

셋째, **재고 수량이 최초 차감 이후 추가로 변경되지 않았는지** 확인한다.

부하는 세 단계다.

기본 단일 결제를 2회 콜백 → 가장 단순한 멱등 검증.

동시 50명이 각자 자신의 결제를 만든 뒤 각각 3회씩 콜백 → 동시 멱등 경합.

스트레스 200명이 각 5회 콜백으로 총 1000 요청 → 중복 방어 레이어가 부하를 버티는지.

측정 지표는 멱등 준수율 (1회 효과 = 100% 기대), 중복 호출의 응답 시간 분포 (빠른 실패 경로가 있는지), 그리고 `PAYMENT_ALREADY_PROCESSED` 같은 의도된 거절과 진짜 에러의 구분이다.

```sql
-- Payment 상태 전이 추적 (approved_at 은 1회만 찍혀야 함)
SELECT payment_id, status, approved_at, updated_at
FROM payments
WHERE payment_id IN ({테스트 결제 ID 목록});

-- 동일 주문의 EARN 포인트가 2건 이상인지 (멱등 실패 탐지)
SELECT order_id, COUNT(*)
FROM point_histories
WHERE point_type = 'EARN'
GROUP BY order_id
HAVING COUNT(*) > 1;

-- 주문 수량 합 vs 차감된 재고 (이중 차감 탐지)
SELECT po.product_option_id, po.stock_quantity,
       (SELECT SUM(od.quantity)
        FROM order_details od
        WHERE od.product_option_id = po.product_option_id)
FROM products_options po
WHERE po.product_option_id IN ({테스트 옵션 ID 목록});
```

## 시나리오 7: DB 커넥션 풀 고갈 및 전염 효과

비관적 락은 **트랜잭션이 끝날 때까지 커넥션을 물고 있는 구조**다.

동시에 같은 상품 옵션에 주문이 몰리면 첫 번째 요청이 락을 쥐고 나머지는 대기 큐에 줄을 선다.

이때 대기 중인 요청도 **각자 커넥션 하나씩 점유한 상태**로 기다리기 때문에, 동시성이 올라가면 재고 락보다 **커넥션 풀이 먼저 바닥난다.**

이 시나리오의 목표는 **풀이 고갈된 순간 어떤 일이 벌어지는지 — 주문만 실패하는지, 상품 조회·로그인 같은 무관한 API까지 전염되는지 — 를 정확히 관찰하는 것**이다. 운영에서 알람 설정과 대응 플랜을 짤 때 이 숫자가 기준이 된다.

현재 HikariCP 풀 크기는 Spring Boot 기본값(`maximum-pool-size: 10`) 기준이고, 풀 고갈 시 `SQLTransientConnectionException: Connection is not available, request timed out after 30000ms` 가 발생할 수 있다.

이 예외가 주문에서만 발생하는지, 상품 조회·로그인에서도 동시에 터지는지가 전염 여부를 판가름한다.

흐름은 세 단계로 설계한다.

첫 단계는 **경합 상황 조성** — 재고 10개인 상품 옵션에 100명이 동시 주문을 건다. 이 상태에서 주문 대기 큐가 형성되고 커넥션 풀이 점유되기 시작한다.

두 번째 단계는 **무관한 API 동시 호출** — 같은 시점에 50명이 상품 목록 조회를 하고 20명이 로그인을 시도한다.

세 번째 단계는 **관측** — 각 API 의 응답 시간·에러율·응답 코드를 분리 집계한다.

검증 케이스는 네 가지다.

첫째, **커넥션 풀 사용률 100% 도달 시점** 에 주문 API 가 먼저 타임아웃이 나는가.

둘째, 풀이 고갈된 동안 **상품 조회 응답 시간이 평소 100ms 에서 얼마까지 늘어나는가** — 전염 효과의 크기.

셋째, 풀 대기 타임아웃(30초) 초과 시 **클라이언트에게 500 으로 떨어지는가, 아니면 다른 코드로 처리되는가** — 운영 알람 규칙 설계에 필요한 정보.

넷째, 경합이 풀린 뒤 **풀 사용률이 정상으로 돌아오는지** — 커넥션이 제대로 반환되지 않으면 장애가 장기화된다.

부하는 두 단계다.

압박 단계 — 100명 경합 주문 + 50명 상품 조회 동시 3분 → 전염 여부 정성 관찰.

극한 단계 — 300명 경합 주문 + 100명 상품 조회 + 50명 로그인 동시 5분 → 장애 시점의 실제 동작과 회복 시간 측정.

측정 지표는 **커넥션 풀 사용률 (HikariCP MBean), 각 API 별 P99 응답 시간, 타임아웃 발생 건수와 예외 타입, 그리고 경합이 풀린 뒤 풀 복귀까지 걸리는 시간**이다.

이 시나리오의 결과는 다음 중 한 가지 개선 방향으로 연결된다.

풀 크기 확대(임시 대응), HikariCP `connectionTimeout` 단축으로 빠른 실패 유도, 읽기 전용 API 를 별도 데이터소스로 분리(Bulkhead 패턴), 또는 비관적 락 자체를 Redis 분산락으로 전환해 **대기를 DB 밖으로 빼는 것**이다.

마지막 방향이 시리즈 3의 주제와 연결된다 — 이 시나리오에서 나온 고갈 숫자가 **분산락 전환 전 기준점** 이 된다.

```sql
-- 커넥션 풀 사용률은 애플리케이션 메트릭(HikariCP JMX / Actuator /actuator/metrics/hikaricp.connections.active)으로 확인

-- 경합 중 발생한 주문 상태 분포
SELECT order_status, COUNT(*)
FROM orders
WHERE created_at >= {테스트 시작 시각}
GROUP BY order_status;

-- 경합 이후 풀 복귀 확인 (활성 세션 수)
SHOW STATUS LIKE 'Threads_running';
SHOW STATUS LIKE 'Threads_connected';
```

## 시나리오 8: 복합 트래픽 시뮬레이션

앞의 시나리오들은 각 API를 고립시켜 한 가지 부하 패턴만 재현한다.

하지만 실제 프로덕션에서는 모든 API가 동시에 호출된다.

이 시나리오의 목표는 **읽기와 쓰기가 섞인 실제 사용 패턴을 재현해 시스템 전체의 균형 성능을 측정** 하는 것이다.


트래픽 비율은 커머스 도메인의 일반적 분포를 따라 구성했다. 상품 목록 조회가 45%로 가장 많고, 상품 단건 조회가 22%로 뒤를 잇는다.

구매 전환 영역에서 쿠폰 없는 주문이 10%, 쿠폰 사용 주문이 8%, 결제 승인이 10%를 차지한다. 선착순 쿠폰 발급은 평소에는 5%로 작지만 이벤트 오픈 시점에는 이 비율이 급증한다고 가정한다.

부하는 세 단계로 올린다. 일반 100명(5분)은 평시 트래픽을 재현하고, 피크 500명(5분)은 저녁 7~9시 같은 혼잡 시간대를 흉내낸다.

블랙프라이데이 1000명(10분)은 극단적 쇼핑 이벤트 상황을 가정한 스트레스 테스트다.

각 단계에서 어느 API가 먼저 한계를 드러내는지, 그리고 그 한계가 다른 API에 어떻게 영향을 미치는지를 관찰한다.

예를 들어 주문 API가 DB 커넥션 풀을 점유하면서 상품 조회까지 느려지는 "전염" 패턴이 나올 수 있는데, 이런 간접 영향은 단일 시나리오로는 관찰되지 않는다.

## 사전 준비

테스트를 돌리기 전에 다음 데이터를 준비해 둔다.

테스트용 유저 500명(test_user_1 ~ test_user_500), 상품 100개에 각 옵션 3개씩(재고는 옵션별로 1000개), 유저당 배송지 1개, 쿠폰 이벤트 몇 종(수량 100장 / 1000장). 쿠폰 사용 주문 시나리오를 위해서는 UserCoupon을 유저당 3장씩 AVAILABLE 상태로 사전 발급해 둬야 한다.

구체적으로 정액 할인 1장(3000원), 정률 할인 1장(10% · 최대 5000원), 최소주문금액 제한 1장(20000원 이상 시 5000원 할인)이다.
각 쿠폰 유형이 다른 할인 로직을 태우기 때문에 섞어서 부하를 걸어야 쿠폰 검증 오버헤드의 평균값이 현실적으로 나온다.

Locust 실행은 시나리오별로 분리된 파일로 돌린다.

상품 조회 hit 베이스라인은 `locustfile_product.py`, 상품 조회 cache miss cold-start 는 `locustfile_product_cache_miss.py`, 쿠폰 없는 주문은 `locustfile_order.py`, 쿠폰 사용 주문은 `locustfile_order_with_coupon.py`, 로그인 폭주는 `locustfile_login.py`, 선착순 쿠폰은 `locustfile_coupon.py`, 결제 타임아웃 스케줄러 검증은 `locustfile_order_timeout.py`, 결제 콜백 멱등성은 `locustfile_payment_idempotent.py`, DB 커넥션 풀 고갈은 `locustfile_pool_exhaustion.py`, 복합 시나리오는 `locustfile_mixed.py` 다.

cache miss 시나리오는 Redis 접근이 필요하므로 `pip install redis` 가 추가로 요구된다.

모두 `--host=http://localhost:8080` 로 로컬 서버를 가리킨다.

```bash
locust -f locustfile_product.py --host=http://localhost:8080
locust -f locustfile_product_cache_miss.py --host=http://localhost:8080
locust -f locustfile_order.py --host=http://localhost:8080
locust -f locustfile_order_with_coupon.py --host=http://localhost:8080
locust -f locustfile_login.py --host=http://localhost:8080
locust -f locustfile_coupon.py --host=http://localhost:8080
locust -f locustfile_order_timeout.py --host=http://localhost:8080
locust -f locustfile_payment_idempotent.py --host=http://localhost:8080
locust -f locustfile_pool_exhaustion.py --host=http://localhost:8080
locust -f locustfile_mixed.py --host=http://localhost:8080
```

## 성능 개선 로드맵

이 시나리오 세트는 **한 번 돌리고 끝나는 게 아니다.** 같은 시나리오를 여러 버전의 구조에 적용해 Before/After를 비교하는 것이 최종 목표다.

첫 번째 버전은 지금 구조, **비관적 락 기반**이다.

여기서 나오는 TPS와 정합성 결과가 이후 모든 비교의 기준점이다.

두 번째 버전은 **Redis 분산락**이다. `@DistributedLock` AOP가 이미 프로젝트에 구축돼 있어 적용 자체는 간단하고, 같은 시나리오를 돌렸을 때 TPS가 얼마나 올라가는지, DB 커넥션 풀 사용률이 얼마나 떨어지는지가 관전 포인트다.

세 번째 버전은 **Redis DECR 원자적 연산**이다.
락 자체를 없애고 원자 연산으로 재고/쿠폰을 차감하는 구조로 이론상 가장 빠르지만 정합성 보장 방식이 달라지므로 별도 검증이 필요하다.
이 세 버전의 숫자가 같은 표에 나란히 찍히면, "왜 이 기술을 선택했는가"라는 질문에 추측이 아닌 데이터로 답할 수 있다.

그 이후에는 DB 인덱스 추가나 HikariCP 풀 사이즈 튜닝 같은 파라미터 레벨 최적화가 남는다.
이런 튜닝은 구조적 변화보다 효과가 작지만, 이미 구조가 최적화된 상태에서는 마지막 1~2%를 짜내는 영역이 된다. 이것도 같은 시나리오로 Before/After를 찍어 정량 비교한다.

## 설계 원칙 요약

이 시나리오들을 설계하며 다섯 가지 원칙을 지켰다.

**TPS만 보지 말고 정합성을 검증 쿼리로 함께 본다.** 숫자가 커도 데이터가 망가지면 불합격이다.

**평균이 아닌 P95/P99를 본다.** 꼬리 지연이 실제 사용자 경험을 망친다.

**부하는 단계별로 올린다.** 한 번에 최대 부하를 던지면 어디서 터졌는지를 알 수 없다.

**의도된 실패와 진짜 에러를 구분한다.** SOLD_OUT이나 409는 에러가 아니라 비즈니스 로직 결과다.

**성능만큼 복원력을 검증한다.** 타임아웃 배치가 정합성을 지키는지, PG 중복 콜백을 멱등으로 막는지, 커넥션 풀이 고갈됐을 때 어디까지 전염되는지는 평시 TPS 못지않게 중요한 운영 지표다.

이 원칙이 지켜지면 측정 결과는 단순한 숫자가 아니라 **의사결정의 근거**가 된다. 다음 편에서는 실제로 이 시나리오를 돌려 나온 숫자를 분석한다.
