# 상품 조회 API 성능 테스트 가이드

> 대상 API: `GET /api/v1/products` (목록 조회, 비인증), `GET /api/v1/products/{productId}` (단건 조회, 비인증)
>
> 시나리오 문서: [성능테스트-시나리오.md](./성능테스트-시나리오.md) — 시나리오 1 참고

## 개요

상품 조회는 StyleHub 전체 트래픽의 절반 이상을 차지하는 읽기 부하의 대표 API다. 이 문서는 Locust 를 이용해 해당 API 의 실측 성능을 확인하는 전체 절차를 정리한다. 처음부터 끝까지 순서대로 따라가면 첫 측정값을 뽑을 수 있도록 구성했다.

### 전체 흐름

```
① Python + Locust 설치
② 테스트 데이터 준비 (상품 100개 이상)
③ locustfile_product.py 작성
④ Spring Boot 서버 실행
⑤ Locust 실행 → 웹 UI 접속
⑥ 부하 단계별로 진행 (Warm-up → Spike)
⑦ 결과 기록 및 해석
```

### 측정 목표 (시나리오 1 기준)

- 평균 응답 시간 < 100ms
- P95 < 300ms
- P99 < 500ms
- 에러율 < 0.1%
- TPS 는 단계별 최댓값을 기록해 분산락 전환 후 비교용 기준점으로 둔다

## 1. Python + Locust 설치

macOS 에는 Python 3 가 기본 내장되어 있다. 버전만 확인한다.

두 가지 방법이 있다.

**방법 A — Homebrew (macOS 권장)**

```bash
brew install locust

```

**방법 B — 가상환경 + pip**

```bash
python3 -m venv venv
source venv/bin/activate
pip install locust

```

Homebrew 로 설치한 경우 자체 Python 런타임을 쓰므로 이후 가상환경 활성화는 불필요하다.

## 2. 테스트 데이터 확인

커서 페이지네이션 성능을 제대로 측정하려면 상품이 **최소 100개 이상** 있어야 한다. 실제 프로덕션 수준 데이터에서 측정해야 의미 있는 숫자가 나오므로 권장은 10만건 이상이다.

### 2-1. 현재 데이터 수 확인

```bash

```

결과 예시:
```

3172205
```

### 2-2. 데이터가 부족할 때 시드 생성

100건 미만이면 아래 SQL 로 대량 삽입한다. (스토어 유저 `user_id = 1` 이 이미 있다고 가정)

```sql
INSERT INTO products (user_id, name, main_category, sub_category, description, price, image_url, created_at, updated_at)
SELECT 1,
       CONCAT('테스트상품-', n),
       'TOP',
       'T_SHIRT',
       'perf test',
       10000 + (n * 100),
       'https://placeholder/img.png',
       NOW(),
       NOW()
FROM (
    SELECT ROW_NUMBER() OVER () AS n
    FROM information_schema.tables
    LIMIT 200
) t;
```

MySQL 버전에 따라 서브쿼리 방식이 안 되면 Python 스크립트나 Spring `CommandLineRunner` 로 시드 로직을 구성해도 된다.

스토어 필터 테스트용 `storeId` 는 실제로 상품을 가진 유저여야 한다.


결과에서 나온 user_id 범위를 `locustfile_product.py` 의 `random.randint(1, 3)` 부분에 반영한다.

## 3. `locustfile_product.py` 작성

프로젝트 루트에 `performance/` 디렉토리를 만들고 그 안에 작성한다.

```bash
mkdir -p /Users/bwj/Desktop/stylehub/performance
```

### 3-1. 파일 위치

```
stylehub/
└── performance/
    └── locustfile_product.py
```

### 3-2. 파일 내용

```python
"""
시나리오 1: 상품 조회 (읽기 부하)

측정 목표
  - P95 < 300ms, P99 < 500ms, 에러율 < 0.1%
  - 커서 페이지네이션 + JOIN FETCH 의 실제 성능
  - 필터 조합(스토어/카테고리)에 따른 쿼리 플랜 변화 관찰

실행 방법
  # 웹 UI 모드 (부하 단계별로 수동 제어)
  locust -f performance/locustfile_product.py --host=http://localhost:8080
  → 브라우저 http://localhost:8089 접속

  # Headless 모드 (CSV 결과 저장 — Warm-up 예시)
  locust -f performance/locustfile_product.py --host=http://localhost:8080 \\
         --headless -u 10 -r 2 -t 30s \\
         --csv=performance/results/product_warmup
"""
import random
from locust import HttpUser, task, between


class ProductReadUser(HttpUser):
    # 가상 유저가 요청 간 대기하는 시간 (초). 실제 사용자의 클릭/스크롤 간격을 흉내낸다.
    wait_time = between(0.5, 2.0)

    # 각 가상 유저가 테스트 시작 시 1회만 수행한다.
    # 실제 DB 에 존재하는 productId 목록을 미리 확보해 이후 커서/상세 호출 시 재사용한다.
    def on_start(self):
        response = self.client.get("/api/v1/products?pageSize=50")
        if response.status_code == 200:
            items = response.json().get("items", [])
            self.product_ids = [item["productId"] for item in items]
        else:
            self.product_ids = []

    @task(5)   # 가중치 5: 가장 빈번한 호출 패턴
    def list_products_first_page(self):
        """첫 페이지 조회 (커서 없음)"""
        self.client.get("/api/v1/products", name="GET /products (first page)")

    @task(5)
    def list_products_next_page(self):
        """다음 페이지 조회 (커서 기반)"""
        if not self.product_ids:
            return
        cursor = random.choice(self.product_ids)
        self.client.get(
            f"/api/v1/products?cursor={cursor}",
            name="GET /products (next page)",
        )

    @task(2)
    def list_products_by_store(self):
        """스토어 필터 조회"""
        store_id = random.randint(1, 3)   # 실제 존재하는 store_id 범위로 조정
        self.client.get(
            f"/api/v1/products?storeId={store_id}",
            name="GET /products (by store)",
        )

    @task(2)
    def list_products_by_category(self):
        """카테고리 필터 조회 (대·소분류 조합)"""
        self.client.get(
            "/api/v1/products?mainCategory=TOP&subCategory=T_SHIRT",
            name="GET /products (by category)",
        )

    @task(3)
    def get_product_detail(self):
        """단건 상세 조회 (JOIN FETCH 성능)"""
        if not self.product_ids:
            return
        product_id = random.choice(self.product_ids)
        self.client.get(
            f"/api/v1/products/{product_id}",
            name="GET /products/{id}",
        )
```

### 3-3. 파일 설계 포인트

- **`@task(N)` 의 N 은 호출 비율 가중치**다. 목록 조회(5 + 5) : 단건 상세(3) : 필터(2+2) = 10 : 3 : 4 비율로 호출된다.
- **`name=` 파라미터** 로 Locust 통계에서 같은 패턴의 URL 을 하나로 그룹화한다. 예: `/products/1`, `/products/2` 가 모두 `GET /products/{id}` 로 묶여 통계 왜곡을 방지한다.
- **`on_start`** 에서 실제 DB 의 productId 를 미리 확보해 이후 커서·상세 호출에서 재사용한다. 존재하지 않는 ID 로 테스트하면 404 가 섞여 측정이 왜곡된다.
- **`wait_time = between(0.5, 2.0)`** — 실제 사용자의 클릭 간격을 흉내낸다. 너무 짧으면 봇 부하가 되어 비현실적인 결과가 나온다.

## 6. 부하 단계별로 진행

웹 UI 에서 세 개 필드를 입력하는 화면이 뜬다.

| 필드 | 의미 |
|---|---|
| **Number of users** | 동시 접속 유저 수 (목표 피크) |
| **Spawn rate** | 초당 몇 명씩 증가시킬지 |
| **Host** | 이미 CLI 에서 지정했으면 비워둬도 됨 |

### 단계별 설정 (시나리오 1 기준)

| 단계 | Users | Spawn rate | 지속 시간 | 목적 |
|---|---|---|---|---|
| Warm-up | 10 | 2 | 30초 | JVM JIT + 커넥션 풀 예열 |
| Light | 50 | 10 | 2분 | 기본 성능 확인 |
| Medium | 200 | 20 | 3분 | 일반 피크 시뮬레이션 |
| Heavy | 500 | 50 | 5분 | 한계점 탐색 |
| Spike | 1000 | 100 | 1분 | 급증 상황 |

**한 단계씩 끝내고 Reset → 다음 단계** 로 진행한다. 한 번에 Spike 까지 올리면 어느 단계에서 터졌는지 알 수 없다. 단계별 응답 시간 변화를 관찰해야 병목이 어디서 나타나는지 추정할 수 있다.

## 7. 결과 해석

웹 UI 화면 상단의 탭을 순서대로 본다.

### 7-1. Statistics 탭

URL 패턴별 요약 통계:

- **# Requests** — 총 호출 수
- **# Fails** — 실패 수 (0.1% 이하여야 합격)
- **Average** — 평균 응답 시간
- **Min / Max** — 최소/최대 응답 시간
- **Median** — 50 percentile
- **Current RPS** — 현재 초당 요청 수 (TPS)

### 7-2. Charts 탭

시간축 그래프:

- **Total Requests per Second** — TPS 추이. 유저 수 증가에 비례해 올라가는지 본다.
- **Response Times (ms)** — 평균 / 95% / 99% 꼬리 지연.
- **Number of Users** — 유저 증가 곡선.

### 7-3. Failures 탭

에러 상세. 이상적으로 0 이 맞다. 실패가 있다면 에러 메시지를 확인하고 서버 로그와 대조한다.

### 7-4. 꼭 봐야 할 포인트

1. **RPS 가 유저 수에 비례해 증가하는가**
   - 비례하면: 아직 병목 없음
   - 포화되면(유저 올려도 TPS 가 제자리): **병목 구간 도달**. 이 지점을 메모한다.
2. **P95 / P99 가 단계별로 얼마나 튀는가**
   - Light 50ms → Heavy 500ms 로 10배로 튀면 병목 징후.
   - 평균이 괜찮아도 P99 가 심하게 튀면 꼬리 지연 문제.
3. **에러율**
   - 0.1% 이하가 목표. 커넥션 풀 고갈이 시작되면 급증한다.

## 8. 결과 기록 (중요)

**블로그 시리즈 2 (실측 결과 분석) 에 쓸 자료를 지금부터 쌓아둔다.** 단계별로 아래 표를 채운다.

| 단계 | Users | 실측 TPS | 평균 | P95 | P99 | 에러율 |
|---|---|---|---|---|---|---|
| Warm-up | 10 | | | | | |
| Light | 50 | | | | | |
| Medium | 200 | | | | | |
| Heavy | 500 | | | | | |
| Spike | 1000 | | | | | |

숫자뿐 아니라 **"예상과 달랐던 지점"** 도 같이 메모한다. 예를 들어:

> Heavy 단계에서 P99 가 갑자기 3초로 튐. 커넥션 풀 사용률이 90% 를 찍었다. JOIN FETCH 가 무거운지 아니면 락 대기인지 추정.

이런 관찰이 블로그의 핵심 콘텐츠가 된다.

### 8-1. CSV export

Locust 에는 CSV 저장 기능이 있다. 단계별로 결과 파일을 남기면 나중에 비교가 쉽다.

```bash
mkdir -p performance/results

locust -f performance/locustfile_product.py --host=http://localhost:8080 \
       --headless -u 50 -r 10 -t 2m \
       --csv=performance/results/product_light
```

`--headless` 모드는 웹 UI 없이 CLI 에서 바로 실행되고, `product_light_stats.csv`, `product_light_stats_history.csv`, `product_light_failures.csv` 등의 파일이 생성된다.

## 9. 대용량 데이터에서 생기는 고려사항

상품이 프로덕션 수준(수백만 건)으로 있는 상태에서 측정한다면 첫 테스트에서 아래가 드러날 가능성이 높다.

1. **커서 필드 인덱스 부재** — `productId` 에 인덱스가 없으면 full scan. 쿼리 플랜(`EXPLAIN`) 으로 확인.
2. **첫 페이지 조회가 무거운 경우** — `ORDER BY` 가 인덱스를 안 타거나 정렬 버퍼가 부족할 수 있다.
3. **JOIN FETCH 비용** — Product + User + Options 를 한 번에 가져오는 구조의 실제 비용.
4. **커넥션 풀 크기** — Spring Boot 기본 10 개. 동시 유저가 많아지면 여기서 먼저 병목.

이것들이 바로 **첫 측정으로 드러날 병목 후보** 다. 측정 후 원인 분석과 개선을 병행한다.
