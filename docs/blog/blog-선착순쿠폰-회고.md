# 선착순 쿠폰 동시성 — 통념을 따라갔다가, 측정에 한 번 더 막혀서 돌아온 길

> StyleHub에서 선착순 쿠폰 발급의 동시성을 처리하면서, "비관적 락 → 분산 락"이라는 교과서적 흐름을 따라갔다가 측정에서 보기 좋게 반박당하고, 결국 Redis DECR + Lua로 도달하기까지의 과정을 정리한 글이다. 결론만 보면 "선착순은 Redis 원자 연산"이라는 흔한 답이지만, 나는 그 답을 알고 시작한 게 아니라 두 번 틀리고 나서 도착했다. 그 두 번의 오답이 이 글의 핵심이다.

## 시작할 때의 생각 — "이건 비관적 락이지"

선착순 쿠폰은 "동시성 제어가 필요하다"는 건 너무 당연했다. 100장 한정인데 500명이 동시에 달려들면, 막지 않으면 100장을 넘겨 발급된다. 문제는 "필요하다"가 아니라 **"무엇으로 막느냐"**였다.

먼저 재고 차감 때 했던 atomic UPDATE를 떠올렸는데, 코드를 보니 그게 안 됐다. 쿠폰 발급은 한 줄 SQL로 환원되지 않았다.

```java
@Transactional
public void issueCoupon(User user, Long couponEventId) {
    CouponEvent event = findById(couponEventId);          // 1. 조회
    couponValidator.validateIssuable(event);              // 2. 활성/시작/만료 검증
    checkDuplicateIssue(user.getUserId(), couponEventId); // 3. 중복 발급 검증
    event.increaseIssuedCount();                          // 4. 카운터 증가 + SOLD_OUT 검증
    userCouponRepository.save(UserCoupon.create(...));    // 5. INSERT
}
```

검증 + 중복 체크 + 카운터 증가 + INSERT, 이 다섯 단계가 **묶여서 원자적으로** 돌아야 했다. 재고처럼 `UPDATE ... WHERE stock >= 1` 한 줄로 끝낼 수가 없었다. 그래서 "이건 복합 트랜잭션이니까 락이 필요하다"고 분류했고, 가장 확실한 비관적 락으로 시작했다.

지금 돌아보면, **이 첫 분류("락이 필요한 영역")가 사실은 부정확했다.** 하지만 그땐 몰랐다. 그걸 알게 된 건 한참 뒤다.

---

## 1차 — 비관적 락. 정합성은 완벽했다

`SELECT ... FOR UPDATE`로 같은 `CouponEvent` row에 대한 동시 접근을 직렬화했다.

```java
CouponEvent event = couponEventRepository.findByIdWithLock(couponEventId);  // FOR UPDATE
```

500명이 100장에 달려드는 시나리오로 측정했다(누적 296,178 reqs).

| 지표 | 값 |
|---|---|
| Fails | **0** |
| Avg | 459 ms |
| Max | 3,717 ms |
| 안정 RPS | ~630 |
| 정합성 | **정확히 100 발급, 중복 0** |

정합성은 완벽했다. 500명이 296K번 시도해서 정확히 100명만 받았다. 그런데 숫자를 보다가 두 군데가 걸렸다.

하나는 **Avg 459ms**. 발급 한 건이 보통 수십 ms인 걸 생각하면 수십 배다. 다른 하나는 **Max 3.7초**. 락 큐가 길어지면 꼬리 지연이 폭증했다. 그리고 더 아까웠던 건, 이미 마감(SOLD_OUT)이라 바로 거절돼야 할 요청도 `SELECT FOR UPDATE`부터 잡고 줄을 서야 했다는 점이다. 빨리 실패해야 할 요청까지 락 큐에 갇히는 구조였다.

여기서 통념대로 다음 수순을 밟았다. "DB 락이 부담되니, 락 대기를 Redis로 옮기는 분산 락이 더 나을 것이다." 면접에서도 교과서에서도 블로그에서도 다들 그렇게 말하니까. `@DistributedLock` 인프라도 이미 만들어둔 상태라 적용만 하면 됐다.

## 2차 — 분산 락. 예상이 정확히 반대로 나왔다

가설은 명확했다. "분산 락은 락 대기를 Redis에서 처리하니 DB 커넥션을 안 물고 있다. 더 빠를 것이다." SETNX + 50ms 폴링 방식으로 트랜잭션 바깥에서 락을 잡게 했다.

```java
@DistributedLock(key = "'coupon:' + #couponEventId", waitMs=5000, leaseMs=3000)
public void issueCoupon(Long userId, Long couponEventId) { ... }
```

같은 부하로 측정했는데, 결과를 보고 좀 당황했다.

| 지표 | 비관적 락 | 분산 락 | 변화 |
|---|---|---|---|
| RPS | 630 | **190** | 3.3배 느림 |
| Avg | 459 ms | **2,084 ms** | 4.5배 느림 |
| 5xx (락 timeout) | 0 | **24.7%** | — |

**모든 차원에서 더 나빴다.** 게다가 24.7%가 5xx였다 — 5초 안에 락을 한 번도 못 받고 거절당한 사용자들이다. "더 나을 것"이라던 가설이 정확히 반대로 나왔다.

원인을 추적하다가, `@DistributedLock`이라는 깔끔한 어노테이션 뒤에 숨어 있던 걸 봤다.

| | DB 비관적 락 | SETNX 폴링 분산 락 |
|---|---|---|
| 큐잉 위치 | DB 커널 | 애플리케이션 스레드 |
| 큐잉 방식 | FIFO 자동 | 50ms 간격 능동 폴링 |
| Fairness | 보장됨 | **보장 안 됨 (운에 따라)** |

DB 비관적 락은 커널 레벨에서 FIFO로 줄을 세워준다. 그런데 내가 만든 SETNX 폴링은 그 FIFO 큐를 **"50ms마다 다시 찔러보는 능동 경쟁"**으로 대체한 거였다. 운 나쁜 요청은 50ms마다 찔러봐도 계속 남이 선점해서, 5초가 다 가도록 한 번도 락을 못 받고 timeout이 났다. 추상화가 그 안의 fairness 문제를 가리고 있었던 거다.

여기서 한 가지를 조심했다. "분산 락은 별로다"라고 결론 내리고 싶었지만, **이건 단일 머신 측정이었다.** 분산 락의 진짜 명분은 "다중 인스턴스에서 DB 커넥션 보호"인데, 그건 다중 인스턴스로 재봐야만 드러난다. 단일 환경 결과로 일반화하는 게 더 위험하다고 봐서, 폐기 대신 **다중 인스턴스 환경을 만들어 재측정**하기로 했다.

## 곁다리에서 터진 것 — 다중 인스턴스로 갔더니 401이 쏟아졌다

같은 머신에 JVM 4개(8080~8083)를 띄우고 nginx로 로드밸런싱해서 다중 인스턴스를 흉내 냈다. 분산 락을 다시 측정했는데, 이번엔 전혀 예상 못 한 게 터졌다.

| 지표 | 값 |
|---|---|
| Fails | **72,130 (85.5%)** |
| 에러 종류 | **status=401 → 99.97%** |

분산 락 timeout이 아니라 **대부분이 401 UNAUTHORIZED**였다. 락 비교는 시작도 못 했다. 추적해보니 원인은 동시성이 아니라 세션이었다.

```
8080에 로그인 → 쿠키 받음 → Tomcat 메모리에 세션 저장
다음 요청 → nginx가 8081로 라우팅 → 8081 메모리엔 세션 없음 → 401
```

Tomcat 메모리 세션은 다중 인스턴스에서 동작하지 않는다. 한 서버에 로그인했는데 다음 요청이 다른 서버로 가면, 그 서버는 나를 모른다. 락을 비교하려다 **대용량 서버라면 당연히 갖춰야 할 아키텍처 요건 하나가 빠져 있다는 걸** 측정의 부산물로 발견한 거다.

이건 측정을 위해서가 아니라 시스템 자체를 위해 고쳐야 했다. 마침 Redis 인프라가 이미 있어서, Spring Session으로 세션을 Redis에 두는 건 의존성 한 줄, 어노테이션 하나로 끝났다.

```java
@EnableRedisHttpSession  // 이거 빠뜨리면 동작 안 함 (첫 시도 때 함정)
@SpringBootApplication
public class StylehubApplication { ... }
```

세션을 고치고 4셀 매트릭스를 채웠다.

| 환경 | 비관적 락 | 분산 락 (SETNX 폴링) |
|---|---|---|
| 단일 인스턴스 | RPS **630** / 0 fails | RPS 190 / 24.7% fails |
| 다중 인스턴스 + Spring Session | RPS **526** / 0.04% fails | RPS 195 / 28.4% fails |

**네 칸 전부 비관적 락이 이겼다.** "다중 인스턴스로 가면 분산 락이 빛난다"던 가설마저 정량적으로 반박됐다. 다중 환경에서도 분산 락은 195 RPS 천장에 막혔다 — Redis 단일 키에 대한 SETNX 폴링이 결국 한계였다.

### 배포하다 정합성이 깨진 사건

이 측정 중에 의도치 않게 무서운 걸 봤다. 4개 인스턴스 중 8080만 옛날 jar(분산 락 코드)로 돌고 있던 시점이었는데, 한도 100짜리 쿠폰이 **500명 모두에게** 발급됐다. 비관적 락 시리즈 통틀어 처음 난 정합성 깨짐이었다.

원인은 이거였다. 옛 8080은 분산 락을 쓰니 DB 락을 안 잡는다. 그래서 비관적 락 인스턴스의 트랜잭션이 끝나기 전에 같은 row를 그냥 SELECT로 읽었고, REPEATABLE READ라 블록되지도 않아서 "아직 안 찼네" 하고 통과해버렸다. Lost Update였다.

여기서 배운 건, **락은 참여하는 모든 인스턴스가 같은 메커니즘을 써야만 보장된다**는 점이었다. 락 방식을 바꾸는 배포는 rolling deploy로 한 대씩 교체하면 안 되고, 전체를 동시에 전환하거나 두 방식이 호환되는 중간 단계를 거쳐야 한다. 동시성 도구 비교와는 별개로, 운영에서 두고두고 새겨둘 사건이었다.

## 멈춰서 다시 던진 질문 — "이거, 락이 정말 필요한가?"

여기까지 결론은 "모든 환경에서 비관적 락이 낫다"였다. 그런데 이 결론을 받아들이기 직전에 멈췄다. 통념(분산 락이 다음 단계)과 정반대 결과가 나왔다는 건, 둘 중 하나라는 뜻이었다.

1. 통념이 (이 영역에선) 틀렸다
2. 내가 측정한 게 통념의 대표가 아니다 (직접 만든 SETNX 폴링은 분산 락의 한 변종일 뿐, Redisson 같은 성숙한 구현은 다를 수 있다)

그러다 더 근본적인 질문이 떠올랐다. **"애초에 이 영역에 락이 필요한가?"**

처음에 나는 "복합 트랜잭션이니 락이 필요하다"고 분류했다. 그런데 선착순의 본질을 다시 보니, 결국 **"한도 100을 넘지 않게 카운터를 하나씩 깎는 것"**이었다. 카운터 차감. 이건 재고 차감과 본질이 같았다 — 락으로 직렬화할 게 아니라, 그 자체로 원자적인 연산으로 풀 수 있는 일이었다.

Redis가 떠올랐다. Redis는 단일 스레드라 명령이 순서대로 처리된다. 그래서 `DECR`은 두 클라이언트가 동시에 호출해도 Redis 안에서 순서가 정해지므로, **락이 없어도 race가 일어날 수가 없다.** 카카오·배민·쿠팡이 선착순에 Redis 원자 연산을 쓰는 이유가 이거였다.

그러면 복합 단계(중복 검증 + 카운터 차감 + 발급 기록)는? 그건 Lua 스크립트로 묶으면 됐다. Redis는 Lua 실행 중 다른 명령이 못 끼어드니, 여러 단계를 한 번의 atomic 호출로 만들 수 있었다. **"락이 필요한 영역"이라던 처음의 분류 자체가 틀렸던 거다.** 락 없이 푸는 길이 있었다.

## 3차 — Redis DECR + Lua

```lua
-- 중복 발급이면 즉시 거절
if redis.call('SISMEMBER', issuedSetKey, userId) == 1 then
    return -2  -- ALREADY_ISSUED
end
-- 카운터 lazy init
if redis.call('EXISTS', counterKey) == 0 then
    redis.call('SET', counterKey, maxCount)
end
-- 차감, 음수면 즉시 복구하고 마감 처리
local remaining = redis.call('DECR', counterKey)
if remaining < 0 then
    redis.call('INCR', counterKey)
    return -1  -- SOLD_OUT
end
redis.call('SADD', issuedSetKey, userId)
return remaining
```

설계에서 신경 쓴 지점들:

| 결정 | 이유 |
|---|---|
| 락 제거 | Redis가 단일 신뢰원 — DB 락이 필요 없어짐 |
| Lua 단일 atomic | 중복 검증 + DECR + SADD를 Redis 한 호출로 묶어 race 자체를 제거 |
| 음수면 INCR back | DECR이 음수를 반환하면 즉시 되돌려 카운터 정확성 유지 |
| DB는 기록만 | UserCoupon INSERT만 담당, 동기화 책임은 안 짐 |

측정 결과는 그동안 막혔던 게 풀리는 느낌이었다.

| 메커니즘 | 단일 | 다중 | 5xx | 정합성 |
|---|---|---|---|---|
| 비관적 락 | RPS 630 / 459ms | RPS 526 / 490ms | 0 / 0.04% | ✅ |
| 분산 락 (SETNX 폴링) | RPS 190 / 2,084ms | RPS 195 / 2,168ms | 24.7% / 28.4% | ✅ |
| **Redis DECR + Lua** | — | **RPS 640+ / 402ms** | **0** | **✅** |

RPS는 비관적 락보다 22%, 분산 락보다 228% 높았고, 5xx는 0이었다. **5xx가 0인 게 당연한 게, 락이 없으니 락 timeout이라는 개념 자체가 없었다.** 정합성도 100%.

세 도구의 차이를 정리하면 이렇게 됐다.

| 메커니즘 | 경쟁을 어떻게 다루나 | 비용의 출처 |
|---|---|---|
| 비관적 락 | DB 락 큐로 직렬화 | 트랜잭션 길이만큼 락 점유 |
| 분산 락 (SETNX 폴링) | 앱이 폴링으로 직렬화 | 폴링 간격(50ms) + fairness 손실 |
| **Redis DECR + Lua** | **경쟁 자체를 제거** | DECR 단일 호출 (~ms) |

비관적 락과 분산 락은 둘 다 "경쟁하는 요청들을 어떻게 줄 세울까"의 문제였다. Redis DECR은 줄 세우는 방식을 바꾼 게 아니라, **줄을 설 필요 자체를 없앤** 거였다. 이게 통념을 뒤집은 핵심이었다 — "락을 어디서 잡을까"를 고민하는 것과 "락이 정말 필요한가"를 묻는 건 차원이 다른 질문이었다.

### 한 가지 더 — DB INSERT를 응답에서 떼어냈다

Redis로 발급 여부가 정해지고 나면, DB의 UserCoupon INSERT는 사용자 응답을 붙잡고 있을 이유가 없었다. 그래서 이벤트 + `@Async`로 백그라운드에 넘겼다.

```java
public void issueCoupon(User user, Long couponEventId) {
    // ... Lua atomic으로 발급 확정
    eventPublisher.publishEvent(new CouponIssuedEvent(...));  // 비동기
}

@Async("couponInsertExecutor")
@EventListener
public void handleCouponIssued(CouponIssuedEvent event) {
    userCouponRepository.save(UserCoupon.create(...));  // 백그라운드
}
```

솔직히 단일 머신 측정에선 RPS가 크게 오르진 않았다. DB INSERT가 진짜 병목은 아니었으니까. 그래도 채택한 이유는, 피크 트래픽을 흡수하고 DB 자원을 응답 경로에서 분리하는 가치 + "Redis가 신뢰원, DB는 기록"이라는 구조가 깔끔해서였다. 측정 수치만으로 정당화되진 않았지만, 대용량을 가정하면 맞는 방향이라고 판단했다.

## 솔직하게 — 이 결론의 한계

이 글의 결론은 "모든 환경에서 Redis DECR이 답"이 아니다. **이번 측정 환경에서의 답**이다. 안 본 것들을 분명히 해둬야 결론이 정직해진다.

| 측정한 것 | 측정 안 한 것 |
|---|---|
| RPS / 응답시간 / 5xx | 수십 인스턴스 수평 확장 |
| 정합성 invariant | Redis 장애 시 내성 (chaos test) |
| 4셀 락 비교 | Redisson 같은 성숙한 분산 락 |
| 5가지 부하 패턴 | Redis Cluster 환경 |

특히 "비관적 락이 분산 락보다 빠르다"는 건 **단일 머신 + 내가 직접 만든 SETNX 폴링** 환경의 결과다. Redisson(pub/sub 기반 fair lock)으로 바꾸면 fairness가 보장돼서 결과가 달라질 수 있다. 분산 락이 진짜 빛나는 자리(대규모 다중 머신 + DB 자원 보호)도 따로 측정해봐야 한다. 그래서 정직한 결론은 "현재 환경(단일~수 인스턴스)에선 Redis DECR이 답이고, 더 큰 환경으로 가면 재측정이 필요하다" 정도다.

## 돌아보며

이 작업에서 내가 제일 의미 있게 보는 건, 도달한 답(Redis DECR)이 아니라 **거기까지 두 번 틀린 과정**이다.

- 비관적 락으로 시작했다. 정합성은 완벽했지만 Avg 459ms, 마감 요청도 락 큐에 갇혔다.
- 통념대로 분산 락으로 갔는데, 예상과 정반대로 모든 차원에서 더 나빴다(RPS 1/3, 5xx 24.7%). SETNX 폴링의 fairness 문제가 어노테이션 뒤에 숨어 있었다.
- 다중 인스턴스로 재측정하다 401 폭탄을 만나, 세션을 Redis로 옮겨야 한다는 걸 곁다리로 발견했다.
- 배포 중 락 방식이 섞여 정합성이 깨지는 것도 봤다. 락은 모든 인스턴스가 같은 방식을 써야 한다는 걸 사고로 배웠다.
- 그러다 멈춰서 "이거 락이 필요한가?"를 다시 물었고, 선착순 카운터는 락이 아니라 Redis 원자 연산으로 푸는 영역이라는 걸 깨달았다.
- Redis DECR + Lua로 모든 차원에서 우월한 결과를 얻었고, 안 본 영역은 한계로 명시했다.

통념(비관적 락 → 분산 락)을 그냥 따랐다면, 더 나쁜 분산 락이 운영에 들어갔을 거고, Redis DECR이라는 답은 통념의 시야 밖이라 영영 못 찾았을 거다. 동시성에 일반해는 없고, 영역의 본질에 맞는 도구를 매번 다시 물어야 한다는 걸 — 두 번 틀려보고 나서야 몸으로 알았다. 그 두 번이 아깝지 않았다.
