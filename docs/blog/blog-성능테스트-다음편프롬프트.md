# 성능 테스트 시리즈 — 다음 편 작성 프롬프트

시리즈 1(시나리오 설계)은 `blog-성능테스트시나리오설계.md` 에 완료 (서술형/문단 중심).
다음 편을 쓸 때 이 파일의 프롬프트를 그대로 Claude Code에 붙여넣으면 된다.

---

## 공통 컨텍스트 (항상 프롬프트 앞에 포함)

```
StyleHub 프로젝트(대용량 트래픽 커머스 서버) 블로그 글을 이어서 쓴다.

참고 파일:
- blog-성능테스트시나리오설계.md — 시리즈 1편 (톤/구조 기준점)
- blog-시리즈3-동시성제어.md — 기존 블로그 형식 참고
- docs/성능테스트-시나리오.md — 시나리오 정의 문서

스타일 조건 (매우 중요):
- 서술형 문단 중심. 표/불릿을 최소화하고 문장으로 풀어 쓸 것.
- 필요한 경우에만 표·불릿·ASCII 다이어그램 사용 (한 섹션에 하나 이하).
- 문단당 2~4문장, 호흡 있게. 문단 간 접속어로 흐름 잇기.
- "~한다, ~다, ~했다" 단정형 반말체.
- 구조: ## 들어가며 → ## 1. ~ ## N. (각 섹션 제목은 한 줄 주장문) → ## 마치며.
- 각 섹션은 "요약 설명 → 왜 그렇게 했는가 → 무엇을 증명/발견했는가" 순.
- "정리된 자료"가 아니라 "누군가에게 설명하는 글"처럼 읽혀야 함.

면접관 어필 포인트 (반드시 녹일 것):
- 숫자/근거로 말하기 (추측 금지).
- 의사결정 과정이 드러나야 함 (왜 이 선택을 했는가).
- 시행착오/예상과 다름 섹션을 반드시 포함.
- "감으로 결정 안 했다"가 톤에서 드러나야 함.
- 대용량 트래픽 관점 유지 (TPS, 정합성, 꼬리 지연).
```

## 시리즈 2 프롬프트 — 실측 결과 분석

**사전 준비**: Locust 실측 완료 후에만 쓸 수 있음. 아래 데이터를 먼저 수집.

### 수집할 데이터 체크리스트

```
1. 측정 환경
   - CPU / RAM / JVM heap
   - MySQL 버전 / 설정
   - Redis 버전
   - 네트워크 (로컬 / 도커 / 클라우드)
   - HikariCP 풀 사이즈

2. 시나리오 1 (상품 조회) — 각 단계(10/50/200/500/1000명)별
   - TPS, 평균/P95/P99 응답 시간
   - 에러율
   - 병목 지점 추정 (DB/JPA/직렬화)

3. 시나리오 2 (주문→결제, 쿠폰 없음)
   - 단계별 TPS, 응답 시간
   - 재고 정합성 쿼리 결과 (차감 수량 == 주문 수량 합?)
   - 락 대기 시간 분포
   - DB 커넥션 풀 사용률 추이

4. 시나리오 2-2 (쿠폰 사용 주문) — 쿠폰 로직 구현 후에만
   - 쿠폰 검증 오버헤드 숫자 (있음 vs 없음 평균 응답 차)
   - UserCoupon 상태 전이 정합성
   - 결제 실패 시 쿠폰 복구율

5. 시나리오 3 (선착순 쿠폰)
   - 50/200/500/1000명 각 단계 TPS
   - 성공/실패 비율 (SOLD_OUT vs 진짜 에러)
   - 중복 발급 쿼리 결과 (0건이어야 함)
   - P99, 에러율

6. 예상과 달랐던 지점 (가장 중요)
   - 예상보다 느렸던 API
   - 예상보다 빨랐던 API
   - 예상치 못한 에러
   - 병목이 예상한 곳이 아닌 다른 곳이었던 케이스
```

### 프롬프트 (실측 후 이걸 복사해서 사용)

```
[위 공통 컨텍스트 붙여넣기]

[성능 테스트 시리즈 2] 실측 — 비관적 락의 한계를 숫자로 확인하다

서술형 문단 중심으로 작성. 표는 Before/After 비교 딱 하나만 쓰고, 나머지는 문장으로 풀 것.

들어가며:
- 시리즈 1에서 "아직 답을 모르는 질문들"로 남겼던 것 중 무엇이 답이 되고, 무엇은 새 질문이 됐는지
- 실측을 시작하면서 가장 궁금했던 한 가지 질문 (예: 비관적 락의 진짜 한계는 어디인가)

본문:
1. 측정 환경 — 어떤 조건에서 뽑은 숫자인지 (한 문단, 담백하게)
2. 상품 조회의 결과 — 목표 달성 여부와 병목 (문단 중심, 숫자는 인라인으로)
3. 주문 → 결제의 결과 — 비관적 락이 몇 명부터 한계를 보였는지
4. 쿠폰 사용 주문의 결과 — 오버헤드 숫자가 의미하는 것 (구현 후에만)
5. 선착순 쿠폰의 결과 — 정합성은 지켰는가, TPS는 어디가 한계였는가
6. 병목 분석 — 왜 이 숫자가 나왔나 (DB 커넥션 풀 / 락 대기 / 네트워크 I/O 중 무엇이 주범)
7. 예상 대비 차이 — 솔직하게 "예상은 X, 실제는 Y, 왜 다르게 나왔는지"
8. 다음 수순 — 이 병목을 어떻게 풀 것인가 (시리즈 3 예고)

마치며:
- "숫자를 본 후에야 의사결정이 가능하다"는 교훈
- 측정 없이 최적화부터 시작했다면 엉뚱한 곳을 고쳤을 거라는 구체적 사례

포함할 실제 수치:
[여기에 위 수집 데이터 붙여넣기]

비교가 필요한 지점은 딱 한 표로 (예: 단계별 TPS와 P99):
| 동시 유저 | 시나리오 2 TPS | 시나리오 3 TPS | 시나리오 1 P99 |
|---|---|---|---|
...

파일명: blog-성능테스트-시리즈2-실측결과.md
```

## 시리즈 3 프롬프트 — 비관적 락 → Redis 분산락 전환

**사전 준비**: 시리즈 2 실측 완료 + Redis 분산락 적용 + 재측정 완료.

### 수집할 데이터 체크리스트

```
1. 전환 동기 — 시리즈 2에서 확인한 병목
   - DB 커넥션 풀 고갈 여부
   - 락 대기 시간이 TPS에 미친 영향 (정량화)

2. 적용 방식
   - @DistributedLock AOP 적용한 메서드 목록
   - SpEL 락 키 설계 (예: stock:{optionId}, coupon:{eventId})
   - leaseTime 설정값 + 선택 근거
   - 폴링 간격 (50ms 등) + 선택 근거
   - UUID value로 자기 락만 해제한 이유

3. 전환하면서 만난 문제
   - Redis 장애 시 폴백 전략 (있는가 / 없다면 왜)
   - leaseTime이 너무 짧아서 생긴 케이스
   - leaseTime이 너무 길어서 생긴 케이스
   - 네트워크 레이턴시가 끼어든 케이스
   - 기존 코드에서 바꿔야 했던 곳 (트랜잭션 경계, 예외 처리 등)

4. Before/After 실측 비교
   - 주문: TPS (비관적 락 vs 분산락)
   - 쿠폰 발급: TPS (비관적 락 vs 분산락)
   - 응답 시간 P95/P99 변화
   - DB 커넥션 풀 사용률 변화
   - 에러율 변화

5. 예상과 달랐던 지점
   - 분산락이 비관적 락보다 느렸던 케이스가 있었는가
   - 기대보다 덜 개선된 부분
   - 예상치 못한 Redis 부하

6. 다음 단계 평가
   - Redis DECR 원자적 연산으로 갈 가치가 있는가
   - 추가로 튜닝해야 할 HikariCP / Redis 파라미터
```

### 프롬프트 (실측 후 이걸 복사해서 사용)

```
[위 공통 컨텍스트 붙여넣기]

[성능 테스트 시리즈 3] 비관적 락에서 Redis 분산락으로 — 숫자로 증명한 전환기

서술형 문단 중심. 개선율을 보여주는 Before/After 비교 표 딱 하나만 쓰고, 나머지는 문단으로 풀 것. 코드 블록은 @DistributedLock 적용 전/후 하나씩이면 충분.

들어가며:
- 시리즈 2에서 발견한 병목을 한 줄로 요약
- "분산락으로 바꾸면 되지 않을까?"라는 가설
- 하지만 가설은 가설일 뿐, 숫자로 확인해야 한다는 태도

본문:
1. 왜 분산락인가 — 비관적 락의 구조적 한계를 문단으로 설명
   - DB 커넥션을 점유한 채 기다리는 구조의 문제
   - 시리즈 2에서 나온 실제 병목 수치를 근거로
2. 이미 있던 @DistributedLock 인프라 — SpEL, UUID, 폴링 간격의 의미를 한 문단씩
3. 주문 API에 분산락 적용 — 코드 변경 전/후 간단히, leaseTime 근거를 문단으로
4. 쿠폰 발급 API에 분산락 적용 — 선착순 특유의 고려점, 이중 방어선 유지 이유
5. 전환 중 만난 문제들 — 솔직하게 서술 (실측 데이터 기반)
6. Before/After 실측 — 여기서 딱 한 표로 비교, 그 전후는 문단으로 숫자를 풀어서 해석
7. 한계와 다음 단계 — 분산락도 결국 락이다, Redis DECR은 어떨까 (시리즈 4 예고)

마치며:
- "병목 발견 → 가설 → 적용 → 재측정" 사이클을 한 번 돈 의미
- 면접에서 이 경험을 한 문장으로 설명하면 무엇이 될지

포함할 실제 수치:
```

## 사용 팁

1. 이 파일은 미래의 나에게 보내는 프롬프트 메모다. 실측 데이터만 채우면 바로 블로그가 나온다.
2. **숫자가 없으면 쓰지 마라.** 추측으로 채우면 면접관이 "이 수치는 어디서 나왔나요"를 물었을 때 답할 수 없다.
3. **"예상과 달랐던 지점" 섹션을 반드시 넣어라.** 이게 면접관이 가장 좋아하는 부분이다. 솔직하고 구체적일수록 점수가 올라간다.
4. 프롬프트 실행 직전 `blog-성능테스트시나리오설계.md` 를 다시 읽어 톤을 맞춰라. 서술형 문단의 호흡이 시리즈 전체에서 일관돼야 한다.
5. 표·불릿·다이어그램은 "꼭 필요한 딱 하나"만 쓰고, 나머지는 문장으로 풀어라. 정리된 자료가 아니라 읽히는 글이 되어야 한다.
