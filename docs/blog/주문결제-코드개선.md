# 주문/결제 API 코드 개선 — 4가지 변경의 설계 근거

## 왜 코드 변경과 측정 환경 변경을 분리했나

성능 작업에서 가장 흔한 함정은 **"코드를 바꿨는데 효과가 안 보인다"** 와 **"빨라졌는데 어디가 빨라졌는지 모르겠다"** 두 가지다. 두 함정 모두 한 가지 원인에서 나온다 — 코드 변경과 측정 환경 변경을 **같은 사이클 안에 섞어서 적용**하기 때문이다.

이번 작업에서는 처음부터 다음 원칙을 적용했다.

> **변경의 종류를 구분한다 — 시스템 코드 변경(production에 영향), 설정 변경(인프라 튜닝), 측정 환경 변경(production 무관). 각 변경의 효과는 그 종류에 맞는 지표로 검증한다.**

이 원칙으로 분류한 결과, 7번의 측정 사이클 동안 적용한 변경은 **시스템 코드 1건 + 설정 1건 + 측정 환경 2건**으로 정리됐다. 각 변경의 동기, 트레이드오프, 측정 효과를 명확히 분리해서 기록한 것이 이 글의 핵심 가치다 — **무엇을 바꾸면 무엇이 따라 바뀌는지**의 인과관계가 흐려지지 않게.

> 측정 사이클 전체 narrative + 데이터는 [주문결제-성능측정.md](주문결제-성능측정.md), 추적·가설 검증·반박 과정은 [주문결제-동시성-트러블슈팅.md](../troubleshooting/주문결제-동시성-트러블슈팅.md)에 있다. 이 글은 의사결정의 골격에 집중한다.

## 변경 1 — 재고 차감을 비관적 락 → atomic UPDATE 로 전환

### 의사결정 근거 — "정합성을 지키는 두 가지 방법" 사이의 트레이드오프

재고 차감의 정합성을 지키는 방법은 크게 두 가지다.

| 방법 | 정합성 보장 | 락 점유 시간 | 동시성 |
|------|------------|-------------|-------|
| 비관적 락 (`SELECT FOR UPDATE`) | ★★★ | SELECT 시점 ~ COMMIT 시점 (수십 ms) | ❌ 동일 row 직렬화 |
| atomic UPDATE (`WHERE stock >= qty`) | ★★★ | UPDATE 1회 안에서만 (~ms) | ✓ DB가 자동 직렬화 |

비관적 락은 **트랜잭션 길이만큼 락이 유지**되며, 그 사이의 모든 작업(비즈니스 로직, OrderDetail 생성, FK 검증 등)이 락 시간에 합산된다. 즉 락 점유 시간 = 트랜잭션 길이 = 동시성 한계.

측정 2(50 users 동일 옵션 집중)에서 **RPS 39.6에서 정확히 막히는 직렬화 흔적**이 관찰됐다. 풀이나 CPU가 아니라 락 자체가 동시성 상한을 결정하고 있다는 증거였다.

**결정: atomic UPDATE로 전환** — 락 점유 시간을 0에 수렴시킨다. `WHERE stock_quantity >= :qty` 조건이 음수 재고 방지와 race condition 방어를 동시에 수행하므로, 비관적 락의 정합성 보장은 그대로 유지된다.

### Before — 비관적 락 + 차감 + flush 시 UPDATE (쿼리 2 회 + 락 점유)

```java
// ProductService.java
@Override
public ProductOption decreaseStockWithLock(Long optionId, int quantity) {
    ProductOption option = productOptionRepository.findByIdWithLock(optionId)  // SELECT FOR UPDATE
            .orElseThrow(() -> new BusinessException(ErrorCode.PRODUCT_OPTION_NOT_FOUND));
    option.decreaseStock(quantity);  // 메모리 상 차감, flush 시 UPDATE
    return option;
}
```

```java
// ProductOptionRepository.java — 기존 메서드 (다른 곳에서 여전히 사용)
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT po FROM ProductOption po JOIN FETCH po.product p JOIN FETCH p.user " +
       "WHERE po.productOptionId = :optionId")
Optional<ProductOption> findByIdWithLock(@Param("optionId") Long optionId);
```

**문제**:
- 쿼리 2 회 (SELECT + UPDATE)
- 락 점유 시간 = SELECT 시각 ~ COMMIT 시각 (수십 ms)
- 동일 row 동시 요청 시 *전부 대기*

### After — 단일 atomic UPDATE (쿼리 1 회 + 락 점유 시간 0)

```java
// ProductOptionRepository.java — 새 메서드 추가
/**
 * 재고를 단일 atomic UPDATE 로 차감한다. 비관적 락 대신 사용.
 * - DB 가 단일 UPDATE 를 atomic 으로 처리 → race condition 자체가 발생 불가능
 * - WHERE stock_quantity >= :qty 조건이 음수 재고 방지 (SOLD_OUT 케이스도 자연스럽게 처리)
 * - 락 점유 시간 = 0 → SELECT FOR UPDATE 시절의 락 대기가 사라짐
 *
 * @return 1 = 차감 성공, 0 = 옵션 없거나 재고 부족 (호출자가 구분 처리 필요)
 */
@Modifying
@Query("UPDATE ProductOption po SET po.stockQuantity = po.stockQuantity - :qty " +
       "WHERE po.productOptionId = :optionId AND po.stockQuantity >= :qty")
int decreaseStockAtomic(@Param("optionId") Long optionId, @Param("qty") int qty);
```

```java
// ProductService.java — 메서드 본문 교체
@Override
public ProductOption decreaseStockWithLock(Long optionId, int quantity) {
    int updated = productOptionRepository.decreaseStockAtomic(optionId, quantity);
    if (updated == 0) {
        // 0건 = 옵션이 없거나 재고 부족 — 둘을 구분해서 정확한 에러 코드 반환
        if (!productOptionRepository.existsById(optionId)) {
            throw new BusinessException(ErrorCode.PRODUCT_OPTION_NOT_FOUND);
        }
        throw new BusinessException(ErrorCode.INSUFFICIENT_STOCK);
    }
    // OrderDetail FK + getProductPrice() 호출을 위해 1회 조회 (단순 SELECT, 락 없음)
    return productOptionRepository.findById(optionId)
            .orElseThrow(() -> new BusinessException(ErrorCode.PRODUCT_OPTION_NOT_FOUND));
}
```

### Why — atomic UPDATE 가 정합성을 어떻게 지키나

```sql
UPDATE products_options
SET stock_quantity = stock_quantity - 1
WHERE product_option_id = ? AND stock_quantity >= 1
```

- DB 는 단일 UPDATE 를 *atomic* 으로 처리 → race condition 자체가 발생 불가능
- `WHERE stock_quantity >= :qty` 조건이 *음수 재고 방지*
- 차감에 실패한 (0 건 반환) 케이스가 SOLD_OUT 분기 = `INSUFFICIENT_STOCK` 에러
- DB row lock 이 *짧은 순간만* 잡히고 즉시 해제 (커밋까지 안 가도 됨)

> **인터페이스명은 그대로** (`decreaseStockWithLock`) — 호출 측 코드 변경 없음. 메서드 본문만 *내부 구현 전환*. 비관적 락 → atomic UPDATE 는 *호출 계약을 깨지 않는 안전한 리팩토링*.

### 측정 효과 (측정 4 — 50 users / wait 0.5~2.0 / 2 분)

| 지표 | Before (비관적 락) | After (atomic UPDATE) |
|---|---|---|
| RPS | 39.6 | 39.9 (변화 없음 — wait_time 천장에 가려짐) |
| Median | 11 ms | 11 ms |
| P99 | 130 ms | 210 ms (추가 SELECT 영향, *측정 4 에서 추적*) |
| 음수 재고 | 0 | **0** ✅ |

→ wait_time 0.5~2.0 환경에서는 RPS 차이가 안 보임 (이론 RPS 40 천장). 진짜 효과는 *변경 2 + 3 후* 에야 가시화 (측정 5 에서 RPS 352.9).

### 적용 위치

| 파일 | 변경 |
|---|---|
| `src/main/java/ccommit/stylehub/product/repository/ProductOptionRepository.java` | `decreaseStockAtomic` 메서드 추가 |
| `src/main/java/ccommit/stylehub/product/service/ProductService.java` | `decreaseStockWithLock` 본문 교체 |

`findByIdWithLock` (비관적 락 SELECT) 는 *그대로 유지* — `updateStock` (재고 수동 변경), `increaseStock` (주문 취소 시 재고 복구) 에서 여전히 사용. **재고 차감 hot path 만** atomic UPDATE 로 전환.

## 변경 2 — JDBC URL + Hibernate batch 설정 (5 줄)

### 의사결정 근거 — "코드는 그대로 둔 채 한 번만 prepare하기"

ORM이 발행하는 SQL의 비용은 두 종류로 나뉜다.

```
1. SQL 자체의 실행 비용  (인덱스, 쿼리 플랜)
2. SQL을 DB로 보내는 비용 (prepare, parsing, network round-trip)
```

이 중 변경 1로 1번을 다뤘다. **2번은 코드를 한 줄도 건드리지 않고 설정만으로 줄일 수 있는 영역**이다 — JDBC 드라이버와 Hibernate 양쪽에 **Prepared Statement 캐싱 + batch insert**를 켜면, 동일한 SQL을 매번 prepare하지 않고 캐싱된 statement를 재사용하며, 여러 INSERT를 한 번의 round-trip에 묶어 발행한다.

설정 변경의 본질적 가치는 **변경 비용이 0이고 롤백 비용이 0이라는 점**이다. 코드 변경은 기능 회귀 위험을 동반하지만, 설정 튜닝은 application.properties의 5줄만 되돌리면 끝난다. 이 비대칭성을 인지하면, 측정 사이클의 초반에 설정 튜닝을 우선 시도하는 것이 합리적이다.

### Before — 기본 JDBC URL

```properties
spring.datasource.url=jdbc:mysql://localhost:3306/stylehub?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul&characterEncoding=UTF-8
```

### After — Prepared Statement 캐싱 + batch insert

```properties
# JDBC URL 보강 — Prepared Statement 캐싱 + batch insert
spring.datasource.url=jdbc:mysql://localhost:3306/stylehub?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Seoul&characterEncoding=UTF-8&rewriteBatchedStatements=true&useServerPrepStmts=true&cachePrepStmts=true&prepStmtCacheSize=250&prepStmtCacheSqlLimit=2048

# Hibernate batch insert/update — N건을 batch 로 묶어 round-trip 감소
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
```

### 각 옵션의 효과

| 옵션 | 효과 |
|---|---|
| `useServerPrepStmts=true` | MySQL 서버에 prepare 요청, 서버에서 statement 보관 |
| `cachePrepStmts=true` | 클라이언트 (JDBC 드라이버) 가 prepared statement 객체 캐싱 |
| `prepStmtCacheSize=250` | 캐시할 statement 종류 수 (250 종류까지 재사용) |
| `prepStmtCacheSqlLimit=2048` | 캐싱 대상 SQL 의 최대 길이 (2 KB 까지) |
| `rewriteBatchedStatements=true` | JDBC `addBatch` 호출을 *multi-row INSERT* 한 번으로 변환 |
| `hibernate.jdbc.batch_size=50` | Hibernate 가 50 건씩 묶어 batch 로 발행 |
| `order_inserts=true` | 같은 종류의 INSERT 를 모아서 batch 효과 극대화 |
| `order_updates=true` | 같은 종류의 UPDATE 도 모아서 batch |

### 측정 효과 (측정 5 — 50 users / wait 0.05~0.2 / 2 분, +변경 3 와 함께 측정)

| 지표 | Before (변경 2 X) | After (변경 2 + 3) |
|---|---|---|
| RPS | 39.9 | **352.9** ⭐ (8.8 배) |
| Median | 11 ms | 10 ms (-1 ms) |
| P95 | 32 ms | 32 ms (동일) |
| P99 | 210 ms | **70 ms** ⭐ (3 배 단축) |
| 음수 재고 | 0 | **0** ✅ |

> 변경 2 와 변경 3 은 *함께 적용해야 효과가 가시화*. 변경 2 만 적용하고 wait_time 그대로 두면 *이론 RPS 40 천장* 에 갇혀 차이가 안 보임. 변경 3 (wait_time 단축) 으로 부하 클라이언트 천장을 풀어줘야 변경 2 의 효과가 드러남.

### 적용 위치

| 파일 | 변경 |
|---|---|
| `src/main/resources/application.properties` | JDBC URL 5 파라미터 추가 + Hibernate batch 3 설정 |

## 변경 3 — Locust `wait_time` 단축 (측정 환경)

### 의사결정 근거 — "측정값이 정직한가"부터 검증한다

측정 4에서 RPS 39.9가 나왔다. 변경 1(atomic UPDATE)을 적용한 후의 결과인데도 측정 2의 RPS 39.6과 거의 동일했다. 이 시점에서 두 가지 가설이 가능했다.

```
가설 A: atomic UPDATE가 효과 없음 → 변경 1을 폐기해야 함
가설 B: 측정 환경이 천장을 만들고 있음 → 측정 환경을 점검해야 함
```

가설 A로 판단하면 잘못된 결론으로 변경 1을 폐기할 위험이 있다. 그래서 측정 환경을 먼저 점검했다.

```
Locust wait_time = between(0.5, 2.0)  → 평균 1.25초 대기
이론 RPS 상한 = users / wait = 50 / 1.25 = 40
```

즉 **부하 클라이언트의 설정값 자체가 RPS 40을 천장으로 만들고 있었다**. 시스템이 RPS 1000을 처리할 수 있어도 측정값은 40에 갇힌다. 가설 B가 옳았던 것이다.

이 결정의 메타 교훈: **측정값을 시스템의 답으로 받아들이기 전에, 측정 도구가 자기 자신의 한계를 만들고 있는지 먼저 의심한다.** 그렇지 않으면 시스템에는 문제가 없는데 시스템을 고치는 잘못된 사이클에 빠진다.

### Before

```python
# performance/locustfile_order.py
class OrderUser(HttpUser):
    wait_time = between(0.5, 2.0)  # 평균 1.25s → 50 users 시 이론 RPS 40 천장
```

### After

```python
class OrderUser(HttpUser):
    # wait_time 단축 측정용: 부하 클라이언트의 wait_time 천장 제거 → 시스템의 진짜 RPS 한계 측정
    # 기존 between(0.5, 2.0) 은 50 users 시 이론 RPS 40 천장에 갇혀 락 제거 효과가 안 보였음
    # 0.05~0.2 로 단축하면 50 users 가 full throttle 에 가까워져 시스템 한계 측정 가능
    wait_time = between(0.05, 0.2)  # 평균 0.125s → 50 users 시 이론 RPS 400 (10 배)
```

### 측정 효과

변경 2 와 함께 *시스템 한계 노출* — 측정 5 의 RPS 352.9 가 비로소 보임. 측정 4 의 *RPS 39.9 가 진짜 시스템 한계가 아니었음* 을 증명.

### 적용 위치

| 파일 | 변경 |
|---|---|
| `performance/locustfile_order.py` | `wait_time = between(0.5, 2.0)` → `between(0.05, 0.2)` |

> **이건 시스템 코드가 아니라 측정 환경 변경**. Production 영향 없음. 부하 테스트의 *천장 자체* 를 푸는 작업.

## 변경 4 — Locust 옵션 풀 쿼리 `JOIN users` (FK 무결성 필터)

### 의사결정 근거 — "오염된 측정 데이터 vs 시스템의 진짜 결함"의 구별

측정 6(100 users)에서 13.28%의 5xx가 발생했다. 이 시점의 가장 중요한 결정은 **이 실패율이 시스템의 한계인지, 측정 데이터의 결함인지를 구별**하는 것이었다.

추적 결과:
- 옵션 풀 200개 중 134개(67%)가 **dangling FK** — `products.user_id`가 `users`에 없는 ID를 가리킴
- atomic UPDATE는 정상 동작했지만, OrderDetail 생성 → store(user) LAZY 로드에서 NPE 발생 → 500
- 무작위 옵션의 fail 비율 67% = 풀의 dangling FK 비율 67% (**완전 일치 → 인과관계 확정**)

이 인과관계 확정이 결정적이다. 두 비율이 정확히 일치한다는 것은 5xx의 원인이 **시스템 코드가 아니라 시드 데이터의 FK 무결성 결함**임을 수학적으로 증명한다. 시스템을 고치는 게 아니라 **측정 풀을 고쳐야 한다**.

이 결정의 일반 원리: **측정에서 비정상이 보이면, 시스템과 측정 환경 양쪽을 동시에 의심해야 한다.** 한쪽만 의심하면 잘못된 영역에서 무한히 헤맨다. 비율 일치 같은 통계적 증거가 인과관계를 가르는 결정적 도구가 된다.

### Before — 단순 `stock > 0` 필터

```python
cur.execute("""
    SELECT product_option_id, stock_quantity
    FROM products_options
    WHERE stock_quantity > 0
    ORDER BY stock_quantity DESC
    LIMIT 200
""")
```

### After — JOIN users 로 유효 store FK 만

```python
# 옵션 풀은 store(user) FK 가 살아있는 옵션만 선택한다.
# 시드 데이터에 dangling FK 가 섞여 있어 (products.user_id → users 미존재) 이를 거르지 않으면
# OrderService 가 store 정보를 LAZY 로드할 때 5xx 가 발생해 시스템 한계가 아닌 데이터 결함이 측정에 노출된다.
cur.execute("""
    SELECT po.product_option_id, po.stock_quantity
    FROM products_options po
    JOIN products p ON p.product_id = po.product_id
    JOIN users u ON u.user_id = p.user_id
    WHERE po.stock_quantity > 0
      AND u.role = 'STORE'
    ORDER BY po.stock_quantity DESC
    LIMIT 200
""")
```

### 측정 효과 (측정 6 재실행 — 100 users / 동일 환경)

| 지표 | Before (오염 풀) | After (깨끗한 풀) |
|---|---|---|
| 누적 reqs | 44,359 | 36,955 |
| **Fails** | **5,892 (13.28 %)** ⚠ | **0 (0 %)** ✅ |
| Total RPS | 431.9 (5xx 가 RPS 부풀림) | 308 (정직한 처리량) |
| Avg | 31 ms | 24.3 ms |
| 음수 재고 | 0 | **0** ✅ |

### 적용 위치

| 파일 | 변경 |
|---|---|
| `performance/locustfile_order.py` | `setup_session_pool` 의 옵션 풀 쿼리 (JOIN 2 줄 + WHERE 1 줄) |

> 시드 데이터의 FK 제약 자체를 보강하는 것(`ALTER TABLE products ADD FOREIGN KEY ...`)도 가능했지만, **기존 데이터의 보존성**과 **결함의 영향 범위(측정에만 영향, production 무관)** 를 평가한 결과, 측정 코드에서 거르는 방식이 트레이드오프가 더 유리했다. 시드 정리는 영역이 다른 작업이라 별도로 분리.

## 적용하지 않은 변경 — "ROI가 정당화되지 않는 변경은 적용하지 않는다"

이 섹션이 이번 작업에서 가장 중요한 의사결정의 기록이다. **무엇을 하지 않기로 결정했는가**가 어떤 변경을 적용했는가만큼 시스템의 품질을 결정한다.

### `@DistributedLock` 적용 — 보류

`@DistributedLock` AOP 인프라(Redis SETNX + UUID 자기 락 해제 + SpEL 동적 키)는 이미 구현되어 있다. 그럼에도 **재고 차감 영역에는 적용하지 않기로 결정**했다.

| 평가 축 | 분산 락 적용 시 | atomic UPDATE 단독 |
|---------|--------------|------------------|
| 정합성 보장 | ★★★ | ★★★ (동등) |
| 추가 비용 | Redis 라운드트립 (~ms) | 0 |
| 동시성 한계 | DB row lock에 의해 결정 | DB row lock에 의해 결정 |
| 다중 인스턴스 보호 | ✓ (이미 DB가 보호) | ✓ (이미 DB가 보호) |

**핵심 통찰**: 단일 row의 atomic UPDATE는 이미 DB 차원에서 직렬화되므로, 그 위에 분산 락을 추가하는 것은 **이미 보장된 정합성에 추가 비용만 얹는 행위**다. 분산 락의 진짜 가치 영역은 **여러 단계가 묶인 비즈니스 단위 락**(선착순 쿠폰 발급, 작업 큐 클레임)으로, 현재 주문/결제 도메인 내부에는 그런 케이스가 없다.

인프라 자체는 보존했다. 다른 도메인에서 필요할 때 즉시 활용 가능하다. **"있다고 다 써야 하는 것이 아니다"** — 도구 사용 자체가 비용이라는 인식이 이 결정의 본질이다.

### 인기 옵션 샤딩 — 영역 분리

단일 row의 contention을 분해하려면 한 옵션의 재고를 N개 row로 분할하는 샤딩이 필요하다. 이는 단일 row 락의 본질적 한계를 푸는 진짜 다음 단계지만, **이 글의 측정 범위(단일 row 영역)와 다른 영역**이라 별도 작업으로 분리했다.

### `OrderDetail.create` 시그니처 단순화 — ROI 부족

atomic UPDATE 후 `findById` 1회를 제거할 수 있다. 측정 5 단계에서 **효과가 P99 -10~-20ms 수준**으로 추정됐다. 시그니처 변경은 호출자 전반에 영향을 주는 변경이라, **현재의 P99(70ms)에서 -10ms를 깎기 위한 변경 비용으로는 ROI가 부족**하다고 판단해 보류했다.

→ 이 세 결정은 모두 동일한 원칙으로 수렴한다 — **모든 가능한 변경을 적용하는 것이 좋은 엔지니어링이 아니다. 측정으로 정당화되는 변경만 적용한다.**

## 검증 — 정합성 invariant

모든 측정에서 *불변* 으로 유지:

```sql
-- 음수 재고 = 0 (어떤 부하에서도)
SELECT SUM(CASE WHEN stock_quantity < 0 THEN 1 ELSE 0 END) AS negative_stock
FROM products_options;
→ 0
```

| 측정 | RPS | 음수 재고 |
|---|---|---|
| 1 (10 users) | 7.5 | 0 |
| 2 (50 users 집중) | 39.6 | 0 |
| 3 (100 users 부분) | 79.6 | 0 |
| 4 (50 users atomic) | 39.9 | 0 |
| 5 (50 users 튜닝) | 352.9 | **0** |
| 6 재실행 (100 users) | 308 | **0** |
| 7 (200 users) | 502 | **0** |

→ **8회 측정, 누적 ~30만 reqs, 음수 재고 0건.** atomic UPDATE의 `WHERE stock >= qty` 조건이 어떤 부하에서도 race를 막아냈다는 결정적 증거다.

이 invariant 검증은 단순한 테스트 통과가 아니라 **"성능 최적화가 정합성을 깨지 않았는가"** 라는 본질적 질문에 대한 답이다. 비관적 락에서 atomic UPDATE로 전환하면서 가장 큰 위험은 정합성 회귀였고, 30만 reqs 누적 측정에서 음수 재고 0건이라는 결과는 그 위험이 실제로 0이었음을 통계적으로 입증한다.
