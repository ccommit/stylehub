# 300만 건 상품 조회 — 가설 검증 사이클 7회의 기록

## 왜 이 글을 "결과 요약"이 아닌 "가설 변경의 추적"으로 썼나

성능 개선 글의 흔한 형태는 **"무엇을 했고 얼마나 빨라졌다"** 의 결과 카탈로그다. 그러나 그 형식은 한 가지 결정적 정보를 누락한다 — **가설이 어떻게 틀렸고, 어떤 측정이 그 가설을 갱신시켰는가**. 이 정보가 없으면 결과 자체는 재현 가능한 방법론이 아니라 단순한 운의 기록이 된다.

이번 작업의 가장 큰 가치는 결과 수치가 아니라 다음에 있다.

> **5단계의 측정 사이클 동안 가설이 3번 틀렸고 예상이 2번 뒤집혔다. 그리고 각 갱신은 우연이 아니라 측정의 결과였다.**

| 갱신 유형 | 횟수 | 의미 |
|---------|----|------|
| 가설이 틀려서 갱신 | 3회 | 추측이 측정으로 반박된 사례 |
| 예상이 뒤집혀서 갱신 | 2회 | 통념이 측정으로 반박된 사례 |
| 예상대로 진행 | 2회 | 가설이 검증된 사례 (드물다) |

이 비율(추측·통념의 50% 이상이 측정에서 반박됨)이 의미하는 본질: **성능 영역에서 측정 없이 결정하는 것은 통계적으로 절반 이상 잘못된다.** 측정 사이클이 곧 신뢰할 수 있는 의사결정의 유일한 경로다.

이 글은 그 7회 가설 갱신의 추적이다 — 결과는 [요약 글(상품조회-3레이어-개선.md)](상품조회-3레이어-개선.md)에서 정리됐고, 이 글은 그 결과에 도달하는 **사고 과정의 기록**에 집중한다.

## 0. 측정 환경

- **DB**: MySQL 8.0 — products 약 317 만 row, product_options 약 952 만 row
- **캐시**: Redis 7
- **앱**: Spring Boot, HikariCP, Tomcat
- **부하**: Locust 2.x, `locustfile_product.py` (5 시나리오 — first page : next page : by store : by category : detail = 5 : 5 : 2 : 2 : 3)
- **환경**: 단일 머신에서 DB · Redis · 앱 · Locust client 가 자원을 공유. **절대 RPS 보다 Before / After 비율 에 의미가 있음.**
- **목표 SLO**: P95 < 300 ms, 에러율 < 0.1% (Google SRE 의 99.9% 가용성 — user-facing read API 표준)

세 가지를 한 번에 다 적용하지 않고 **하나씩 분리해서 측정** 하기로 했다. 그래야 어느 카드가 얼마만큼 기여했는지 알 수 있으니까.

## 2. 첫 번째 가설 — 카테고리 인덱스 부재

가장 먼저 카테고리 6 초의 EXPLAIN 부터 떴다.

```sql
EXPLAIN SELECT ... FROM products WHERE main_category = 'TOP' AND sub_category = 'T_SHIRT' ORDER BY product_id DESC LIMIT 21;
```

| 지표 | 값 |
|---|---|
| type | index |
| key | PRIMARY |
| filtered | **2.50 %** |

`filtered: 2.5%` — PK 역순으로 스캔하면서 카테고리 조건을 만족하는 행을 찾는데, **2.5% 만 매칭** 된다는 뜻. 300만 건의 2.5% 면 약 7.5만 건 검사 후 21건을 골라내는 셈. 인덱스 부재 확정.

복합 인덱스 추가:

```sql
CREATE INDEX idx_products_category
ON products (main_category, sub_category, product_id DESC);
```

300만 건에서 **5 초** 만에 생성. EXPLAIN 다시.

| 지표 | Before | After |
|---|---|---|
| key | PRIMARY | **idx_products_category** |
| filtered | 2.50 % | **100.00 %** |

`filtered: 100%` — 인덱스를 정확히 사용. 카테고리 P95 **5,400 → 540 ms (10 배)**.

여기서 예상 밖 발견. **카테고리 외 API 도 같이 빨라짐.** RPS 가 10.5 → 21.9 로 두 배 증가. 이유를 추적해보니 **"느린 쿼리 하나가 풀을 오래 점유 → 풀 회전율 저하 → 다른 쿼리도 대기"** 였던 것. 카테고리 쿼리가 빨라지자 풀이 회전하면서 다른 쿼리들도 덜 기다리게 된 셈. *"느린 쿼리 하나가 시스템 전체 처리량 상한을 결정한다"* 의 첫 번째 실측 증거.

## 3. 두 번째 가설 — N+1 이라고 확신했는데, 틀렸다

Step 1 후에도 first page 가 여전히 P95 1,200 ms. 이번엔 **N+1 쿼리** 가 의심됐다. JPA 의 LAZY 로딩이 List 순회 중 N 번 추가 쿼리를 날리는 전형적 패턴.

`application.properties` 에 `spring.jpa.show-sql=true` 켜고 first page 한 번 호출해서 SQL 로그를 봤다.

**그런데 N+1 이 아니었다. 쿼리는 정확히 1 개였다.**

자세히 보니까 SELECT 절이 이상하게 길었다.

![과다 컬럼 투영 — Hibernate SQL 로그 (Before)](images/2026-04-24_over-fetching-before.png)

`p1_0.product_id, p1_0.created_at, p1_0.description, p1_0.image_url, p1_0.like_count, p1_0.main_category, p1_0.name, ..., u1_0.user_id, u1_0.is_active, u1_0.approved_at, u1_0.birth_date, u1_0.created_at, u1_0.email, u1_0.grade, u1_0.last_login_date, u1_0.name, u1_0.password, u1_0.point_balance, u1_0.provider, u1_0.role, u1_0.store_deleted_at, u1_0.store_description, u1_0.store_like_count, u1_0.store_name, ...`

**31 개 컬럼이 SELECT 되고 있었다.** 그 중에는 심지어 **`u.password` 해시값** 까지 있었다. 목록 조회 API 가 User 엔티티 전체를 가져오면서 보안상 민감한 비밀번호 해시까지 앱 메모리로 올리고 있었던 것.

화면에 실제로 필요한 건 8 개 컬럼 (`product_id, user_id, store_name, name, main_category, sub_category, price, image_url`).

**N+1 이 문제가 아니라 "한 쿼리가 31 컬럼을 가져오는 과다 투영" 이 진짜 원인이었다.** 결과적으로 응답 시간이 길어진 건 같지만 **원인의 성격이 다르고, 해결책도 다르다.**

> **여기서 얻은 교훈**: EXPLAIN 은 "쿼리가 빠르다" 고 진실을 말했고, 실제로 PK 역순 스캔 21 건은 빠른 쿼리다. **하지만 가져오는 컬럼 수는 EXPLAIN 이 보여주지 않는다.** `show_sql=true` 로 실제 SQL 을 본 뒤에야 진짜 문제가 드러났다. EXPLAIN 한 줄로 끝나면 안 된다 — 실제 쿼리 로그, 애플리케이션 코드, 엔티티 구조를 교차 검사해야 한다.

## 4. Projection 적용 — 그런데 효과가 안 보였다 (Warm-up 의 함정)

해결책은 **DTO 직접 투영**. 엔티티 전체를 가져오지 않고 QueryDSL 의 `Projections.constructor` 로 필요한 8 개 컬럼만 바로 DTO 로 매핑.

```java
// Before: 엔티티 전체 조회 → DTO 변환
queryFactory.selectFrom(product).where(...).fetch()

// After: DTO 직접 투영
queryFactory
    .select(Projections.constructor(ProductListResponse.class,
        product.id, product.user.id, product.user.storeName,
        product.name, product.mainCategory, product.subCategory,
        product.price, product.imageUrl))
    .from(product).where(...).fetch()
```

After SQL.

![Projection 적용 후 — Hibernate SQL 로그 (After)](images/2026-04-24_projection-after.png)

**컬럼 31 → 8 로 1/4 감소.** JOIN 구조와 쿼리 개수는 그대로지만 DB → 앱 사이 전송 데이터량이 약 1/4 로 감소.

기대하고 Warm-up (10명, 30초) 재측정.

![Step 2 Warm-up 재측정 — 의외의 결과](images/2026-04-24_step2-warmup-result.png)

| API | Step 1 After P95 | Step 2 After P95 | 변화 |
|---|---|---|---|
| `/products/{id}` | 14 ms | **24 ms** | ↑ 10 ms |
| next page | 7 ms | 16 ms | ↑ 9 ms |
| by store | 7 ms | 13 ms | ↑ 6 ms |
| first page | 510 ms | 570 ms | ↑ 60 ms |
| by category | 540 ms | 610 ms | ↑ 70 ms |
| **Aggregated P95** | **470 ms** | **520 ms** | ↑ 50 ms |
| RPS | 6.7 | 7.4 | ↑ 0.7 |

**Projection 을 적용했는데 오히려 P95 가 살짝 올라갔다.** 개선이 안 된 것처럼 보인다.

처음엔 당황했다. *"내가 뭘 잘못 짠 건가? Projection 이 오히려 비싼가?"* 한참 고민하다가 실험 조건을 들여다봤다.

**Projection 의 핵심 효과는 쿼리 실행 시간 단축 → 커넥션 풀 점유 시간 단축 → 풀 회전율 증가.** 즉 **커넥션 풀에 경합이 있어야** 효과가 드러난다. Warm-up 10 명은 wait_time 평균 1.25 초, 이론 RPS 8 — 풀 10 개에 비해 한참 모자라서 **경합이 거의 없는 상태.** 경합이 없으면 풀 회전율이 빨라져도 아무 의미가 없다.

Light (50 명) 로 다시 돌리니까 답이 나왔다.

| 지표 | Step 1 | **Step 2 (Light)** | 변화 |
|---|---|---|---|
| RPS | 21.9 | **31.9** | **+46 %** |

**RPS 가 21.9 → 31.9 (46% 증가).** Warm-up 노이즈에 묻혀 보이지 않던 효과가 경합이 있는 Light 에서 명확히 드러났다.

> **여기서 얻은 교훈**: 통제 변수가 잘못된 실험은 잘못된 결론을 낸다. *"개선했는데 효과 없음"* 으로 결론 내고 롤백할 뻔했다. **개선이 효과를 발휘할 조건 (경합 발생)** 을 만들고 측정해야 진짜 효과가 보임.

## 5. 풀 확대 — 그런데 무거운 쿼리는 오히려 나빠졌다 (예상이 뒤집힌 두 번째)

Step 2 후에도 RPS 31.9 가 천장. 유저 50 명 × wait 1.25 초 = 이론 최대 RPS 40 의 80% 도달. **여전히 풀이 병목이라는 신호.**

```properties
spring.datasource.hikari.maximum-pool-size=50
```

10 → 50 으로 확대. 이론적으로 RPS 5 배가 가능해야 한다. Light (50 명) 재측정 결과는 예상과 달랐다.

| API | Step 2 After P95 | Step 3 After P95 | 변화 |
|---|---|---|---|
| `/products/{id}` | 410 ms | **30 ms** | **13.7×** ↓ ✅ |
| next page | 400 ms | **35 ms** | **11.4×** ↓ ✅ |
| by store | 430 ms | **35 ms** | **12.3×** ↓ ✅ |
| **first page** | **1,100 ms** | **1,300 ms** | **↑ 200 ms** 🔴 |
| **by category** | **1,200 ms** | **1,500 ms** | **↑ 300 ms** 🔴 |

**가벼운 쿼리는 10 배 이상 개선됐는데, 무거운 쿼리는 오히려 악화.** 왜?

풀을 10 → 50 으로 늘리면 **동시에 DB 에 날아가는 쿼리가 5 배** 가 된다. 가벼운 쿼리 (PK 조회, 인덱스 범위 스캔) 는 각자 I/O 가 작아 동시 실행해도 서로 안 방해한다. 하지만 무거운 쿼리 (300만 건 위의 ORDER BY + LIMIT, 카테고리 필터) 는 디스크 I/O 가 크고, **50 개가 동시에 날아가면 서로 I/O 자원을 빼앗는다.**

```
풀 10 시절: [요청 50] → [풀 대기 큐] → [DB 여유]    ← 풀이 병목
풀 50 시절: [요청 50] → [바로 DB]    → [DB I/O 경합] ← DB 자체가 병목
```

**병목이 사라진 게 아니라 한 층 이동한 것.**

> **여기서 얻은 교훈**: 풀 확대 = 무조건 개선이 아니다. **쿼리 유형 (가벼운 / 무거운) 에 따라 풀 확대의 방향성이 다르다.** 풀이 병목인 가벼운 쿼리에는 ✅, DB I/O 가 병목인 무거운 쿼리에는 🔴.

## 6. Covering Index — DB 레벨 병목 풀기

Step 3 에서 드러난 DB I/O 경합을 풀려면 **무거운 쿼리의 I/O 자체를 줄여야** 한다. 카드는 **Covering Index**.

InnoDB 의 secondary index 는 매칭된 행의 다른 컬럼을 **테이블로 돌아가 읽어야** 한다. 21 건이어도 21 번의 추가 I/O. SELECT 에 필요한 컬럼까지 인덱스에 모두 포함시키면 **테이블 접근 자체를 없앨** 수 있다.

```sql
DROP INDEX idx_products_category ON products;

CREATE INDEX idx_products_category_cover
ON products (main_category, sub_category, product_id DESC,
             user_id, name, price, image_url);
```

EXPLAIN 의 Extra 에 **`Using index`** 가 새로 찍혔다. 인덱스 페이지만으로 조회 완료라는 뜻 — 테이블 방문이 사라졌다.

Light (50 명) 재측정.

![Step 4a Light 재측정 결과](images/2026-04-24_step4a-light-result.png)

| API | Step 3 P95 | **Step 4a P95** | 개선 |
|---|---|---|---|
| `/products/{id}` | 30 ms | 12 ms | 2.5× ↓ |
| next page | 35 ms | 12 ms | 2.9× ↓ |
| by store | 35 ms | 13 ms | 2.7× ↓ |
| **by category** | **1,500 ms** | **200 ms** | **7.5×** ↓ 🎯 |
| first page | 1,300 ms | 620 ms | 2.1× ↓ (예상 밖) |

**Covering 인덱스는 by category 에만 붙였는데 first page 도 2 배 빨라졌다.** Step 1 에서 본 것과 정반대 방향의 연쇄 — by category 가 테이블 I/O 를 안 쓰게 되니 DB 전체의 I/O 자원에 여유가 생겼고, first page 같은 다른 무거운 쿼리도 덜 방해받았다.

**"느린 쿼리 하나가 시스템 전체 성능을 제한한다"** 가 반대 방향으로도 성립한다 — *"하나를 빠르게 만들면 나머지도 같이 빨라진다."*

## 7. 50 users 5/5 달성 — 그런데 1,000 users 에서 first page 만 갑자기 튐

**여기서 50 users 기준 5 개 API 모두 P95 < 300 ms 목표 달성.** Aggregated P95 5,200 → 69 ms (75 배), RPS 10.5 → 38.6.

다음 단계로 부하를 올렸다. 500 users 까지는 여유. 1,000 users 로 올린 순간 **first page 만 P95 4,100 ms 로 튐**. 다른 API 들은 300 ms 대로 멀쩡.

처음엔 당황했다. *"왜 first page 만? 캐시 적용된 가장 빠른 API 가 왜 갑자기?"*

요청 분포를 다시 봤다. **first page 가 전체 요청의 29 % — 가장 많이 호출되는 경로.** 13,588 요청 중 5% ≈ 680 개가 P95 를 망치고 있었다. 그게 어떤 순간에 몰리는지 궁금해서 시계열을 봤더니, **TTL 만료 시점 (캐시가 비워지는 순간) 에 집중적으로 발생**.

**Cache Stampede (썬더링 허드).** TTL 만료 순간 동시에 들어온 요청들이 전부 cache miss 로 DB 로 몰리는 현상. 이론으로만 알고 있던 패턴이 실측으로 보였다.

해결책은 Spring 에 내장된 `@Cacheable(sync = true)`. **같은 키로 동시 cache miss 가 발생하면 한 스레드만 DB 로 가고 나머지는 그 결과를 기다린다.**

```java
@Cacheable(
    value = "products:firstPage",
    key = "...",
    condition = "#cursor == null",
    sync = true                       // ← 한 줄
)
```

TTL 도 30 → 60 초로 올려 miss 빈도를 절반으로.

![1,000 users — 캐시 + sync=true 적용 후](images/2026-04-24_redis-after-1k.png)

| 지표 | Before | After |
|---|---|---|
| first page P95 | **4,100 ms** | **310 ms (13× ↓)** |
| Aggregated P95 | 430 ms | 310 ms |
| RPS | 462 | 798 (1.7× ↑) |

**한 줄로 stampede 가 사라졌다.**

> **단, 여기서 짚어야 할 한계** — `sync = true` 의 락은 **JVM 내부 락 (`ReentrantLock`)** 이라 **단일 인스턴스 한정.** 다중 인스턴스 환경에서는 TTL 만료 순간 cache miss 가 인스턴스 수만큼 DB 로 전파된다. 진짜 분산 stampede 방어가 필요하면 Redisson `RReadWriteLock` 같은 분산 락 캐시 레이어로 바꿔야 한다. 이 프로젝트는 단일 서버 측정 환경이라 sync=true 로 충분, 다중 인스턴스 운영 시에는 부하 측정 후 Redisson 도입 여부를 결정할 영역으로 분리해뒀다 (코드 리뷰 반영).

## 8. 캐시 추가했는데 RPS 가 오히려 줄었다 (예상이 뒤집힌 세 번째)

2,000 users 로 올리니 다시 P95 1,300 ms. *"Median 13 ms → 530 ms 로 40 배"* 상승 — 캐시 효율 문제가 아닌 **시스템 전체 큐잉** 신호.

요청 분포를 보니 캐시 미스 경로가 여전히 46 % (next page + `/products/{id}`). 이 중 `/products/{id}` 는 같은 응답 → 캐시 가능.

상세 조회도 캐시 추가:

```java
@Cacheable(value = "products:detail", key = "#productId", sync = true)
@Transactional(readOnly = true)
public ProductResponse getProduct(Long productId) { ... }
```

(여기서 **Jackson 3 의 default typing 함정** 도 만났다. record 가 직렬화 안 됨 — Spring Boot 의존성 업데이트 후 default typing 동작이 달라진 것. `JavaType` 을 `RedisCacheManager` 에 직접 등록하는 방식으로 우회.)

2,000 users 재측정. **놀라운 결과.**

| 지표 | Before (detail 캐시 X) | After (detail 캐시 O) |
|---|---|---|
| RPS | 1,016 | **890 (↓)** |
| P95 | 1,300 ms | 1,500 ms (↑) |
| Median | 530 ms | 460 ms (↓) |

**캐시를 추가했는데 RPS 가 오히려 줄었다.** Median 은 개선됐는데 RPS 와 P95 는 악화.

Median 개선 = 캐시 효과는 있다. RPS 악화 = **다른 어딘가에 상한이 있다** 는 뜻.

## 9. Tomcat 한계 — 캐시도 풀도 아닌 곳

병목을 의심해야 할 곳을 다 한 번씩 점검했다.

- HikariCP 풀: 50/100 — 모니터링 보니 사용률 낮음. 풀이 아님.
- DB I/O: 캐시 적중률 양호, DB 쿼리 수 줄어듦. DB 가 아님.
- Redis: `INFO memory` 로 보니 1.41 MB, 한가함. Redis 가 아님.

남은 후보 — **Tomcat 스레드 풀**. Spring Boot 기본값 `server.tomcat.threads.max = 200`. 즉 **동시에 처리할 수 있는 요청은 200 개**.

이론 RPS 계산.

```
유저 2,000 명 × wait_time avg 1.25 초 = 이론 RPS 1,600
실측 RPS 890 — 이론의 56 %
```

이론과 실측의 차이가 너무 크다. 왜? **Tomcat 200 스레드 × (1000ms / 평균 응답시간 250ms) = 800 RPS** — 이론 상한 800 과 실측 890 이 거의 일치.

**Tomcat threads.max 가 정확히 처리량 천장이었다.**

```properties
server.tomcat.threads.max=400
server.tomcat.accept-count=200
```

200 → 400 + accept-count (OS 소켓 큐) 200. 2,000 users 재측정.

| 지표 | Before (200) | **After (400)** |
|---|---|---|
| Aggregated P95 | 1,500 ms | **1,000 ms** |
| RPS | 577 | **1,003 (1.74×)** |
| 총 요청 / 2 분 | — | **120,328** (실패 0) |

**RPS 1,003 — 단일 서버 처리량 절대 상한.**

## 10. 극한 부하 — 0% 실패율의 함정

2,000 users 가 합리적 상한이라는 건 확인. 하지만 **진짜 파괴점이 어딘지** 궁금해서 3,000 → 5,000 → 10,000 users 까지 밀어붙였다.

| 동시 사용자 | Aggregated P95 | 평균 RPS | 총 요청 / 2 분 | Max | 실패율 |
|---|---|---|---|---|---|
| 1,000 | 310 ms | 798 | 92,984 | 7,016 | **0%** |
| 2,000 | 1,000 ms | **1,003** | 120,328 | 6,834 | **0%** |
| 3,000 | 2,500 ms | 826 | 99,129 | 20,251 | **0%** |
| 5,000 | 6,500 ms | 561 | 67,280 | 49,652 | **0%** |
| **10,000** | 5,600 ms | 868 | **104,157** | **108,638** | **0%** |

**모든 구간 실패율 0%.** 약 53 만 건의 요청을 전부 응답. 10,000 users 극한 부하에서도 `accept-count=200` 큐잉이 graceful degradation 으로 작동.

**하지만 이 표를 자세히 보면 함정이 있다.**

10,000 users 의 **Max 응답이 108,638 ms = 108.6 초.** pageSize=50 경로의 일부 요청은 **1 분 49 초** 동안 서버 큐에서 대기하다 응답. 실사용자 환경이라면:

- 브라우저: HTTP 기본 타임아웃 60 초 넘어 오래전에 끊김
- 모바일 앱: 유저는 앱을 재시작했을 것
- 비즈니스: "구매 결제 1분 49초 대기" = 거의 모든 유저 이탈

**서버는 살아있지만 서비스는 이미 죽은 지 오래** 인 구간. 이게 **"0% 실패율" 숫자 하나만으로 건전성을 판단하면 안 되는 이유** — 반드시 **P95, P99, Max 를 동반해서** 봐야 한다는 걸 숫자로 체감.

> **여기서 얻은 교훈**: "서버가 죽지 않는다" 와 "서비스가 된다" 는 다른 개념. 0% 실패율은 매력적인 숫자지만 그 자체로는 무의미하다. UX 관점에서는 P99 와 Max 가 더 중요하고, 비즈니스 관점에서는 *"몇 % 의 요청이 5 초 안에 응답되는가"* 가 더 중요하다.

## 12. 정리 — 7번의 가설 갱신이 도달한 메서드론

### 가설이 틀렸던 순간 (3회)

| # | 처음 가설 | 측정으로 드러난 진실 | 메서드론 교훈 |
|---|---------|------------------|------------|
| 1 | "N+1 문제일 것이다" | **과다 컬럼 투영**이 진짜 원인 | EXPLAIN 한 줄로 끝내지 말고 SQL 로그 + 엔티티 교차 검사 |
| 2 | "Projection 적용 → 효과 없음" | 측정 조건(Warm-up 10명)에 풀 경합 없어 효과 미발현 | **통제 변수가 잘못된 실험은 잘못된 결론을 낸다** |
| 3 | "풀 늘리면 다 빨라질 것이다" | 무거운 쿼리에서는 오히려 악화 | **풀 확대는 쿼리 유형에 따라 방향성이 다르다** |

### 예상이 뒤집힌 순간 (2회)

| # | 예상 | 측정 결과 | 본질적 원인 |
|---|------|--------|-----------|
| 1 | 카테고리 인덱스 → 카테고리만 빨라질 것 | 다른 API도 동반 개선 | 풀 회전율 효과 — "느린 쿼리 하나가 전체를 잡는다"의 일반 법칙 |
| 2 | 상세 캐시 → RPS 향상 | 오히려 RPS 감소 | 진짜 병목이 캐시가 아닌 Tomcat 스레드였음 |

### 도달한 3가지 메서드론

1. **EXPLAIN 한 줄로 결론 내지 않는다** — SQL 로그, HikariCP 모니터링, Tomcat 스레드 풀, 라이브러리 문서의 교차 검사가 진짜 원인을 잡는다
2. **통제 변수가 결론의 신뢰도를 결정한다** — 개선이 효과를 발휘할 조건을 만든 뒤 측정해야 진짜 효과가 보인다
3. **병목은 이동한다** — "DB → 풀 → DB → 캐시 → Tomcat"의 5단계 이동을 추적해야 한다 (한 카드로 끝나지 않는다)

### 결론의 적용 범위 명시

이 프로젝트의 절대 RPS / P95 수치는 **단일 머신 환경**(DB · Redis · 앱 · Locust 동거)에서 측정됐다. 운영 환경에서는 다를 수 있다. 의미가 있는 것은 **Before / After 비율** — 이 비율은 환경이 달라져도 어느 정도 보존된다.

이 한계 명시 자체가 결론의 신뢰도를 결정한다. **"모든 환경에서 75배 빨라진다"** 가 아니라 **"이 측정 환경에서 75배 비율이 관찰됐고, 동일한 메서드론을 다른 환경에 적용할 수 있다"** 가 정직한 결론이다.

### 후속 영역 (이 프로젝트 범위 외)

- **Read Replica 분리** — 읽기 트래픽 복제본 분산
- **애플리케이션 수평 확장** — Load Balancer + 다중 인스턴스로 Tomcat 스레드 병목 병렬 극복
- **Redisson 분산 락 캐시** — `sync=true`의 단일 JVM 한계를 분산 환경으로 확장
