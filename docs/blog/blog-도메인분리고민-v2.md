# 주문과 결제 도메인 분리 — 결합과 분리 사이의 의도적 설계

## 왜 처음부터 두 도메인의 경계를 의식했나

이커머스 시스템에서 "주문"과 "결제"는 사용자 관점에서는 한 흐름이지만, 시스템 관점에서는 **수명 주기, 트랜잭션 경계, 외부 의존성, 정책 소유권이 모두 다른 두 개의 컨텍스트**다. 이 차이를 도메인 설계 단계에서 의식하지 않으면, 단일 서비스에 모든 로직이 응축되며 다음 세 가지 문제가 동시에 터진다.

1. **트랜잭션 범위가 외부 시스템 응답 시간을 흡수** — 결제 인증을 기다리는 동안 DB 커넥션을 점유해 풀이 고갈된다
2. **정책 소유권이 모호** — "환불 가능 여부"가 Order에 있어야 할지 Payment에 있어야 할지 코드 곳곳에서 충돌한다
3. **장애 격리가 불가능** — 결제 PG의 문제가 주문 조회 API까지 멈춘다

도메인을 단순히 패키지로 나누는 수준이 아니라, **트랜잭션 경계 / 의존 방향 / 정책 소유권 / 에러 코드**까지 일관된 기준으로 분리해야 위 문제들을 동시에 해결할 수 있다. 이 글은 그 분리 기준을 어떻게 잡았는지의 기록이다.

---

## 분리의 가장 강력한 근거 — "두 트랜잭션 사이에 사용자의 시간이 흐른다"

토스페이먼츠의 결제 흐름을 분석하면, 주문 생성과 결제 승인 사이에는 **사용자의 인증 시간**이라는 비결정적 구간이 존재한다.

```
[서버] 주문 생성 → [사용자] 카드 선택·비밀번호 입력 (수초~수분) → [서버] 결제 승인
```

이 구간을 단일 트랜잭션으로 묶으면 다음 식이 성립한다.

```
DB 커넥션 점유 시간 = 사용자의 의사결정 시간
```

HikariCP 기본 풀 크기 10개 환경에서, 11명이 동시에 결제창에서 망설이면 11번째 사용자의 상품 조회·로그인까지 대기 큐에 쌓인다. 즉 **결제 도메인의 외부 I/O가 무관한 도메인의 가용성을 갉아먹는 구조**가 된다.

이 한 가지 사실이 도메인을 분리해야 하는 가장 강력한 근거가 되었다. 분리 후 트랜잭션 구조는 다음과 같다.

```
[트랜잭션 1] placeOrder()        — 주문 생성 + 재고 차감 + Payment READY 저장
                                 → 커밋 → 커넥션 즉시 반환
   ... 사용자의 결제 인증 시간 (DB 커넥션 0개 점유) ...
[트랜잭션 2] approvePayment()    — 토스 승인 + 상태 변경
```

분리는 공짜가 아니다. 트랜잭션이 둘이 되는 순간 **정합성 보장 책임이 인프라에서 애플리케이션으로 이동**한다. 그 책임을 어떻게 설계했는지가 다음 절들의 주제다.

## 두 트랜잭션을 잇는 신뢰 매개체 — pgOrderId + requestedAmount

분리된 트랜잭션 사이에는 사용자의 시간뿐 아니라 **클라이언트의 조작 가능성**까지 흐른다. 즉 트랜잭션 2에서 받는 입력은 신뢰할 수 없다. 따라서 두 트랜잭션을 잇는 매개체는 **클라이언트가 조작할 수 없는 영역**에 있어야 한다.

```
트랜잭션 1 (placeOrder)
  ├── pgOrderId 생성 (UUID 기반 — DB PK 노출 방지)
  └── Payment READY 저장 (requestedAmount = 서버 계산 금액)

    ── 사용자 인증 → 토스가 successUrl로 리다이렉트 (orderId, amount 동반) ──

트랜잭션 2 (approvePayment)
  ├── pgOrderId로 Payment 조회
  ├── DB의 requestedAmount vs 토스가 보낸 amount 비교 (위변조 검증)
  └── 일치 시 토스 승인 호출
```

핵심 원리: **DB에 기록된 requestedAmount가 두 트랜잭션 사이의 단일 진실 공급원(SSOT)** 이다. 클라이언트나 URL 파라미터를 통한 amount는 검증 대상이지 신뢰 대상이 아니다.

이 패턴은 일반화하면 다음과 같다.

> 분산된 트랜잭션 사이의 정합성은 **서버가 직접 쓴 불변 기록**으로만 이을 수 있다. 외부에서 들어오는 값은 그 기록과 비교하기 위해 존재한다.

이 원칙을 명문화한 덕에 [위변조 검증](blog-위변조검증.md), 후속 멱등성 처리까지 같은 사고 프레임으로 연결할 수 있었다.

## 의존 방향 — 순환을 끊은 의도적 비대칭 설계

두 도메인을 분리하면 즉시 마주하는 질문은 **"누가 누구를 참조할 것인가"** 이다. 두 가지 방향이 모두 필요해 보인다.

- Order → Payment: 주문 생성 시 결제 준비 데이터를 만들어야 함
- Payment → Order: 결제 실패/취소 시 주문을 보상 처리해야 함

이 두 방향을 모두 Service 단위로 풀면 그대로 **순환 의존**이 된다. 해결 후보 세 가지를 검토했다.

| 후보 | 방식 | 트레이드오프 |
|------|------|-------------|
| A. 이벤트 기반 양방향 분리 | 모든 호출을 이벤트로 | 단순 INSERT까지 이벤트화하면 과도한 추상화 |
| B. Service → Repository 직접 호출 (단방향만) | Order는 PaymentRepository만 사용 | 도메인 경계 일부 양보, 단순성 확보 |
| C. 공통 Facade Service | 별도 OrderPaymentFacade가 양쪽 호출 | 책임 분산이 흐려지고 새로운 신을 만듦 |

**후보 B를 선택**했다. 근거:

- Order → Payment 방향의 호출은 "Payment를 READY 상태로 INSERT" 한 가지뿐이며, **비즈니스 규칙이 없는 단순 영속화**다. 이 한 호출에 이벤트와 비동기 처리를 도입하는 것은 트레이드오프가 맞지 않다
- 반대 방향(Payment → Order의 보상 처리)은 비즈니스 규칙이 있으므로 **OrderService를 거친다**. 즉 양 방향에 동일한 추상화를 강요하지 않고 **각 호출의 무게에 비례한 결합 강도**를 적용한 것

```java
// OrderService — Payment의 비즈니스 로직은 모름, 단순 영속화만 수행
paymentRepository.save(Payment.create(savedOrder, ...));

// PaymentService — Order의 비즈니스 로직(취소/재고 복구) 호출
orderService.cancelOrder(order.getOrderId());
```

원칙주의에 매몰되어 모든 도메인 간 호출을 이벤트로 풀면 코드가 "안전하지만 추적 불가능"해진다. **결합 강도를 호출의 무게에 맞춰 차등 적용**하는 것이 실용적 설계다.

## 정책 소유권 — "데이터의 위치"가 아니라 "판단의 주체"가 기준

결제 취소 시 배송 상태와 환불 기간을 검증해야 한다. 이 정책(`CancelPolicy`)을 어느 도메인에 둘 것인가?

배송 상태는 `Order` 엔티티의 필드이므로 직관적으로는 Order 도메인이 자연스러워 보인다. 그러나 **정책의 위치를 결정하는 진짜 기준은 데이터의 위치가 아니라 판단의 주체**다.

| 기준 | Order에 두기 | Payment에 두기 |
|------|------------|--------------|
| 데이터 접근 편의성 | ★★★ | ★★ |
| 호출 시점의 의미 | "주문이 자기 상태를 검증" | "결제 취소가 가능한지 결제가 판단" |
| 변경 압력의 원천 | 배송 정책 변경 시 | 환불 정책 변경 시 |
| 호출자 | PaymentService | PaymentService |

**결정적 근거**: 환불 기간이 7일에서 14일로 바뀌는 변경이 발생할 때, **수정해야 할 도메인은 Payment**다. 정책 변경의 원인은 결제 도메인의 비즈니스 규칙에 있기 때문이다. 만약 이 정책이 Order에 있다면, **결제 정책 변경이 주문 도메인의 코드를 수정**시키는 역방향 결합이 생긴다.

```java
// payment/policy/CancelPolicy.java
@Component
public class CancelPolicy {
    public void validate(Order order) {
        if (order.getDeliveryStatus() == DeliveryStatus.SHIPPING) {
            throw new BusinessException(ErrorCode.CANCEL_NOT_ALLOWED_SHIPPING);
        }
        // ...
    }
}
```

원칙: **데이터는 읽기 전용으로 공유하되, 판단의 주체는 변경 압력을 받는 도메인에 둔다.** Order의 상태를 읽는 것은 허용하지만, 그 상태에 대한 해석 규칙은 Payment가 소유한다.

## 에러 코드의 도메인 접두사 — 운영 가시성 설계

작아 보이지만 의도적으로 분리한 영역이다.

```
OR001 — 존재하지 않는 주문
OR002 — 현재 상태에서는 처리 불가
PM001 — 존재하지 않는 결제
PM002 — 결제 금액 불일치
PM007 — 배송 중에는 취소 불가
```

이 설계의 목적은 **장애 발생 시 1차 분류 비용을 0에 수렴시키는 것**이다. 운영 환경에서 알람이 울렸을 때, `PM007`만 봐도 "결제 도메인의 취소 정책 위반"이라는 컨텍스트가 즉시 잡힌다. 검색 조건, 대시보드 필터, 알림 라우팅 모두 접두사 단위로 묶을 수 있다.

대용량 서비스에서 운영 가시성은 코드 품질이 아니라 **장애 대응 시간**으로 측정된다. 이 작은 컨벤션이 장애 발생 시 분 단위 차이를 만든다.

## 결과 구조

```
Order 도메인
├── OrderController
├── OrderService              — 주문 생성/취소/조회
├── Order, OrderItem
├── OrderCreatedEvent         — 도메인 간 결합 최소화
└── OrderPaymentTimeout       — Redis 기반 결제 타임아웃

Payment 도메인
├── PaymentController
├── PaymentService            — 승인/취소/실패 처리
├── Payment
├── PaymentClient → TossPaymentClient   — 전략 + 팩토리 패턴
├── PaymentValidator          — 상태/금액 검증
└── CancelPolicy              — 환불 정책 (배송 상태, 기간)
```

## 정리 — 분리는 "비용을 옮기는 행위"

도메인 분리는 복잡도를 없애는 작업이 아니다. **인프라가 부담하던 정합성 비용을 애플리케이션 영역으로 이동**시키는 작업이다. 그래서 분리 자체보다 더 중요한 것은 다음 네 가지를 동시에 명시적으로 설계했는가다.

1. **트랜잭션 경계** — 사용자의 시간이 흐르는 구간을 트랜잭션 밖으로 분리
2. **신뢰 매개체** — 분리된 트랜잭션을 잇는 불변 기록(pgOrderId + requestedAmount)
3. **의존 방향** — 호출의 무게에 따라 결합 강도를 차등 적용
4. **정책 소유권** — 변경 압력의 원천을 따라 정책 위치 결정

이 네 가지를 모두 통과한 분리는 단순한 패키지 분리와 본질적으로 다르다. 면접에서 "DDD를 적용했나요?"라는 질문을 받으면, 교과서적 정의 대신 **이 네 가지 설계 결정의 근거**를 답할 수 있다 — 그것이 이번 프로젝트가 도달한 도메인 설계의 깊이다.
