# 토스페이먼츠 결제 연동 — 포트폴리오/블로그 어필 포인트

## 1. 결제 금액 위변조 검증

클라이언트에서 금액을 조작하여 승인 요청하는 공격을 서버에서 방어한다. 주문 생성 시 requestedAmount를 DB에 저장해두고, 토스 리다이렉트로 넘어온 amount와 비교하여 불일치하면 결제를 거부한다.

왜 어필이 되는가:
- 대부분의 신입 프로젝트는 결제 기능 자체를 구현하지 않거나, 위변조 검증 없이 토스 응답만 믿고 처리한다
- 토스 공식문서에서도 "서버에서 반드시 검증하라"고 명시하는데, 이를 실제로 구현했다는 것은 보안 의식을 보여준다
- 면접에서 "결제 시 보안 위협과 대응 방안"을 물어보면 실제 경험 기반으로 답할 수 있다

---

## 2. 전략 + 팩토리 패턴으로 PG사 확장 설계

PaymentClient 인터페이스를 두고 TossPaymentClient가 구현하는 전략 패턴, PaymentClientFactory가 pgType으로 구현체를 선택하는 팩토리 패턴을 조합했다. 카카오페이 등 새로운 PG사 추가 시 구현체 클래스만 만들면 기존 코드 수정 없이 자동 등록된다.

왜 어필이 되는가:
- 단순히 "토스 연동했습니다"가 아니라 "확장 가능하게 설계했습니다"로 차별화
- OCP(개방폐쇄원칙)를 실제 코드에 적용한 사례
- 면접에서 "디자인 패턴을 실무에 어떻게 적용했나요?"에 구체적으로 답할 수 있다
- Spring의 List 주입 + Collectors.toMap으로 구현체를 자동 수집하는 패턴은 실무에서도 자주 사용된다

---

## 3. 결제 타임아웃 — Redis ZSET + Lua 스크립트

주문 생성 시 Redis ZSET에 30분 타임아웃 타이머를 등록하고, 결제 완료 시 제거한다. 스케줄러가 1분마다 만료된 주문을 폴링하여 자동 취소 + 재고 복구한다. Lua 스크립트로 ZRANGEBYSCORE + ZREM을 원자적으로 실행하여 다중 서버 환경에서 중복 처리를 방지한다.

왜 어필이 되는가:
- 결제를 안 하고 방치하는 주문의 재고를 자동 복구하는 운영 관점의 사고
- Redis Lua 스크립트로 원자적 연산을 구현한 것은 동시성 제어 역량을 보여준다
- DB 보정 스케줄러를 별도로 둔 것은 "Redis가 죽으면?"이라는 장애 시나리오까지 고려한 것
- 면접에서 "서버 장애 시 데이터 정합성을 어떻게 보장하나요?"에 실제 사례로 답할 수 있다

---

## 4. 트랜잭션 경계 설계 — 이벤트 기반 분리

결제 승인 API 호출(외부 HTTP)을 트랜잭션 안에서 하면 DB 커넥션 점유 시간이 길어진다. 주문 생성 시 Redis 타이머 등록을 @TransactionalEventListener(AFTER_COMMIT)으로 트랜잭션 밖으로 분리하여, 트랜잭션 롤백 시 Redis에 잘못된 데이터가 남는 것을 방지했다.

왜 어필이 되는가:
- "트랜잭션 안에서 외부 API를 호출하면 안 되는 이유"를 이해하고 있다는 것을 증명
- Spring Event + TransactionalEventListener 활용은 실무 수준의 아키텍처 패턴
- 대부분의 신입은 @Transactional을 메서드에 붙이는 것까지만 하는데, 트랜잭션 경계를 의식적으로 설계한 점이 차별화

---

## 5. 비관적 락 + Deadlock 방지 정렬

주문 시 여러 상품 옵션의 재고를 동시에 차감할 때, optionId 오름차순으로 락을 획득하여 deadlock을 방지한다. 주문 취소 시에도 같은 순서로 재고를 복구한다.

왜 어필이 되는가:
- 동시성 제어를 단순히 "락을 걸었다"가 아니라 "deadlock까지 고려했다"로 깊이를 보여준다
- 락 획득 순서를 통일하는 것은 데이터베이스 교과서적 해결법인데, 이를 실제 코드에 적용한 경험
- 면접에서 "동시에 같은 상품을 주문하면 어떻게 되나요?"라는 질문에 재고 정합성 + deadlock 방지까지 설명 가능

---

## 6. Secret Key 보안 처리

토스 시크릿키를 application.properties에서 관리하고, Base64 인코딩하여 Authorization 헤더에 담는다. 클라이언트에 절대 노출하지 않으며, pgOrderId를 UUID 기반으로 생성하여 DB의 auto increment PK가 외부에 노출되지 않도록 했다.

왜 어필이 되는가:
- 보안 의식이 있다는 것을 보여준다 (시크릿키 관리, PK 노출 방지)
- 추후 환경변수나 Vault로 전환하기 쉬운 구조로 설계
- 면접에서 "API 키를 어떻게 관리하나요?"에 답할 수 있다

## 7. 환불 정책 — Policy 패턴으로 비즈니스 규칙 분리

배송 상태에 따라 취소/환불 가능 여부를 CancelPolicy 클래스에서 판단한다. 배송 전은 취소 가능, 배송 중은 불가, 배송 완료 후 7일 이내만 환불 가능. 정책이 변경되면 Policy 클래스만 수정하면 된다.

왜 어필이 되는가:
- 비즈니스 규칙을 엔티티나 서비스가 아닌 독립 클래스로 분리하는 설계 판단력
- 환불 기간 변경, VIP 별도 정책 등 확장 시 기존 코드 수정 없이 대응 가능
- SRP 원칙 적용 — 엔티티는 상태 관리, Policy는 규칙 판단
- 면접에서 "환불 조건은 어떻게 관리하나요?"에 구체적으로 답할 수 있다

---

## 8. 결제 취소/부분 취소

토스 취소 API 하나로 전액 취소, 부분 취소, 환불을 모두 처리한다. 부분 취소 시 잔액을 관리하고, 잔액이 0이 되면 자동으로 전액 취소 상태로 전환한다.

왜 어필이 되는가:
- 부분 취소의 잔액 관리 로직은 실무에서 자주 요구되는 기능
- 단순한 전액 취소만 구현한 프로젝트와 차별화
- 면접에서 "부분 환불은 어떻게 처리하나요?"에 잔액 관리까지 설명 가능

---

## 10. 주문/결제 도메인 분리 — DDD 관점의 설계 판단

주문과 결제를 별도 도메인으로 분리하면서 의존 방향, 트랜잭션 경계, 정책 소속, 순환 의존 문제를 고민했다.

왜 어필이 되는가:
- "도메인 분리했습니다"가 아니라 "왜 이 경계로 나눴는가"를 근거와 함께 설명 가능
- 의존 방향 제어: Payment → Order 방향이 자연스러운 이유를 현실 모델로 설명
- 순환 의존 회피: PaymentService를 거치지 않고 PaymentRepository를 직접 사용한 판단 근거
- CancelPolicy를 Payment 도메인에 둔 이유: 호출하는 쪽의 응집도 기준
- 면접에서 "DDD를 어떻게 적용했나요?"에 구체적 사례로 답할 수 있다

## 면접 예상 질문과 답변 키워드

- "결제 시 보안은 어떻게 처리했나요?" → 위변조 검증, 시크릿키 서버 관리, PK 비노출
- "PG사가 추가되면 어떻게 대응하나요?" → 전략 + 팩토리 패턴, OCP, Spring List 주입
- "결제를 안 하고 방치하는 주문은요?" → Redis ZSET 타임아웃, 보정 스케줄러, 자동 재고 복구
- "동시 주문 시 재고 정합성은?" → 비관적 락, optionId 정렬 deadlock 방지
- "외부 API 장애 시 어떻게 되나요?" → 트랜잭션 분리, 이벤트 기반, 롤백 전략
- "결제 취소 조건은 어떻게 관리하나요?" → CancelPolicy 클래스, 배송 상태별 분기, 환불 기간 검증
- "부분 환불은 어떻게 처리하나요?" → 잔액 관리, 잔액 0이면 자동 전액 취소 전환
- "트랜잭션 범위를 어떻게 결정했나요?" → 작업별 안/밖 판단 기준, AFTER_COMMIT, readOnly, 커넥션 점유 트레이드오프
- "주문과 결제를 왜 분리했나요?" → 의존 방향 제어, 트랜잭션 경계 = 도메인 경계, 최종적 정합성
- "순환 의존은 어떻게 해결했나요?" → Repository 직접 사용, 이벤트 기반 대안과 트레이드오프
- "CancelPolicy는 왜 Payment 도메인에 있나요?" → 호출 시점 기준 응집도, Order 상태는 읽기만
