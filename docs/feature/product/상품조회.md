# 상품 조회 API 구현 정리

## 1. 전체 구조

```
ProductViewController (비인증 공개 API)
  → ProductViewService (조회 전용, readOnly)
    → ProductQueryRepository (목록 — QueryDSL 동적 쿼리)
    → ProductRepository (상세 — JPQL fetch join)
    → ProductOptionRepository (상세 — 옵션 조회)
```

상품 등록/재고 수정의 ProductService(Command)와 분리하여 CQRS 패턴을 적용했다.

### API

| Method | URL | 설명 |
|--------|-----|------|
| GET | `/api/v1/products` | 상품 목록 조회 (커서 페이징, 필터링) |
| GET | `/api/v1/products/{productId}` | 상품 상세 조회 (옵션 포함) |

## 2. ProductViewController

```java
@RestController
@RequestMapping("/api/v1/products")
@RequiredArgsConstructor
public class ProductViewController {

    private final ProductViewService productViewService;
```

- `@RequiredRole` 없음 — 비인증 공개 API. 로그인 없이 누구나 상품을 조회할 수 있어야 하므로 역할 검증을 걸지 않았다
- `ProductViewService`만 의존 — 조회 전용 서비스. ProductService(등록/재고)와 분리하여 책임을 명확히 했다
- WebConfig에서 `/api/v1/products/**`를 `excludePathPatterns`에 추가하여 AuthInterceptor 인증 검사도 제외했다

### 목록 조회 메서드

```java
@GetMapping
public ResponseEntity<ProductCursorResponse> getProducts(
        @RequestParam(required = false) Long cursor,
        @RequestParam(required = false) Long storeId,
        @RequestParam(required = false) MainCategory mainCategory,
        @RequestParam(required = false) SubCategory subCategory,
        @RequestParam(required = false) Integer size) {
    return ResponseEntity.ok(productViewService.getProducts(cursor, storeId, mainCategory, subCategory, size));
}
```

- 모든 파라미터가 `required = false` — 전부 선택적 필터. 아무것도 안 보내면 전체 상품, 조합하면 필터링
- `cursor` — 이전 응답의 `nextCursor` 값. 첫 페이지는 null
- `storeId` — 특정 스토어의 상품만 조회. 별도 API 없이 하나의 엔드포인트에서 처리
- `mainCategory`, `subCategory` — 카테고리 필터링. Spring이 문자열을 enum으로 자동 변환
- `size` — 페이지 크기. null이면 기본 20건
- 하나의 API로 전체 조회, 스토어별 조회, 카테고리별 조회, 조합 조회를 모두 처리한다

### 상세 조회 메서드

```java
@GetMapping("/{productId}")
public ResponseEntity<ProductResponse> getProduct(@PathVariable Long productId) {
    return ResponseEntity.ok(productViewService.getProduct(productId));
}
```

- `@PathVariable` — URL 경로에서 productId 추출
- 옵션(색상, 사이즈, 재고)을 포함한 상세 정보를 반환한다

## 3. ProductViewService

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class ProductViewService {

    private static final int DEFAULT_PAGE_SIZE = 20;
    private static final int MAX_PAGE_SIZE = 100;

    private final ProductRepository productRepository;
    private final ProductOptionRepository productOptionRepository;
    private final ProductQueryRepository productQueryRepository;
```

- `@Transactional(readOnly = true)` 클래스 레벨 — 이 서비스의 모든 메서드가 읽기 전용. dirty checking을 생략하고 읽기 전용 커넥션을 사용하여 조회 성능을 최적화. 추후 CQRS로 읽기 전용 Replica DB를 분리할 때 이 어노테이션 기반으로 라우팅 가능
- `DEFAULT_PAGE_SIZE = 20` — 패션 이커머스에서 이미지 기반 목록에 적합한 크기
- `MAX_PAGE_SIZE = 100` — 클라이언트가 `size=1000000`을 보내도 최대 100건으로 제한. OOM 방지
- 3개의 Repository를 의존 — 목록은 QueryDSL(ProductQueryRepository), 상세는 JPQL(ProductRepository) + 옵션(ProductOptionRepository)

### getProducts() — 목록 조회

```java
public ProductCursorResponse getProducts(Long cursor, Long storeId,
                                          MainCategory mainCategory,
                                          SubCategory subCategory, Integer size) {
    int pageSize = (size != null && size > 0) ? Math.min(size, MAX_PAGE_SIZE) : DEFAULT_PAGE_SIZE;
```

- `Math.min(size, MAX_PAGE_SIZE)` — size가 100을 초과하면 100으로 강제 제한. 양수가 아니면 기본값 20

```java
    List<Product> products = productQueryRepository.findProductsWithCursor(
            cursor, storeId, mainCategory, subCategory, pageSize + 1
    );
```

- `pageSize + 1` — 20건이 필요하면 21건을 조회. 21건이 오면 다음 페이지가 있는 것, 20건 이하면 마지막 페이지. COUNT 쿼리 없이 다음 페이지 존재 여부를 판별하는 방법

```java
    List<ProductListResponse> productList = products.stream()
            .map(ProductListResponse::from)
            .toList();
```

- 엔티티 → 경량 DTO 변환. 목록에서는 옵션을 포함하지 않아 N+1 문제를 원천 차단
- stream + map은 엔티티 → DTO 매핑에서 관례적이고 가독성이 좋다

```java
    return ProductCursorResponse.of(productList, pageSize);
}
```

- 커서 응답 DTO로 변환. products, nextCursor, hasNext를 포함

### getProduct() — 상세 조회

```java
public ProductResponse getProduct(Long productId) {
    Product product = productRepository.findByIdWithStore(productId)
            .orElseThrow(() -> new BusinessException(ErrorCode.PRODUCT_NOT_FOUND));
```

- `findByIdWithStore()` — Product와 Store를 fetch join으로 한 쿼리에 조회. Store를 별도 조회하면 추가 쿼리가 발생하므로 fetch join으로 방지
- 존재하지 않으면 `PRODUCT_NOT_FOUND(P002)` 예외

```java
    List<ProductOption> options = productOptionRepository.findByProductProductId(productId);
```

- 해당 상품의 옵션(색상, 사이즈, 재고) 조회. PK 기반 조회라 빠름
- 상세 조회에서만 옵션을 가져온다 (목록에서는 가져오지 않음)

```java
    return ProductResponse.from(product, options);
}
```

- Product + Options를 합쳐서 상세 응답 DTO로 변환
- 총 쿼리 2번: Product+Store fetch join 1번 + Options 1번

## 4. ProductQueryRepository (QueryDSL)

```java
@Repository
@RequiredArgsConstructor
public class ProductQueryRepository {

    private final JPAQueryFactory queryFactory;
```

- `@Repository` — Spring Data JPA의 Repository가 아닌 순수 Spring 빈. QueryDSL 전용
- `JPAQueryFactory` — QueryDSL의 쿼리 빌더. QueryDslConfig에서 빈으로 등록했다

### findProductsWithCursor()

```java
public List<Product> findProductsWithCursor(Long cursor, Long storeId,
                                             MainCategory mainCategory,
                                             SubCategory subCategory, int size) {
    QProduct product = QProduct.product;
    QStore store = QStore.store;
```

- `QProduct`, `QStore` — QueryDSL이 엔티티 기반으로 자동 생성하는 쿼리 타입. 컴파일 타임에 필드명 오타를 잡아준다

```java
    BooleanBuilder builder = new BooleanBuilder();

    if (cursor != null) {
        builder.and(product.productId.lt(cursor));
    }
```

- `BooleanBuilder` — 동적 WHERE 조건을 조립하는 빌더. null인 조건은 아예 쿼리에 포함하지 않는다
- `product.productId.lt(cursor)` — `WHERE product_id < cursor`. 커서 기반 페이징의 핵심. PK 인덱스를 타서 해당 위치로 바로 점프

```java
    if (storeId != null) {
        builder.and(product.store.storeId.eq(storeId));
    }
```

- storeId가 null이면 이 조건이 SQL에 안 붙음 → 전체 상품 조회
- storeId가 있으면 `WHERE store_id = ?` → 해당 스토어 상품만 조회
- 처음에 JPQL로 `(:storeId IS NULL OR p.store.storeId = :storeId)` 방식을 썼는데, Hibernate가 null 파라미터를 제대로 처리하지 못해서 QueryDSL로 전환했다

```java
    if (mainCategory != null) {
        builder.and(product.mainCategory.eq(mainCategory));
    }
    if (subCategory != null) {
        builder.and(product.subCategory.eq(subCategory));
    }
```

- 카테고리 필터링. 대분류만, 소분류만, 둘 다, 아무것도 안 보내기 모두 가능
- 각 조건이 독립적이라 어떤 조합이든 동적으로 처리된다

```java
    return queryFactory
            .selectFrom(product)
            .join(product.store, store).fetchJoin()
            .where(builder)
            .orderBy(product.productId.desc())
            .limit(size)
            .fetch();
}
```

- `.selectFrom(product)` — Product를 기준으로 조회
- `.join(product.store, store).fetchJoin()` — Store를 한 쿼리에 함께 가져옴. 목록 응답에 storeName이 필요한데 fetch join이 없으면 상품 N건마다 Store 조회 쿼리가 N번 발생(N+1)
- `.where(builder)` — 동적 조건 적용. 조건이 하나도 없으면 WHERE절 자체가 안 붙음
- `.orderBy(product.productId.desc())` — 최신순 정렬. PK DESC라 인덱스를 그대로 역순 스캔
- `.limit(size)` — JPQL에서는 LIMIT를 직접 쓸 수 없었는데, QueryDSL은 `.limit()`으로 간단히 처리
- `.fetch()` — 쿼리 실행 후 결과 리스트 반환

## 5. ProductRepository (JPQL)

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Query("SELECT p FROM Product p JOIN FETCH p.store WHERE p.productId = :productId")
    Optional<Product> findByIdWithStore(@Param("productId") Long productId);
}
```

- 상세 조회 전용 쿼리. Product와 Store를 fetch join으로 한번에 가져온다
- `findById()`를 쓰면 Product만 가져오고, 응답에서 `product.getStore().getName()` 호출 시 Store 조회 쿼리가 추가로 발생. fetch join으로 방지
- 상세 조회는 동적 필터가 없어서 JPQL로 충분. QueryDSL을 쓸 필요 없다

## 6. ProductOptionRepository

```java
public interface ProductOptionRepository extends JpaRepository<ProductOption, Long> {

    Optional<ProductOption> findByProductOptionIdAndProductProductId(Long optionId, Long productId);

    List<ProductOption> findByProductProductId(Long productId);
}
```

- `findByProductProductId()` — 상품 상세 조회 시 해당 상품의 옵션 목록을 가져온다. productId(FK) 기반 조회라 빠름
- `findByProductOptionIdAndProductProductId()` — 재고 수정 시 옵션이 해당 상품에 속하는지 검증하는 용도 (상품 조회와는 무관)
- 목록 조회에서는 이 Repository를 호출하지 않는다 — 옵션을 포함하지 않아 N+1 원천 차단

## 7. DTO

### ProductListResponse — 목록 전용 경량 DTO

```java
@Builder
public record ProductListResponse(
        Long productId,
        Long storeId,
        String storeName,
        String name,
        MainCategory mainCategory,
        SubCategory subCategory,
        Integer price,
        String imageUrl
) {
    public static ProductListResponse from(Product product) {
        return ProductListResponse.builder()
                .productId(product.getProductId())
                .storeId(product.getStore().getStoreId())
                .storeName(product.getStore().getName())
                .name(product.getName())
                .mainCategory(product.getMainCategory())
                .subCategory(product.getSubCategory())
                .price(product.getPrice())
                .imageUrl(product.getImageUrl())
                .build();
    }
}
```

- 옵션(options), 설명(description), 생성일(createdAt)을 포함하지 않는다 — 목록에서 불필요한 데이터를 빼서 네트워크 전송량 감소
- `product.getStore().getStoreId()` — fetch join으로 Store가 이미 로딩되어 있어 추가 쿼리 없음
- 상세 조회의 ProductResponse와 분리한 이유: 목록에 옵션을 포함하면 상품 1건당 옵션 조회 쿼리가 발생하여 N+1 문제가 생긴다

### ProductCursorResponse — 커서 페이징 응답

```java
@Builder
public record ProductCursorResponse(
        List<ProductListResponse> products,
        Long nextCursor,
        boolean hasNext
) {
    public static ProductCursorResponse of(List<ProductListResponse> products, int size) {
        boolean hasNext = products.size() > size;
```

- `products.size() > size` — 21건이 왔으면 다음 페이지 있음(true), 20건 이하면 마지막(false)
- COUNT 쿼리 없이 1건만 더 읽어서 판별. 100만건에서 COUNT 쿼리 한번을 아끼는 건 의미가 크다

```java
        List<ProductListResponse> content = hasNext
                ? products.subList(0, size)
                : products;
```

- hasNext가 true면 초과분 1건을 잘라내서 요청한 size만큼만 반환

```java
        Long nextCursor = hasNext
                ? content.get(content.size() - 1).productId()
                : null;
```

- 다음 페이지가 있으면 마지막 상품의 productId가 nextCursor
- 프론트는 이 값을 `?cursor=` 파라미터로 보내서 다음 페이지를 요청한다
- 마지막 페이지면 null — 프론트는 null이면 더 이상 요청하지 않는다

```java
        return ProductCursorResponse.builder()
                .products(content)
                .nextCursor(nextCursor)
                .hasNext(hasNext)
                .build();
    }
}
```

### ProductResponse — 상세 조회 응답

```java
@Builder
public record ProductResponse(
        Long productId,
        Long storeId,
        String storeName,
        String name,
        MainCategory mainCategory,
        SubCategory subCategory,
        String description,
        Integer price,
        String imageUrl,
        LocalDateTime createdAt,
        List<ProductOptionResponse> options
) {
    public static ProductResponse from(Product product, List<ProductOption> options) {
        return ProductResponse.builder()
                .productId(product.getProductId())
                .storeId(product.getStore().getStoreId())
                .storeName(product.getStore().getName())
                .name(product.getName())
                .mainCategory(product.getMainCategory())
                .subCategory(product.getSubCategory())
                .description(product.getDescription())
                .price(product.getPrice())
                .imageUrl(product.getImageUrl())
                .createdAt(product.getCreatedAt())
                .options(options.stream()
                        .map(ProductOptionResponse::from)
                        .toList())
                .build();
    }
}
```

- 목록 DTO와 달리 description, createdAt, options를 포함한다 — 상세 페이지에서 필요한 정보
- `options.stream().map(ProductOptionResponse::from)` — 옵션 엔티티 리스트를 DTO 리스트로 변환
- Product와 Options를 별도 쿼리로 가져온 뒤 이 DTO에서 합친다

## 8. 실행 플로우

### 목록 조회

```
GET /api/v1/products?mainCategory=SHOES&size=20

  ProductViewController.getProducts()
    → cursor=null, storeId=null, mainCategory=SHOES, subCategory=null, size=20

  ProductViewService.getProducts()
    → pageSize = Math.min(20, 100) = 20

  ProductQueryRepository.findProductsWithCursor()
    → BooleanBuilder에 mainCategory=SHOES 조건만 추가 (나머지 null이라 안 붙음)
    → SELECT p FROM products p
        JOIN stores s ON p.store_id = s.store_id
        WHERE p.main_category = 'SHOES'
        ORDER BY p.product_id DESC
        LIMIT 21
    → 쿼리 1번

  ProductListResponse.from() × 21건 → DTO 변환

  ProductCursorResponse.of(21건, 20)
    → hasNext = true (21 > 20)
    → content = 앞 20건
    → nextCursor = 20번째 상품의 productId

  응답:
  {
    "products": [...20건],
    "nextCursor": 980,
    "hasNext": true
  }
```

### 상세 조회

```
GET /api/v1/products/1

  ProductViewController.getProduct()
    → productId = 1

  ProductViewService.getProduct()
    → productRepository.findByIdWithStore(1)
      → SELECT p.*, s.* FROM products p
          JOIN stores s ON p.store_id = s.store_id
          WHERE p.product_id = 1
      → 쿼리 1번 (Product + Store fetch join)

    → productOptionRepository.findByProductProductId(1)
      → SELECT * FROM products_options WHERE product_id = 1
      → 쿼리 2번 (Options)

  ProductResponse.from(product, options) → DTO 변환

  응답:
  {
    "productId": 1,
    "storeId": 1,
    "storeName": "길동의 옷가게",
    "name": "나이키 에어맥스",
    "options": [
      { "productOptionId": 1, "color": "BLACK", "size": "270", "stockQuantity": 50 },
      ...
    ]
  }
```

## 9. 성능 설계 요약

| 설계 | 효과 |
|------|------|
| 커서 페이징 | 100만건에서도 ~100ms 일정한 성능 (Offset은 ~2초) |
| fetch join | Store 추가 조회 쿼리 방지 |
| 경량 목록 DTO | 옵션 미포함으로 N+1 원천 차단 |
| QueryDSL 동적 쿼리 | null 필터 정확 처리 + LIMIT 지원 |
| `@Transactional(readOnly = true)` | dirty checking 생략, 읽기 전용 커넥션 |
| size + 1 조회 | COUNT 쿼리 없이 hasNext 판별 |
| MAX_PAGE_SIZE 제한 | 클라이언트 악용으로 인한 OOM 방지 |
| CQRS 서비스 분리 | 조회와 등록/수정의 책임 분리, 추후 DB 분리 기반 |
