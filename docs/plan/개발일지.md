# StyleHub 개발일지

## 프로젝트 개요

- **프로젝트**: StyleHub — 대용량 트래픽 이커머스 플랫폼
- **기술 스택**: Spring Boot 4.0, JPA/QueryDSL, MySQL, Redis, 토스페이먼츠
- **설계 기준**: 대용량 트래픽, 확장 가능한 구조, 읽기 쉬운 코드

---

## 1단계: 프로젝트 셋업 + 엔티티 설계

### 작업 내용
- Spring Boot 프로젝트 생성, MySQL + JPA 설정
- ERD 기반으로 전체 도메인 엔티티 생성 (User, Product, Order, Payment, Store, Coupon, Point)
- `BaseEntity`로 createdAt/updatedAt 공통 관리 (@SuperBuilder 상속 지원)
- `ddl-auto=validate`로 설정하여 엔티티와 DB 스키마 불일치 시 즉시 감지

### 멘토님 피드백 반영
- ⭐ 와일드카드 import(`jakarta.persistence.*`) → 명시적 import로 전부 교체
- 모든 Java 파일에 Javadoc 헤더 필수 추가 (작성자, 생성일, 역할 설명)

## 2단계: 회원 API + OAuth

### 작업 내용
- 일반 회원가입/로그인 API (BCrypt 비밀번호 해싱)
- Google OAuth 소셜 로그인 연동
- HTTP 세션 기반 인증 (AuthInterceptor)
- 역할 기반 권한 체크 (@RequiredRole + RoleCheckInterceptor)

### 설계 결정
- ⭐ BCrypt 해싱을 트랜잭션 밖에서 실행 — DB 커넥션 점유 방지
- ⭐ 로그인 포인트 지급을 이벤트 기반(@TransactionalEventListener)으로 변경 — user-point 도메인 간 결합 제거
- OAuthController를 UserController로 통합 (멘토님 피드백: 컨트롤러 수 줄이기)
- Provider → OAuthProvider로 리네이밍 (도메인 책임 명확화)

## 5단계: 상품 등록/조회 API

### 작업 내용
- STORE 역할의 상품 등록, 재고 관리 API
- 공개 상품 목록 조회 (커서 기반 페이징, QueryDSL 동적 필터)
- 상품 상세 조회 (Store + Options JOIN FETCH 한방 쿼리)

### 멘토님 피드백 반영
- ⭐ ProductViewService → ProductService로 통합, ProductViewController → ProductController로 통합
- ⭐ `size` 파라미터명 → `pageSize`로 변경 (의미 명확화)
- ⭐ ProductCursorResponse → CursorResponse<T> 제네릭으로 공통화 (도메인 간 중복 제거)
- 상품 단건 조회 시 옵션 별도 조회 제거 → JOIN FETCH로 한방 쿼리 변경
- ProductQueryRepository에 오버로딩 메서드 추가하여 null 파라미터 제거

### 시행착오
- ⭐ Custom Repository 패턴으로 ProductQueryRepository 통합 시도 → 오히려 파일이 늘어나서 되돌림
- JPQL vs QueryDSL 통일 시도 → ProductRepository는 save/delete에 JpaRepository 필수라서 불가능, 되돌림

## 6단계: 주문 생성 + 주문 내역 조회 API

### 작업 내용
- 주문 생성 API (비관적 락 재고 차감)
- 주문 내역 목록 조회 (커서 페이징, 총액 배치 조회로 N+1 방지)
- 주문 상세 조회 (본인 주문만 접근)

### 설계 결정
- ⭐ deadlock 방지를 위해 optionId 오름차순으로 락 획득 순서 통일 (차감/복구 모두)
- ⭐ 같은 옵션 수량 합산 (mergeAndSort) — TreeMap으로 합산 + 정렬 동시 처리
- createOrder → placeOrder 네이밍 변경 (Order.create()와 역할 구분)

### 멘토님 피드백 반영
- ⭐ OrderService 3개(OrderService + OrderTransactionService + OrderViewService) → 1개로 통합
- ⭐ "클래스가 많아지면 관리 힘들고, 테스트 코드 짜기 어렵다"
- OrderCursorResponse → CursorResponse<T>로 대체
- Object[] 캐스팅 → OrderTotalAmountDto 프로젝션으로 타입 안전성 확보
- buildOrderResponse()로 응답 변환 중복 제거
- restoreStock()으로 재고 복구 로직 분리

## 7단계: 결제 타임아웃 (Redis ZSET + Lua 스크립트)

### 작업 내용
- 주문 생성 시 Redis ZSET에 10분 타임아웃 타이머 등록
- 스케줄러가 1분마다 만료 주문 폴링 → 자동 취소 + 재고 복구
- DB 보정 스케줄러 (1시간마다, Redis 장애 대비)

### 설계 결정
- ⭐ Lua 스크립트로 ZRANGEBYSCORE + ZREM 원자적 실행 — 다중 서버 중복 처리 방지
- ⭐ @TransactionalEventListener(AFTER_COMMIT)으로 Redis 등록 — 롤백 시 Redis 오염 방지
- ⭐ Redis 스케줄러(1차 방어) + DB 보정 스케줄러(2차 방어) 이중 안전장치
- OrderTimeoutManager → OrderPaymentTimeout 네이밍 변경

### 멘토님 피드백 반영
- 타임아웃 폴링 주기 1초 → 1분으로 변경 (30분 타임아웃에 1초 간격은 과도)
- 타임아웃 30분 → 10분으로 단축 (토스 결제 세션 유효시간 10분 기준)

## 8단계: 토스페이먼츠 결제 연동 ⭐⭐⭐

### 작업 내용
- 결제 승인 API (GET /api/v1/payments/success)
- 결제 실패 처리 (GET /api/v1/payments/fail)
- 결제 취소 API (POST /api/v1/payments/{paymentId}/cancel)
- 결제 테스트용 HTML 페이지 (토스 JS SDK v2)

### 설계 결정
- ⭐ 주문/결제 트랜잭션 분리 — 사용자 결제 인증 시간 동안 DB 커넥션 점유 방지
- ⭐ pgOrderId + requestedAmount로 두 트랜잭션 간 정합성 보장 (위변조 검증)
- ⭐ 전략 + 팩토리 패턴으로 PG사 확장 구조 (PaymentClient 인터페이스 + PaymentClientFactory)
  - Spring List 주입으로 구현체 자동 수집, 새 PG사 추가 시 기존 코드 수정 0줄
- ⭐ 금액 위변조 검증 — DB 저장 금액 vs 토스 전달 금액 비교
- 토스 API를 트랜잭션 안에서 호출 — 실패 시 상태 변경 자동 롤백 (트레이드오프: 커넥션 점유, 허용 가능 판단)
- paymentKey는 토스 인증 완료 후 발급 → approve() 시 저장

### 시행착오
- ⭐ paymentKey를 빈 문자열("")로 저장 → 취소 시 토스 API URL이 깨지는 버그 발견 → approve()에서 paymentKey 저장하도록 수정
- 토스 취소 URL 하드코딩 → application.properties로 분리

## 9단계: 결제 취소/환불 정책

### 작업 내용
- 전액 취소 시 주문 취소 + 재고 복구
- 부분 취소 잔액 관리 (잔액 0이면 자동 전액 취소 전환)
- 배송 상태별 환불 가능 여부 검증

### 설계 결정
- ⭐ CancelPolicy로 환불 정책을 독립 클래스로 분리
  - 배송 전(PREPARING): 취소 가능
  - 배송 중(SHIPPING): 취소 불가
  - 배송 완료(DELIVERED) + 7일 이내: 환불 가능
  - 7일 초과: 환불 불가
- ⭐ PaymentValidator로 검증 로직 분리 (상태/금액/잔액 검증)
- cancelOrderIfFullyCanceled() 메서드로 분기 로직 캡슐화

### 설계 고민
- 부분 취소 시 "어떤 상품의 재고를 복구할지" 판단 불가 → 전액 취소만 재고 복구, 부분 취소는 TODO

## 10단계: 도메인 분리 (Order ↔ Payment) ⭐⭐

### 설계 결정
- ⭐ OrderService → PaymentRepository 직접 의존 제거 → 이벤트 기반으로 분리
  - OrderCreatedEvent 하나로 두 리스너가 동작
  - BEFORE_COMMIT: PaymentReadyEventListener → Payment READY 생성 (같은 트랜잭션)
  - AFTER_COMMIT: OrderCreatedEventListener → Redis 타임아웃 등록 (트랜잭션 밖)
- ⭐ 순환 의존 방지: OrderService → PaymentService 호출 대신 이벤트로 분리
- 의존 방향: Payment → Order (결제 실패 시 주문 취소, 보상 트랜잭션)

### 왜 이렇게 했는가
- OrderService가 PaymentRepository를 직접 의존하면 도메인 경계 침범
- PaymentService를 호출하면 순환 의존 (OrderService → PaymentService → OrderService)
- 이벤트로 분리하면 OrderService가 Payment 도메인을 완전히 모르게 됨

## 12단계: 상품 찜하기 API

### 작업 내용
- 상품 찜하기/취소 API (POST/DELETE /products/{productId}/likes)
- 내 찜 상품 목록 조회 (커서 페이징)
- 상품 조회 응답에 likeCount 필드 추가

### 설계 결정
- ⭐ 중복 찜 방지: DB unique 제약 (userId + productId) + DataIntegrityViolationException
- ⭐ likeCount 증감: `UPDATE SET like_count = like_count + 1` DB 원자적 쿼리 (락 불필요)
- 좋아요는 재고와 다르게 오차가 비즈니스에 영향 없으므로 비관적 락/분산 락 불필요

### 시행착오
- likes 도메인을 별도 패키지로 만들었다가 → Product/Store 도메인에 각각 배치하는 게 자연스러워서 이동

## 전체 설계 원칙 (프로젝트 전반에 적용)

### 대용량 트래픽
- 비관적 락 + deadlock 방지 정렬
- 커서 기반 페이징 (OFFSET 없이 일정 성능)
- @Transactional(readOnly = true) 더티체킹 스킵
- 트랜잭션 범위 최소화 (외부 API, Redis 호출을 밖으로)

### 확장성
- 전략 + 팩토리 패턴 (PG사 확장)
- Policy 패턴 (CancelPolicy, DeliveryPolicy)
- CursorResponse<T> 제네릭 공통화
- 이벤트 기반 도메인 분리

### 코드 품질
- 메서드명으로 의도 표현 (validateApprovedStoreOwner, cancelOrderIfFullyCanceled)
- 책임 분리 (Service: 흐름 조율, Validator: 검증, Policy: 규칙, Client: 외부 호출, Entity: 상태 변경)
- 에러코드 도메인별 접두사 분리

### 멘토님 핵심 피드백
- "클래스가 많아지면 관리 힘들고 테스트 어렵다" → 서비스/컨트롤러 통합
- "중복코드를 줄여라" → CursorResponse 제네릭, createAuthHeaders 추출
- "대입을 안 하는데 왜 호출하냐" → 검증 전용 메서드 분리
- "추상화를 진행해라" → CursorResponse<T> 공통화 (실제 중복이 있는 곳만)
