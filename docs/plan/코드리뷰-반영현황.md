## PR — 상품 조회 캐시 확대 (`refactor :상품조회 캐시 확대 + sync=true`)

| 리뷰 내용 | 반영 여부 | 비고 |
|---|---|---|
| `@Cacheable(sync = true)` 는 단일 JVM 락 — 다중 인스턴스 환경에서 cache miss 가 인스턴스 수만큼 DB 로 전파됨, 진짜 stampede 방어가 필요하면 Redisson 분산 락 기반 캐시 로직 필요 | ⏸️ 보류 (성능 테스트 이후 결정) | 리뷰어가 "추후 성능 테스트 이후 필요 시" 로 명시. 현재 단일 서버 환경이라 `sync = true` 는 정상 작동. 다중 인스턴스 부하 테스트에서 cache miss 시 DB 쿼리 수가 인스턴스 수만큼 늘어나는지 실측 후 Redisson 도입 여부 결정. todo.md "대용량 트래픽 (성능)" 섹션에 추적 항목 등록 완료 |

**향후 계획**
1. 다중 인스턴스(2대 이상) 환경 구축
2. Locust 부하 테스트로 TTL 만료 순간의 DB 쿼리 수 측정 (1대 vs 2대 비교)
3. 인스턴스 배수만큼 쿼리가 늘어나면 Redisson `RReadWriteLock` 기반 캐시 레이어로 전환
4. 영향이 작다면 `sync = true` 유지 (Redisson 도입 시 락 타임아웃·해제 누락 등 새 복잡도 발생)

이 프로젝트의 의사결정 원칙(추측이 아닌 측정)을 따라, 부하 테스트 결과가 나오기 전엔 코드 변경 없이 메모만 유지한다.

## 개선 방향

### 즉시 반영 가능
1. `DEFAULT_PAGE_SIZE` → `PRODUCT_PAGE_SIZE` 네이밍 변경 (PR #21 미반영)
2. 분산락 키 prefix `lock_optionId:` 형식 확인 및 수정 (PR #29)
3. 조건문 단일 라인 `{}` 제거 검토 (PR #21)

### 중기 과제
4. Redisson 분산락 전환 — 현재 StringRedisTemplate 직접 구현 → Redisson tryLock()으로 단순화
5. N+1 모니터링 자동화 — p6spy 또는 datasource-proxy 적용
6. confirmPayment 메서드명 확인 및 통일

### 장기 과제
7. Bearer/Grant 인증 방식 학습 정리
8. expires_in 활용 및 Redis 세션 전환 시점 정리
9. 성능 테스트 후 분산락 waitTime/leaseTime 최적값 재조정
