# @Transactional 범위를 고민한 과정

## 왜 트랜잭션 범위가 중요한가

트랜잭션이 시작되면 DB 커넥션을 점유한다.
트랜잭션이 끝날 때까지 커넥션을 반환하지 않는다. 
대용량 트래픽에서 트랜잭션이 오래 열려있으면 커넥션 풀이 고갈되어 다른 요청이 커넥션을 얻지 못하고 대기한다.

StyleHub을 개발하면서 트랜잭션 범위를 어떻게 잡을지 세 번 고민했다.

---

## 1단계: TransactionTemplate으로 시작

처음에는 `TransactionTemplate`으로 트랜잭션 범위를 직접 제어했다.
회원가입에서 BCrypt 해싱이 트랜잭션 안에 있으면 안 됐기 때문이다.

```java
public User signUp(String name, String email, String password, ...) {
    // BCrypt 해싱 (~100ms) — 트랜잭션 밖
    String hashedPassword = passwordHasher.hash(password);

    // DB 작업만 트랜잭션
    return transactionTemplate.execute(status -> {
        userValidator.validateSignUp(email, name);
        User user = User.create(name, email, hashedPassword, ...);
        return userRepository.save(user);
    });
}
```

BCrypt는 의도적으로 느린 알고리즘이라 약 100ms 소요된다. `@Transactional`을 메서드에 붙이면 해싱 동안에도 DB 커넥션을 점유한다. 동시에 100명이 회원가입하면 100개의 커넥션이 100ms씩 점유되어 커넥션 풀이 고갈될 수 있다.

`TransactionTemplate`으로 해싱은 밖에서, INSERT만 트랜잭션 안에서 실행하여 커넥션 점유 시간을 최소화했다.

### 장점
- 트랜잭션 범위를 코드 블록 단위로 정밀 제어
- 트랜잭션 밖에서 할 작업을 명확히 분리

### 단점
- `Objects.requireNonNull(transactionTemplate.execute(...))`로 코드가 장황해짐
- 두 객체를 반환하려면 `record`를 메서드 안에 선언해야 함
- 테스트 시 TransactionTemplate을 모킹해야 하는 번거로움

## 2단계: 주문 API에서 @Transactional로 전환

주문 생성 API를 만들면서 `@Transactional`로 전환했다. 
주문 생성에는 트랜잭션 밖에서 할 작업이 없었기 때문이다.

```java
// TransactionTemplate 방식 — 장황함
public OrderResponse createOrder(Long userId, OrderCreateRequest request) {
    record CreateResult(Order order, List<OrderItem> items) {}

    CreateResult result = Objects.requireNonNull(
            transactionTemplate.execute(status -> {
                User user = userService.findUserById(userId);
                Address address = userService.findAddressByOwner(userId, request.addressId());
                Order savedOrder = orderRepository.save(Order.create(user, address));
                List<OrderItem> savedItems = decreaseStockAndCreateItems(savedOrder, request.items());
                return new CreateResult(savedOrder, savedItems);
            })
    );

    return OrderResponse.from(result.order(), result.items());
}

// @Transactional 방식 — 깔끔함
@Transactional
public OrderResponse createOrder(Long userId, OrderCreateRequest request) {
    Address address = userService.findAddressByOwner(userId, request.addressId());
    User user = address.getUser();

    Order savedOrder = orderRepository.save(Order.create(user, address));
    List<OrderItem> savedItems = decreaseStockAndCreateItems(savedOrder, request.items());

    return OrderResponse.from(savedOrder, savedItems);
}
```

`record CreateResult`도 필요 없고, `Objects.requireNonNull`도 필요 없다. 코드가 훨씬 읽기 쉬워졌다.

### 그런데 문제가 보였다

토스페이먼츠 결제를 연동하면 이렇게 된다:

```java
@Transactional
public OrderResponse createOrder(...) {
    // DB 작업 — 빠름
    Order order = ...;
    decreaseStock(...);

    // 외부 API 호출 — 수초 소요
    paymentClient.confirm(order.getPgOrderId(), ...);  // 이 시간 동안 커넥션 점유
}
```

외부 HTTP 호출이 트랜잭션 안에서 실행되면 결제 대기(수초) 동안 DB 커넥션을 점유한다. 대용량 트래픽에서 동시에 100명이 주문하면 100개의 커넥션이 수초씩 잠긴다.

## 3단계: 서비스 분리로 해결

`@Transactional`의 깔끔함을 유지하면서 트랜잭션 범위를 제어하기 위해 **서비스를 분리**했다.

```
OrderService              — 흐름 관리 (트랜잭션 없음)
OrderTransactionService   — DB 작업 (@Transactional)
```

```java
// OrderTransactionService — 트랜잭션 담당
@Transactional
public OrderResponse createOrder(Long userId, OrderCreateRequest request) {
    Address address = userService.findAddressByOwner(userId, request.addressId());
    User user = address.getUser();

    Order savedOrder = orderRepository.save(Order.create(user, address));
    List<OrderItem> savedItems = decreaseStockAndCreateItems(savedOrder, request.items());

    return OrderResponse.from(savedOrder, savedItems);
}

// OrderService — 흐름 관리
public OrderResponse createOrder(Long userId, OrderCreateRequest request) {
    // 1. 트랜잭션: 주문 생성 + 재고 차감
    OrderResponse order = orderTransactionService.createOrder(userId, request);

    // 2. 트랜잭션 밖: 외부 API 호출 (커넥션 점유 안 함)
    // paymentClient.confirm(order.pgOrderId(), order.totalAmount());

    return order;
}
```

### 왜 같은 클래스에서 분리하면 안 되는가

Spring의 `@Transactional`은 프록시 기반으로 동작한다. 같은 클래스 내에서 `@Transactional` 메서드를 호출하면 프록시를 거치지 않아 **트랜잭션이 적용되지 않는다.**

```java
// 같은 클래스 — @Transactional 안 먹음
public class OrderService {
    public OrderResponse createOrder(...) {
        createOrderTransaction(...); // this.createOrderTransaction() → 프록시 우회
    }

    @Transactional  // 적용 안 됨!
    public OrderResponse createOrderTransaction(...) { ... }
}
```

Spring은 빈을 등록할 때 프록시 객체를 만든다. 외부에서 `orderService.createOrderTransaction()`을 호출하면 프록시를 거쳐 트랜잭션이 시작된다. 하지만 클래스 내부에서 `this.createOrderTransaction()`을 호출하면 프록시가 아닌 실제 객체를 호출하므로 트랜잭션이 적용되지 않는다.

별도 클래스로 분리하면 `orderTransactionService.createOrder()`가 프록시를 거쳐 호출되므로 `@Transactional`이 정상 동작한다.

## 각 방식을 언제 써야 하는가

| 방식 | 적합한 상황 |
|------|------------|
| `@Transactional` | 메서드 전체가 트랜잭션이면 되는 경우. 가장 깔끔 |
| `TransactionTemplate` | 트랜잭션 밖에서 할 작업이 있고, 클래스 분리가 과한 경우 (회원가입의 BCrypt 해싱) |
| 서비스 분리 | 트랜잭션 안팎 작업이 모두 있고, @Transactional의 깔끔함을 유지하고 싶은 경우 |

StyleHub에서는 세 가지를 모두 사용한다:

```
UserService.signUp()           — TransactionTemplate (BCrypt 해싱 분리)
StoreAdminService.approve()    — TransactionTemplate (상태 변경 범위 제어)
OrderTransactionService        — @Transactional + 서비스 분리 (결제 연동 대비)
ProductViewService             — @Transactional(readOnly = true) (조회 최적화)
```

## @Transactional(readOnly = true)

조회 전용 메서드에는 `readOnly = true`를 붙인다.

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)  // 클래스 레벨
public class ProductViewService {

    public ProductCursorResponse getProducts(...) { ... }
    public ProductResponse getProduct(Long productId) { ... }
}
```

효과:
- **dirty checking 생략** — JPA가 엔티티 변경 감지를 안 하므로 메모리와 CPU 절약
- **읽기 전용 커넥션** — DB에 따라 읽기 전용 커넥션 풀을 사용하여 쓰기 커넥션 부하 감소
- **Replica DB 라우팅 기반** — 추후 CQRS로 읽기/쓰기 DB를 분리할 때 이 어노테이션 기반으로 라우팅 가능

클래스 레벨에 붙이면 모든 메서드에 적용된다. ProductViewService는 조회만 하는 서비스라 클래스 레벨이 적합하다.

## 트랜잭션 범위와 커넥션 점유 비교

동시에 100명이 회원가입하는 상황을 가정한다:

### @Transactional (메서드 전체)
```
트랜잭션 시작 → BCrypt 해싱 (100ms) → 검증 → INSERT → 트랜잭션 종료
커넥션 점유: ~110ms
100명 × 110ms = 커넥션 11초 점유
```

### TransactionTemplate (DB 작업만)
```
BCrypt 해싱 (100ms) → 트랜잭션 시작 → 검증 → INSERT → 트랜잭션 종료
커넥션 점유: ~10ms
100명 × 10ms = 커넥션 1초 점유
```

**11배 차이.** HikariCP 기본 커넥션 풀 크기가 10개인데, 첫 번째 방식은 10명만 동시 처리 가능하고 나머지 90명은 커넥션 대기한다. 두 번째 방식은 100명을 거의 동시에 처리할 수 있다.

## 주문 생성에서의 트랜잭션 범위

주문 생성의 최종 구조:

```
OrderService.createOrder()                    ← 트랜잭션 없음
  │
  ├─ orderTransactionService.createOrder()    ← @Transactional
  │    ├─ 배송지 + 유저 조회 (fetch join)
  │    ├─ 주문 생성 (INSERT)
  │    ├─ 재고 차감 (SELECT FOR UPDATE + UPDATE) × N
  │    └─ 주문 항목 저장 (INSERT 배치)
  │
  ├─ paymentClient.confirm()                  ← 트랜잭션 밖 (추후)
  │    └─ 토스 결제 API 호출 (수초)
  │
  └─ 결제 실패 시 취소 + 재고 복구            ← 별도 트랜잭션 (추후)
```

DB 작업만 트랜잭션에 묶고, 외부 API 호출은 밖에서 처리한다. 결제 API가 수초 걸려도 DB 커넥션은 이미 반환된 상태다.

## 정리

| 고민 | 선택 | 이유 |
|------|------|------|
| BCrypt가 트랜잭션 안에 있으면? | TransactionTemplate으로 분리 | 100ms 커넥션 점유 방지 |
| 주문 생성에 트랜잭션 밖 작업이 없으면? | @Transactional | 코드 깔끔 |
| 결제 연동으로 외부 API가 추가되면? | 서비스 분리 | @Transactional 유지 + 결제는 밖 |
| 같은 클래스에서 분리하면? | 프록시 안 먹음 | 별도 클래스 필수 |
| 조회 전용이면? | readOnly = true | dirty checking 생략 + 읽기 전용 커넥션 |

트랜잭션 범위는 "가능한 짧게, 필요한 만큼만"이 원칙이다. DB 작업만 트랜잭션에 넣고, 해싱이나 외부 API 같은 느린 작업은 밖에서 처리한다. 이 원칙을 지키면 대용량 트래픽에서도 커넥션 풀이 고갈되지 않는다.
