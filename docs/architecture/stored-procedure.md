# DB Stored Procedure — 무엇이고 왜 있고 요즘은 어떻게 쓰이는가

## 한 줄로 정의하면

**Stored Procedure(저장 프로시저)는 DB 안에 이름을 붙여 저장해둔 SQL 명령어 묶음이다.** 평범한 SQL은 매번 작성해서 날리지만, 프로시저는 한 번 만들어두면 함수 호출하듯 `CALL 프로시저_이름(파라미터)` 한 줄로 DB가 해당 로직을 실행한다. 여러 SQL 문을 묶을 수 있고, 변수·조건문·반복문 같은 제어 구조도 쓸 수 있어서 **DB 안에서 돌아가는 작은 프로그램** 에 가깝다.

간단한 MySQL 예시 하나를 보면 감이 온다.

```sql
CREATE PROCEDURE transfer_points(
    IN from_user_id BIGINT,
    IN to_user_id BIGINT,
    IN amount INT
)
BEGIN
    START TRANSACTION;
    UPDATE users SET point_balance = point_balance - amount WHERE user_id = from_user_id;
    UPDATE users SET point_balance = point_balance + amount WHERE user_id = to_user_id;
    INSERT INTO point_history(from_user_id, to_user_id, amount) VALUES (from_user_id, to_user_id, amount);
    COMMIT;
END;

-- 호출
CALL transfer_points(1, 2, 1000);
```

원래 같으면 애플리케이션 코드에서 UPDATE 두 번 + INSERT 한 번을 각각 쿼리로 날려야 했을 일을, **DB에 한 번만 호출해서 끝낸다.** 트랜잭션 시작과 커밋까지 DB 안에 담겨 있다.

---

## 왜 이게 나왔는가 — 역사적 배경

프로시저는 **클라이언트 ↔ DB 간 네트워크 왕복이 비쌌던 시절** 에 큰 장점이 있었다. 주문 처리 같은 복잡한 트랜잭션이 SQL 다섯 개로 구성돼 있다고 하면, 클라이언트는 매번 네트워크를 타고 DB에 다녀와야 했다. 프로시저로 묶어두면 **한 번의 왕복으로 다섯 개 쿼리를 다 실행** 하니까 지연이 크게 줄었다. 2000년대 초반까지만 해도 비즈니스 로직 상당 부분을 DB 프로시저로 작성하는 게 흔한 설계였다.

또 하나의 이유는 **실행 계획 캐싱** 이다. DB는 SQL을 받으면 파싱하고 최적화된 실행 계획을 세우는데, 프로시저는 이 계획을 처음 컴파일한 뒤 캐시해두고 재사용한다. 같은 쿼리를 반복해서 날리는 것보다 이론상 빠르다는 주장이 있었다. 현대 DB는 prepared statement로도 비슷한 효과를 내지만, 당시에는 유효한 근거였다.

**보안** 도 중요한 동기였다. 애플리케이션 계정에 테이블에 대한 직접 권한을 주지 않고, **프로시저 실행 권한만 부여** 하는 방식이다. 이러면 개발자가 실수로든 악의로든 테이블을 통째로 DELETE할 수 없고, DB 관리자가 허용한 프로시저로만 데이터를 건드릴 수 있다. SQL Injection에 대한 방어도 파라미터 바인딩 덕분에 상대적으로 안전했다.

---

## 장점 정리

네트워크 왕복 감소, 실행 계획 캐시, 재사용성, 보안 계층, 복잡한 트랜잭션을 DB 안에서 원자적으로 묶을 수 있다는 것이 전통적인 장점이다. 특히 **대량 데이터 처리**(예: 수백만 건 집계 → 결과 테이블 저장) 같은 작업은 애플리케이션으로 데이터를 끌어와 처리하는 것보다 DB 안에서 프로시저로 돌리는 게 훨씬 효율적이다. 데이터를 "움직이지 않고" 처리하는 셈이라 네트워크도, 메모리도 절약된다.

---

## 그런데 왜 요즘 덜 쓰이는가

현대 웹 서비스에서는 프로시저 사용이 예전만큼 많지 않다. 이유가 여러 가지다.

첫째, **버전 관리가 어렵다.** 애플리케이션 코드는 Git으로 관리되고 PR 리뷰를 거치지만, 프로시저는 DB 안에 저장된 상태라 **코드베이스와 분리** 돼 버린다. 누가 언제 왜 바꿨는지 추적이 어렵고, 스테이징과 프로덕션 간 프로시저 버전이 어긋나는 사고도 잦다. 마이그레이션 도구(Flyway, Liquibase) 로 DDL처럼 관리할 수는 있지만, 애플리케이션 코드만큼 자연스럽지는 않다.

둘째, **테스트가 어렵다.** 애플리케이션 코드는 단위 테스트로 로직을 검증할 수 있지만, 프로시저는 DB가 떠 있어야 테스트가 가능하고, mocking도 쉽지 않다. 논리가 복잡해질수록 디버깅이 고통이 된다.

셋째, **DB 벤더에 종속된다.** MySQL의 프로시저 문법과 PostgreSQL, Oracle의 문법이 전부 다르다. 나중에 DB를 바꿔야 할 때 프로시저 전체를 다시 작성해야 한다. 애플리케이션 레이어에 로직을 두면 JPA 같은 추상화 덕분에 DB 교체가 훨씬 쉽다.

넷째, **수평 확장이 안 된다.** 비즈니스 로직이 DB에 몰려 있으면 계산 부담도 DB가 진다. 웹 서버는 여러 대로 늘리기 쉽지만 DB는 그렇지 않다. 애플리케이션 레이어에 로직을 두면 부하가 생길 때 서버 대수만 늘리면 되지만, 프로시저에 몰려 있으면 DB 자체를 키우는 수밖에 없다.

다섯째, **비즈니스 로직이 분산** 된다. 일부는 애플리케이션 코드에, 일부는 DB 프로시저에 흩어져 있으면 "이 요청이 어떻게 처리되는지"를 파악하려면 두 군데를 다 봐야 한다. 유지보수 난이도가 올라간다.

## Stored Procedure vs Function vs Trigger

자주 헷갈리는 개념들을 간단히 구분하면 이렇다.

- **Function**: 단일 값을 반환하는 함수형 객체. `SELECT get_discount(user_id)` 처럼 쿼리 안에서 호출할 수 있다.
- **Procedure**: 결과 집합(result set)을 반환하거나 값을 안 반환하거나 다양하다. `CALL`로 호출한다.
- **Trigger**: INSERT/UPDATE/DELETE 같은 이벤트에 자동으로 반응해서 실행되는 특수한 프로시저다. 이벤트 기반이라는 점에서 수동 호출인 Procedure와 다르다.

---

## 현대 백엔드 개발자 관점

Spring Boot + JPA 같은 현대적 스택에서 프로시저를 쓰는 경우는 드물다. 대부분의 비즈니스 로직은 **서비스 레이어(@Service)** 에 두고, 복잡한 조회는 **QueryDSL이나 JPQL** 로 해결한다. StyleHub 프로젝트도 이 패턴을 따르고 있고, 프로시저는 전혀 쓰지 않는다. 테스트 가능성, 버전 관리, 디버깅 편의성을 우선했기 때문이다.

그렇다고 프로시저가 완전히 사라진 건 아니다. **대용량 배치 작업**(매일 새벽 집계, 통계 산출 등) 이나 **DB 내부 자동화**(파티션 관리, 아카이빙 등), 레거시 시스템과의 연동에서는 여전히 쓰인다. 특히 데이터가 수억 건을 넘어가는 집계 작업은 애플리케이션으로 끌어와 처리하면 네트워크와 메모리 비용이 감당이 안 되기 때문에, DB 안에서 프로시저나 `INSERT ... SELECT` 같은 방법으로 처리하는 게 여전히 정석이다.

## 면접에서 나올 법한 질문과 답

### Q1. "Stored Procedure를 쓰면 좋은 점이 뭔가요?"

> 네트워크 왕복 감소, 실행 계획 캐시로 인한 성능 이점, 복잡한 트랜잭션을 DB 안에서 원자적으로 묶을 수 있다는 점, 그리고 테이블 직접 접근을 제한하고 프로시저 실행 권한만 허용하는 방식의 보안 계층화가 전통적인 장점입니다.

### Q2. "그런데 왜 현대 웹 애플리케이션에서는 잘 안 쓰나요?"

> 버전 관리가 어렵고, 테스트와 디버깅이 불편하며, DB 벤더에 종속되어 이식성이 떨어지기 때문입니다. 무엇보다 비즈니스 로직이 애플리케이션과 DB로 분산되면 유지보수가 어려워지고, DB에 계산 부담이 몰려 수평 확장이 어려워진다는 구조적 단점이 있습니다. 그래서 저는 Spring Service 레이어에 로직을 두고 JPA/QueryDSL로 쿼리를 구성하는 방식을 택했습니다.

### Q3. "프로시저가 꼭 필요한 경우는 어떤 경우인가요?"

> 수억 건 규모의 배치 집계처럼 **데이터를 애플리케이션으로 끌어오는 비용이 엄청나게 큰 작업** 이나, DB 파티션 관리·아카이빙 같은 **DB 내부 자동화** 는 지금도 프로시저가 유효하다고 생각합니다. 일반적인 웹 요청 처리에는 부적합하지만, "데이터를 움직이지 않고 처리해야 하는 상황"에서는 여전히 강력한 도구입니다.

### Q4. "Procedure와 Function의 차이는?"

> Function은 단일 값을 반환하고 `SELECT` 쿼리 안에서도 호출할 수 있어서 일반 SQL 식처럼 사용 가능합니다. Procedure는 결과 집합 반환이나 값 없는 수행이 가능하고, 별도의 `CALL` 문으로만 호출합니다. 용도상 Function은 "계산", Procedure는 "작업 수행"에 가깝습니다.

---

## 한 문장 요약

**Stored Procedure는 DB에 저장해둔 SQL 프로그램이고, 네트워크 왕복이 비쌌던 시대에는 필수에 가까웠지만, 현대 웹 개발에서는 버전 관리·테스트·수평 확장의 어려움 때문에 비즈니스 로직은 애플리케이션 레이어에, 프로시저는 대용량 배치나 DB 내부 자동화 같은 특수 용도에 국한해서 쓰는 게 정석이다.**

## 추가 학습 키워드

- **Prepared Statement**: 프로시저의 실행 계획 캐시와 비슷한 효과를 애플리케이션 레벨에서 제공
- **Flyway / Liquibase**: DB 스키마·프로시저 버전 관리 도구
- **Trigger**: 이벤트 기반 자동 실행 프로시저
- **Cursor**: 프로시저 내부에서 결과 집합을 한 행씩 순회하는 포인터 (반복 처리용)
- **CTE (Common Table Expression)** / **Window Function**: 프로시저 없이도 복잡한 집계를 SQL로 해결하게 해주는 현대 SQL 기능
