# 재고 동시성 제어 — 비관적 락을 선택하기까지의 고민

## 문제 상황

StyleHub은 패션 이커머스 플랫폼이다. 인기 상품에 동시 주문이 몰리면 재고가 정확히 차감되어야 한다. 동시성 테스트를 작성하여 재고 1개인 상품에 10명이 동시에 주문하는 상황을 재현했을 때, 2명 이상이 주문에 성공하는 Lost Update 문제를 발견했다.

```
재고: 1개

스레드 A: 재고 1 읽음 → 1 - 1 = 0 저장
스레드 B: 재고 1 읽음 → 1 - 1 = 0 저장 (A가 커밋하기 전에 읽음)

결과: 2명이 주문 성공, 재고 0. 상품은 1개인데 2개가 팔림.
```

두 트랜잭션이 같은 재고 값을 동시에 읽고 수정하면서 한쪽의 변경이 유실되는 것이 원인이었다. 이걸 어떻게 해결할지 여러 방법을 검토했다.

---

## 검토한 5가지 방법

재고 동시성을 제어하는 방법은 락을 거는 방식만 있는 게 아니다. 락 없이도 해결할 수 있는 방법이 있어서 모두 비교해봤다.

### 1. 비관적 락 (SELECT FOR UPDATE)

```sql
SELECT * FROM products_options WHERE product_option_id = 1 FOR UPDATE;
-- 이 행을 잠금. 다른 트랜잭션은 커밋될 때까지 대기
UPDATE products_options SET stock_quantity = stock_quantity - 1 WHERE product_option_id = 1;
```

행에 배타적 락을 걸어서 다른 트랜잭션이 접근하지 못하게 한다. 확실하지만 대기 시간이 발생한다. 100명이 동시에 같은 옵션을 주문하면 마지막 사람은 약 1초를 대기해야 한다.

### 2. 낙관적 락 (@Version)

```java
@Version
private Long version;
```

읽을 때 version을 기억하고, 저장할 때 version이 바뀌었으면 충돌로 판단하여 예외를 던진다. 락을 걸지 않아 대기가 없지만, 충돌이 발생하면 애플리케이션에서 재시도 로직을 구현해야 한다.

재고 차감은 인기 상품에 주문이 몰릴 때 충돌 확률이 매우 높다. 충돌이 잦으면 재시도가 반복되어 오히려 비관적 락보다 느려질 수 있고, 사용자에게 "다시 시도해주세요"를 보여줘야 하는 상황이 생긴다. 재고 차감처럼 충돌이 빈번한 연산에는 적합하지 않다고 판단했다.

### 3. DB 원자적 UPDATE (락 불필요)

```sql
UPDATE products_options
SET stock_quantity = stock_quantity - 1
WHERE product_option_id = 1 AND stock_quantity >= 1;
```

한 쿼리로 "재고 확인 + 차감"을 동시에 처리한다. DB가 내부적으로 원자성을 보장하므로 별도의 락이 필요 없다. 영향받은 행(affected rows)이 0이면 재고 부족으로 판단한다.

이 방법이 가장 단순하고 성능도 좋지만, 치명적인 한계가 있었다. StyleHub의 주문 생성은 재고 차감만 하는 게 아니다. 재고를 차감한 뒤에 **상품 가격, 스토어 정보** 같은 추가 데이터가 필요하다. 주문 항목(OrderItem)을 생성하려면 `option.getProduct().getPrice()`와 `option.getProduct().getStore().getName()`이 필요한데, 단순 UPDATE 쿼리만으로는 이 정보를 가져올 수 없다.

별도로 SELECT를 추가하면 되지만, 그러면 "SELECT → UPDATE" 사이에 다시 동시성 문제가 발생할 수 있어 결국 락이 필요해진다. 그렇다면 처음부터 SELECT FOR UPDATE로 읽으면서 락을 거는 게 더 깔끔하다.

### 4. Redis DECR (락 불필요)

```
DECR stock:option:1 → 99 (원자적, 동시 1000명도 ~1ms)
```

Redis의 DECR은 원자적 연산이라 락 없이도 동시성이 보장된다. 메모리 기반이라 1000명이 동시에 요청해도 ~1ms로 처리된다. 비관적 락의 대기 시간 문제가 완전히 해결된다.

하지만 Redis에서 재고를 차감한 뒤 DB에 최종 반영하는 "이중 저장소" 구조가 필요하다. Redis와 DB 사이의 정합성을 보장해야 하고, Redis 장애 시 복구 로직도 필요하다. 현재 단일 서버 환경에서 이 복잡도를 감수할 이유가 없었다.

### 5. Redis 분산 락 (SETNX)

```
SETNX lock:stock:1 → 락 획득
-- 재고 처리
DEL lock:stock:1 → 락 해제
```

Redis SETNX로 분산 환경에서 락을 건다. 서버가 여러 대일 때 같은 DB를 사용하지 않아도 동시성을 제어할 수 있다. 하지만 현재 단일 서버이므로 DB 비관적 락으로 충분하고, Redis 분산 락은 과한 선택이다.

## 비교 정리

| 방법 | 락 필요 | 동시 1000명 | 추가 데이터 조회 | 현재 적합성 |
|------|---------|-----------|----------------|-----------|
| 비관적 락 | O | ~10초 (대기) | SELECT 시 함께 조회 | **적합** |
| 낙관적 락 | X (Version) | 재시도 반복 | 가능 | 충돌 빈번하여 부적합 |
| DB 원자적 UPDATE | X | ~1초 | **불가** (UPDATE만) | 추가 데이터 필요하여 부적합 |
| Redis DECR | X | ~1ms | 별도 조회 필요 | 이중 저장소 복잡도 과함 |
| Redis 분산 락 | O (Redis) | ~1ms | 별도 조회 필요 | 단일 서버에서 과함 |

## 비관적 락을 선택한 이유

결론적으로 비관적 락을 선택한 이유는 세 가지다.

**첫째, 주문 생성에는 재고 차감만이 아니라 추가 데이터가 필요하다.** 주문 항목을 생성하려면 상품 가격, 스토어 정보가 필요한데, SELECT FOR UPDATE로 재고를 잠그면서 동시에 Product와 Store를 fetch join으로 함께 가져올 수 있다. DB 원자적 UPDATE로는 이 정보를 가져올 수 없고, 별도 SELECT를 추가하면 동시성 문제가 다시 발생한다.

**둘째, 주문 생성 + 재고 차감 + 주문 항목 저장이 한 트랜잭션이어야 한다.** 비관적 락은 트랜잭션 내에서 자연스럽게 동작한다. Redis DECR은 DB 트랜잭션 밖에서 실행되므로 Redis와 DB 사이의 정합성을 별도로 관리해야 한다.

**셋째, 현재 단일 서버 + 단일 DB 환경이다.** Redis 분산 락이나 Redis DECR의 이중 저장소 구조는 현재 규모에서 과한 복잡도다. 비관적 락으로 충분하고, 추후 트래픽이 늘어나면 전환할 수 있도록 `@DistributedLock` AOP를 미리 준비해두었다.

## 비관적 락 위에서 추가로 해결한 문제들

비관적 락을 적용한 것만으로는 끝이 아니었다. 실제 주문 시나리오에서 발생할 수 있는 문제들을 하나씩 해결했다.

### Deadlock 방지 — TreeMap으로 정렬 + 합산

여러 옵션을 동시에 주문할 때 deadlock이 발생할 수 있다:

```
스레드 A: 옵션 1 락 획득 → 옵션 2 락 대기
스레드 B: 옵션 2 락 획득 → 옵션 1 락 대기
→ 서로 무한 대기 (deadlock)
```

모든 트랜잭션이 같은 순서로 락을 획득하면 deadlock이 발생하지 않는다. TreeMap을 활용하여 optionId를 오름차순으로 정렬한 뒤 순서대로 락을 획득하도록 했다. TreeMap은 같은 옵션이 중복으로 들어온 경우 수량을 합산하는 역할도 동시에 수행한다.

```java
private List<OrderItemRequest> mergeAndSort(List<OrderItemRequest> itemRequests) {
    Map<Long, Integer> merged = new TreeMap<>(); // optionId 오름차순 자동 정렬
    for (OrderItemRequest request : itemRequests) {
        merged.merge(request.productOptionId(), request.quantity(), Integer::sum);
    }
    ...
}
```

optionId=1(수량2), optionId=1(수량3)이 들어오면 optionId=1(수량5)로 합산되어 락을 1번만 획득한다. 정렬과 합산을 TreeMap 하나로 동시에 처리한 것이 이 구조의 핵심이다.

### N+1 방지 — fetch join으로 락 + 데이터 조회를 한 쿼리에

비관적 락으로 옵션을 조회할 때 Product와 Store도 함께 필요하다. fetch join 없이 접근하면 옵션 N개마다 Product 조회 N번, Store 조회 N번이 추가로 발생한다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT po FROM ProductOption po JOIN FETCH po.product p JOIN FETCH p.store WHERE po.productOptionId = :optionId")
Optional<ProductOption> findByIdWithLock(@Param("optionId") Long optionId);
```

비관적 락 + 데이터 조회를 한 쿼리로 처리하여 불필요한 쿼리를 제거했다.

### 재고 복구에도 비관적 락 — Lost Update 방지

주문 취소 시 재고를 복구하는 `increaseStock()`에서 처음에는 `findById()`로 조회한 뒤 재고를 증가시켰다. 하지만 동시에 다른 사용자가 같은 옵션을 주문 중이라면 `decreaseStockWithLock()`이 비관적 락으로 재고를 차감하고 있는데, 락 없이 읽은 값에 증가시키면 Lost Update가 발생한다.

```
Thread A: decreaseStockWithLock → stock=10, lock 획득 → stock=8 (2개 차감)
Thread B: increaseStock → findById → stock=10 읽음 (락 없이) → stock=13 (3개 복구)
Thread A: commit → stock=8 저장
Thread B: commit → stock=13 저장  ← Thread A의 차감이 사라짐
```

재고를 변경하는 모든 경로에서 동일한 락 전략을 사용해야 정합성이 보장된다. `increaseStock()`도 `findByIdWithLock()`을 사용하도록 수정했다.

```java
// 수정 전: 락 없이 조회 → Lost Update 가능
public void increaseStock(Long optionId, int quantity) {
    ProductOption option = productOptionRepository.findById(optionId) ...
}

// 수정 후: 비관적 락으로 조회 → 정합성 보장
public void increaseStock(Long optionId, int quantity) {
    ProductOption option = productOptionRepository.findByIdWithLock(optionId) ...
}
```

### 엔티티 캡슐화 — 재고 부족 검증을 엔티티 내부에

재고 부족 검증을 서비스에서 하면 호출하는 모든 곳에서 반복해야 한다. ProductOption 엔티티의 `decreaseStock()` 메서드에 캡슐화하여 어디서 호출해도 규칙이 보장되도록 했다.

```java
public void decreaseStock(int quantity) {
    if (this.stockQuantity < quantity) {
        throw new BusinessException(ErrorCode.INSUFFICIENT_STOCK);
    }
    this.stockQuantity -= quantity;
}
```

### DB 접근 최소화 — 7쿼리로 주문 생성

Address fetch join으로 User 별도 조회를 제거하고, 비관적 락 fetch join으로 Product/Store 프록시 초기화를 방지하고, saveAll()로 주문 항목을 배치 INSERT하여 옵션 2개 기준 총 7쿼리로 최적화했다.

| 순서 | 쿼리 | 설명 |
|------|------|------|
| 1 | SELECT address + user | 배송지 + 유저 fetch join |
| 2 | INSERT orders | 주문 생성 |
| 3 | SELECT option + product + store FOR UPDATE | 옵션1 비관적 락 |
| 4 | SELECT option + product + store FOR UPDATE | 옵션2 비관적 락 |
| 5 | UPDATE products_options | 옵션1 재고 차감 |
| 6 | UPDATE products_options | 옵션2 재고 차감 |
| 7 | INSERT order_items (배치) | 주문 항목 저장 |

## 동시성 테스트 결과

ExecutorService와 CountDownLatch로 10개 스레드가 동시에 주문하는 테스트를 작성했다.

**테스트 1: 재고 10개 + 10명 동시 주문**

```
성공: 10
실패: 0
최종 재고: 0
```

**테스트 2: 재고 5개 + 10명 동시 주문**

```
성공: 5
실패 (INSUFFICIENT_STOCK): 5
최종 재고: 0
```

비관적 락이 없으면 테스트 1에서 최종 재고가 0이 아닌 값이 되고, 테스트 2에서 5명 이상이 성공하여 재고가 음수가 된다. 비관적 락 덕분에 두 테스트 모두 정합성 100%를 확인했다.

## 비관적 락의 한계와 대응 계획

비관적 락에 만족하고 있지만 한계도 인지하고 있다.

### 동시 주문이 1000명이면?

트랜잭션 하나당 약 10ms가 걸린다면 1000번째 사용자는 약 10초를 대기해야 한다. 10초면 사용자가 이탈하는 수준이다. 현재 패션 이커머스 특성상 같은 옵션에 동시 1000명이 몰리는 상황은 타임세일이 아니면 드물지만, 대비는 필요하다.

Redis DECR로 전환하면 락 없이 원자적으로 재고를 차감할 수 있어 1000명이 동시에 요청해도 ~1ms로 처리된다. `@DistributedLock` AOP를 미리 준비해두었으므로 전환 비용이 크지 않다.

### 서버가 여러 대이면?

DB 비관적 락은 같은 DB를 사용하는 서버에서만 유효하다. 스케일아웃 시 Redis 분산 락이 필요하다. 이미 DistributedLockAspect를 구현해두었으므로 어노테이션만 교체하면 된다.

```java
// 현재: DB 비관적 락
ProductOption option = productOptionRepository.findByIdWithLock(optionId);

// 추후: Redis 분산 락 전환 시
@DistributedLock(key = "'stock:' + #optionId")
public ProductOption decreaseStockWithLock(Long optionId, int quantity) { ... }
```

## 정리

재고 동시성 제어에 비관적 락, 낙관적 락, DB 원자적 UPDATE, Redis DECR, Redis 분산 락 다섯 가지를 검토했다. 비관적 락을 선택한 건 주문 생성에 재고 차감 외 추가 데이터가 필요하고, 한 트랜잭션으로 묶여야 하며, 현재 단일 서버 환경에서 가장 단순하면서 확실한 방법이기 때문이다.

비관적 락 위에서 deadlock 방지(TreeMap 정렬), 중복 옵션 합산, fetch join N+1 방지, 7쿼리 최적화, 엔티티 캡슐화를 추가로 적용하여 단순히 락을 거는 것 이상의 설계를 했다. 추후 트래픽이 늘어나면 Redis DECR로 전환할 수 있는 구조를 미리 준비해두었다.

## 코드 리뷰 후 개선 사항 (2026-03-27)

코드 리뷰를 통해 동시성과 성능에 영향을 주는 문제들을 발견하고 수정했다.

### 1. 재고 복구에도 비관적 락 적용 — Lost Update 방지

주문 취소 시 `increaseStock()`이 `findById()`로 락 없이 조회하면, 동시에 같은 옵션을 주문 중인 `decreaseStockWithLock()`의 변경이 유실될 수 있다. 재고를 변경하는 모든 경로에서 동일한 락 전략을 사용하도록 `findByIdWithLock()`으로 수정했다.

### 2. 주문 취소 시 N+1 제거 — fetch join 적용

`cancelOrder()`에서 `findByOrderOrderId()`로 OrderItem을 조회하면 각 아이템마다 `getProductOption()`에서 LAZY 로딩이 발생했다. `findByOrderIdWithDetails()`로 교체하여 OrderItem + ProductOption + Product + Store를 한 쿼리로 가져오도록 수정했다.

### 3. Redis 타임아웃 처리 — Lua 스크립트로 원자적 처리

기존에는 `ZRANGEBYSCORE`로 조회한 뒤 개별 `ZREM`으로 제거했다. 조회와 제거 사이에 다른 서버가 동일 데이터를 읽어 불필요한 중복 시도가 발생할 수 있었다. Lua 스크립트로 조회+제거를 원자적으로 실행하여 다중 서버 환경에서의 효율성을 높였다.

```lua
local orders = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, ARGV[2])
if #orders > 0 then
    redis.call('ZREM', KEYS[1], unpack(orders))
end
return orders
```

### 4. 보정 스케줄러 배치 LIMIT 추가

`findExpiredOrders()`에 `Pageable`을 추가하여 한 번에 최대 100건만 처리하도록 수정했다. Redis가 장시간 장애 시 수천 건이 누적되어 OOM이 발생하는 것을 방지한다.

### 5. 금액 계산 로직 중복 제거 — Order 엔티티로 이동

`totalAmount - discountAmount - usedPoint` 계산이 OrderTransactionService와 OrderViewService에 중복되어 있었다. Order 엔티티에 `calculateFinalAmount(int totalAmount)` 메서드를 추가하여 금액 계산 규칙을 한 곳에서 관리하도록 했다.

### 6. 디미터 법칙 준수 — ProductOption 위임 메서드 추가

`item.getProductOption().getProduct().getStore().getStoreId()`처럼 3~4단계 체이닝으로 결합도가 높았다. ProductOption에 `getProductName()`, `getStoreId()`, `getStoreName()` 위임 메서드를 추가하여 2단계로 축소했다.

### 7. OrderItem — BaseEntity 상속으로 시간 관리 일관성 확보

OrderItem만 `createdAt`을 `LocalDateTime.now()`로 직접 관리하고 있었다. BaseEntity를 상속하여 `@CreatedDate`/`@LastModifiedDate`로 다른 엔티티와 동일한 방식으로 통일했다.
