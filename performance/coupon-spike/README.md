# 선착순 쿠폰 오픈 순간 측정 (2026-10-01)

## 왜 다시 쟀나
기존 선착순 쿠폰 측정(`performance/locustfile_coupon.py`)은 같은 500명이 7분 동안 0.05~0.2초 간격으로 계속 발급을 요청하는 방식이었다. 목표는 "몰려도 정해진 수량만 나가는가"였고 그 검증에는 충분했다. 하지만 쿠폰은 처음 몇 초 안에 다 나가므로 응답 시간 수치 대부분이 매진 뒤 거절 구간이었다. 선착순에서 궁금한 오픈 순간(매진까지 걸린 시간, 성공·거절 응답 시간, 그동안 다른 API가 받는 영향)은 따로 보지 못했다. 이 측정은 그 순간만 본다.

## 비교 대상
- **비관적 락**: 커밋 `fcb4011`(2026-05-03). 쿠폰 이벤트 행을 `SELECT … FOR UPDATE`로 잠근 뒤 발급 수를 올린다. 지표 수집용으로 actuator·prometheus 의존성 두 줄만 더했다(`old-build-gradle.patch`). 업무 코드는 그대로다.
- **지금 구조**: develop `1ba1a9f`. Redis Lua 사전 확인이 매진·중복을 거르고, 통과한 요청은 MySQL 조건부 UPDATE로 한도를 최종 확인한다. 운영에서는 이벤트를 만들 때 커밋 뒤 Redis 수량을 올려 두므로(`resetIssueCounterAfterCommit`) 본측정도 수량을 미리 올려 둔 상태(`PREWARM=1`)로 쟀다.
- 분산 락은 코드가 삭제돼(`803db01`) 다시 재지 않았다.

## 조건
- 한 맥(16코어)에서 앱, MySQL 8.0과 Redis 7(Docker), Locust 2.43.4가 함께 돈다. 절대 수치보다 두 버전의 비교에 의미가 있다.
- 두 버전 모두 같은 MySQL·Redis 컨테이너(데이터베이스만 다름), 힙 1GB, Hikari 100, Tomcat 스레드 400과 accept-count 200, 같은 JDBC 설정(`old.properties`, `new.properties`).
- OSIV는 다르다. 비관적 락 버전은 당시 기본값(켜짐), 지금 구조는 운영 설정(꺼짐)이다. 옛 코드는 OSIV를 끄면 깨질 수 있어 맞추지 않았다.
- 한 버전을 잴 때 다른 버전 앱은 내려 두었다. 버전마다 예열 회차를 먼저 돌리고 버렸다.
- 데이터: 판매자 1명, 상품 10,000개(`seed-base.sql`), 구매자 1,000명(`../seed-test-buyers.sql`), 쿠폰 이벤트(`../seed-test-coupons.sql`, 회차마다 초기화).

## 부하 (`locust_spike.py`)
- 구매자 1,000명을 측정 전에 미리 로그인시킨다(`login.py`). 로그인(BCrypt) 비용이 측정에 섞이지 않게 하려는 것이다.
- 시작 25초 뒤 1,000명이 같은 시각에 첫 발급 요청을 보낸다. 성공(200)이나 거절(4xx)을 받으면 멈춘다. 5xx나 연결 오류면 0.1초 뒤 다시 누르고 최대 3번까지 시도한다.
- 배경 부하로 상품 목록 조회 50명이 처음부터 끝까지 사용자당 초당 2건씩 돈다. 캐시를 타지 않는 커서 페이지를 고른다.
- 시나리오는 100장 / 1,000명과 1,000장 / 1,000명. Locust는 4개 프로세스로 나눠 돌렸다.

## 무엇으로 쟀나
- **사용자 기준 지연**: Locust가 요청마다 남긴 기록. 서버 스레드를 기다린 시간까지 포함한다. 표의 P50·P99는 첫 시도 기준이다.
- **서버 처리 시간**: Tomcat 접근 로그 `%D`. 스레드를 얻은 뒤부터라 줄 선 시간은 빠진다. 1,000건이 같은 순간에 와도 서버가 처리를 시작한 시각은 수 초에 걸쳐 퍼졌다. 그래서 사용자 기준 값을 주로 본다.
- **매진·완료 시각**: 요청을 보낸 시각부터 마지막 성공 응답(또는 마지막 응답)까지.
- **정합성**: DB 발급 수, 중복 발급 수, Redis 카운터.
- **DB 연결 대기, Tomcat 바쁜 스레드**: actuator를 읽은 최대값. 비관적 락과 수량 없는 지금 구조 회차는 1초마다, 본측정(newp)은 0.2초마다 읽었다. 몰림이 1~2초에 끝나 1초 간격은 순간을 놓칠 수 있어 바꿨다.
- **간섭 게이트**(`foreign.sh`): 측정과 무관한 프로세스 CPU 합이 250% 미만이고 Jenkins 컨테이너가 10% 미만인 상태가 5초 간격 3번 연속일 때 시작한다. 측정 중 외부 CPU도 기록했다.

## 측정 중 고친 것
예열 회차에서 1,000장 중 998장만 나갔다. Locust 프로세스 4개에 사용자가 고르게 나뉘지 않아 한 구매자의 세션을 두 사용자가 함께 썼다. 그래서 같은 사람이 동시에 두 번 요청했고 유니크 키 위반(500)과 중복(409)이 났다. 측정 도구의 결함이라 파일 잠금으로 세션을 한 번씩만 나눠 주게 고친 뒤 본측정을 했다.

처음 지금 구조 회차(`new`)는 회차마다 Redis 쿠폰 키를 지워 수량이 없는 상태로 쟀다. 운영에서는 이벤트를 만들 때 수량을 올려 둔다는 것을 뒤에 코드에서 확인했다. 수량이 없으면 오픈 순간 몰린 요청이 수량을 만들려고 이벤트 행 잠금(`FOR UPDATE`)에 줄을 선다. 그래서 수량을 미리 올린 회차(`newp`)를 본측정으로 쓰고 수량 없는 회차는 `results/results-cold-counter.md`에 남겼다. `results/results-diag.md`는 수량 없는 회차와 그때 따로 돌린 수량을 올린 진단 회차를 비교한 표다.

## 읽는 법
- **정합성**은 모든 회차에서 정확했다. 서버 오류와 재시도도 0이었다.
- **100장 경쟁에서는 거절이 줄을 서지 않게 됐다.** 비관적 락은 매진으로 거절될 요청도 행 락을 기다려 거절 응답(2.65초)이 성공 응답(0.71초)보다 느렸다. 지금 구조는 매진 뒤 요청을 Redis 사전 확인에서 끝내 거절 응답이 0.46초가 됐다. 모든 응답이 끝나는 시간도 4.1초에서 1.07초로 줄었고 범위가 겹치지 않는다.
- **발급 성공 응답은 거의 같다.** 0.71초 대 0.80초이고 범위가 겹친다.
- **다른 API가 받는 영향이 줄었다.** 몰리는 동안 상품 조회 P99가 3.4초에서 0.37초로 줄었다. 100장 경쟁에서 DB 연결 대기 최대도 300에서 139로 내려갔다.
- **1,000명이 모두 받는 경쟁은 여전히 무겁다.** 1,000건이 모두 같은 쿠폰 행에 조건부 UPDATE를 하므로 DB 연결이 다 찼다. 다 나가는 시간은 8.9초에서 5.8초로 줄었지만, 비관적 락 회차는 외부 CPU가 더 높을 때 돌아(최대값 중앙값 584% 대 187%) 줄어든 폭은 표보다 작을 수 있다.

## 한계
- 한 머신 측정이다. 외부 CPU(브라우저 등)가 회차마다 달랐고 기록해 두었다.
- OSIV 설정이 두 버전에서 다르다.
- 먼저 누른 사람이 먼저 받았는지(순서 공정성)는 보지 않았다.
- 1,000명이 모두 받는 경우 같은 쿠폰 행 하나에 UPDATE가 몰리는 한계는 남아 있다.

## 다시 돌리는 법
1. 측정용 컨테이너: `docker run -d --name spike-mysql -p 127.0.0.1:13317:3306 -e MYSQL_ROOT_PASSWORD=perf mysql:8.0 --max-connections=500`, `docker run -d --name spike-redis -p 127.0.0.1:16389:6379 redis:7-alpine`
2. 두 버전의 jar를 빌드한다. 비관적 락은 `git worktree add <dir> fcb4011` 뒤 `old-build-gradle.patch`를 적용하고 `./gradlew bootJar -x test`.
3. 이 폴더에서 `SPIKE_HOME=$(pwd)`로 앱을 띄우고 PID를 적는다. 예: `SPIKE_HOME=$(pwd) java -Xms1g -Xmx1g -jar <old.jar> --spring.config.location=file:old.properties & echo $! > app-old.pid`
4. 앱이 스키마를 만든 뒤 시드를 넣는다: `seed-base.sql`, `../seed-test-buyers.sql`
5. `./run.sh old 100 old-100-r1`, `PREWARM=1 ./run.sh new 100 newp-100-r1` 처럼 회차를 돌리고 `python3 aggregate.py old+old2 newp`로 모은다. `PY`, `LOCUST` 환경 변수로 파이썬과 Locust 경로를 바꿀 수 있다.
